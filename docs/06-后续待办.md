**验收结果**（`python scripts/demo_service_split.py`）：

```
✓ 两个进程能独立启动            —— 记忆服务是子进程，Agent 通过 HTTP 访问
✓ 杀掉记忆服务主流程仍能返回结果  —— recall 返回空列表而非崩溃，耗时 1048ms
✓ 能画出服务拓扑图              —— 见下方
```

**服务拓扑**：

```
[Agent 进程]                          [记忆服务进程]
 TriageAgent                              MemoryService
  ├─ react.py 主循环                        ├─ HTTP 路由
  ├─ tools/registry.py                     ├─ MemoryStore (SQLite)
  │    └─ RemoteMemoryStore ──HTTP/JSON──→ ├─ APIEmbedding (1024 维)
  │         · 超时 1.0s                    └─ 冲突队列 / 轨迹归档
  │         · 失败 → 降级（空结果）
  └─ 无状态，可水平扩展                     有状态，可独立伸缩/备份
```

**核心设计：降级**（这是拆分里最重要的部分）

很多人拆服务只关心"怎么调通"，不关心"调不通怎么办" ——
结果系统**变得更脆**（原来进程内调用不会失败，现在多了一跳网络）。

所以本项目把降级做成了**架构保证**而不是"每处记得写 try/except"：

| 方法 | 失败时返回 | 理由 |
|---|---|---|
| `recall` | `[]` | 少一条记忆参考，继续判断 |
| `insert` | `False` | 这次没沉淀，不影响当前结论 |
| `find_similar` | `None` | 表示"没找到重复"，**绝不会误判成"是重复"** |
| `count` | `0` | |

降级逻辑收在 `RemoteMemoryStore._call()` **一处** ——
如果散布在 12 个调用点上，"每处都要记得写"的东西必然会在某处被忘记。

**新增的可观测指标**：`degradation_rate()`（降级率）。
拆分引入了新的失败模式，不监控就等于把风险藏起来。

**顺带铺了 AI Infra 那条线**：每路由的延迟、降级率、记忆条数都是独立指标。

**踩到的坑（3 个，都不报错、只静默走错分支）**：

1. **`except` 顺序** —— `HTTPError` 是 `URLError` 的子类，
   写在父类后面永远匹配不到。正确顺序是**从具体到宽泛**（叶子到根）。
2. **平台差异** —— 我按 Linux 行为写了"连接被拒 → `ConnectionRefusedError`"，
   但 **Windows 上连接被拒表现为 `TimeoutError`**。代码按一个平台写、在另一个平台跑，
   静默走了重试分支，让降级耗时从 1 秒变成 3 秒。
3. **改了默认值但没生效** —— demo 里显式传了 `retries=1`，覆盖了新默认值。
   **改默认值之后要检查所有显式传参的调用点。**

**生产环境还需补**（已写在 `service.py` 的模块文档里）：
鉴权（现在无鉴权，只应监听内网）、向量索引（现在是全表扫描，
上万条后必须换 HNSW/IVF —— **这是最先会遇到的瓶颈**）、
连接池（SQLite 单写锁）、每路由延迟直方图、完整的优雅关闭。

**工作量**：约 1 天（原估 1~2 周，因为不需要 K8s，只做服务边界）

**验收结果**（`python scripts/demo_semantic.py`）：

```

    —— 两组超阈值模式被提案，单例未被提案（验证阈值生效）
✓ 未经审核的模式不会进入语义层
    —— scan() 之后语义层仍为 0；拒绝后仍为 1
✓ 审核通过后，新 issue 能检索到这条 SOP
    —— 跨层检索：语义层给规则（相似度 0.42），情景层给案例（0.50）
```

**★ 三层记忆的风险量级不同 —— 这是闸门的理由**

```
工作记忆  → 无持久影响                       自动管理
情景记忆  → 写错了最多影响**一次召回**        自动写入（评分够就写）
语义记忆  → 写错了会被**所有后续同类任务**召回   ★ 必须人工批准
```

语义记忆相当于**写下一条规则**。规则错了会被反复应用：

```
事实错了 → 错一次
规则错了 → 错很多次
```

**所以"人工闸门"不是技术做不到自动，是不该自动。**

**CLI 的三个设计决定**（都是为了"闸门不被绕过"）：

| 决定 | 理由 |
|---|---|
| **拒绝必须给理由**（`--note` 必填） | 同一模式以后可能又被扫出来；看到"上次谁为什么拒"就不用重复判断。**不需要理由的审核会退化成点按钮。** |
| **`--by` 必填** | 审核是人为决定，必须能追溯到人。没有署名的记录等于没有记录。 |
| **审核后不能改** | 允许反复改的话，就无法回答"这条 SOP 到底是谁批的"。要改结论应重新走流程。 |

**★ 触发入口的取舍**（`docs/06` 原来说"需要接上调用入口"）

入口**不该是主循环**，理由：
1. **成本**：`scan()` 要遍历全部情景记忆（O(n)），而主循环是热路径
2. **语义**：SOP 提炼是**低频动作**，不是每个任务结束都该重新评估

正确入口：**定时任务**（cron 每天 `--scan`）或**人工触发**。

> **"写好了但没接上"和"接错地方"是两种不同的错误。**
> 前者的解法是补入口，后者是换入口 —— 不想清楚就接，容易做成后者。

**★ 顺带修掉一个潜伏的接口不一致 bug（5 处）**

做 P1-2 时发现 `recall()` 返回的是 `[(记忆, 相似度), ...]`，
但**有 5 处调用点把它当 `[记忆]` 用了**（含 1 处生产代码 `memory/service.py`）。

```
本地 MemoryStore.recall       → [(MemoryRecord, float), ...]
远程 RemoteMemoryStore.recall → [MemoryRecord, ...]      ← 不一致！
```

**后果**：同一段调用代码，单机模式能跑、切到分布式就崩 ——
这种 bug 最难查，因为"本地测试全过"。

**为什么一直没暴露**：因为演示用哈希伪向量，召回恒为空，
循环体一次都没执行。

> **"空结果"会掩盖序列化 bug。**
> 测试召回类接口时，一定要构造"能召回出东西"的用例 ——
> 只测"空输入返回空"等于没测。

修法：远程接口对齐本地（返回 `(记忆, 分数)`，并兼容旧版服务端）。

#### P1-3 · 组件组合实验（不是单变量实验）✅ **已实现**（结果见 `data/combo_l9_real.html`）

**为什么**：MIT 的受控实验（44 张发票 × 4 种模型配置）给出一个反直觉结论：

> **能力最强、成本最高的模型配置，反而表现最差。**
> 结论不是"用便宜模型"，而是**按任务匹配模型 + 做组件组合测试**；
> 单独测试每个组件会得出错误结论，因为 Agent 的表现来自整条链路的配合。

**已实现**：

| 组件 | 实现 | 位置 |
|---|---|---|
| 实验设计（DOE） | L9 正交表 + 全因子，含正交性校验 | `eval/doe.py` |
| 主效应分析 | 各因子水平均值 + 极差 | `doe.main_effects()` |
| 成本-效果曲线 | 帕累托前沿（不是加权排名） | `doe.cost_effect_points()` |
| 多目标推荐 | 四个"最优"而非一个 | `doe.recommend()` |
| 空记忆实现 | Null Object 模式（对照组的"关记忆"） | `memory/null_store.py` |
| 强制档位 | `force_tier`（避免路由策略混淆因子） | `llm/client.py` |
| 运行器 + 报告 | HTML（Chart.js）+ JSON | `scripts/run_combo_experiment.py` |

**实验设计（3 因子 × 3 水平）**：

```
因子 1  模型档次      small(turbo) / medium(plus) / strong(max)
因子 2  记忆策略      关 / 只情景 / 情景+语义
因子 3  思考链        全开 / 按任务分档 / 全关

L9 正交 = 9 组（估主效应）　全因子 = 27 组（估交互）
```

**★ 本模块的方法论核心：为什么要正交设计**

3 因子 3 水平全跑是 27 次，L9 只要 9 次 —— 代价是**估不了交互效应**。

```
正交性：任意两因子的水平组合恰好出现一次
       → 所以"A 的不同水平"在 B 的每个水平下都被比较过
       → A 的主效应不会被 B 的分布失衡干扰
```

**而这个性质必须有测试守住**，因为：
**正交性被破坏时，算出来的主效应仍然是一个"看起来正常的数字"。**
这是最危险的一类 bug —— 实验设计错了，但结果看起来是对的。

（`tests/test_smoke.py` 的 `TestDOE` 里有一条测试逐对因子验证正交性。）

**★ 关于"交互效应"**（这是组合实验的真正价值）

```
假设单独测：
  强模型更好；开记忆更好
  那"强模型 + 开记忆"是不是最好？

**不一定。** 强模型可能已能从上下文推断答案，记忆的噪声反而干扰它；
而弱模型需要记忆补充信息，开记忆收益很大。
```

**两个单独看都更好的选项，组合起来可能更差（负交互）。**
这种效应只能通过"让因子同时变化"发现 —— 这就是"组合实验"而非
"多变量实验"的重点。

**★ 四个刻意的设计决定**

| 决定 | 理由 |
|---|---|
| **成本用两个代理并排**（token + 耗时） | ⚠️ 第一版只用 token，实验后发现它**区分不出组合**（见下方"度量问题"）。**单一成本代理会决定你能看到什么。** |
| **帕累托前沿**，不做加权求和排名 | "多花 1 块钱换 0.01 的 F1"没有客观答案；前沿给出所有理性选择 |
| **给四个"最优"而非一个** | 优化目标（省钱/效果/性价比）由业务决定，工具不该替业务做价值判断 |
| **`--from-json` 重新分析** | 换成本指标不必重跑实验（33 分钟 → 几秒） |

**★ 实验结果**（L9 正交，5 条 holdout，真实模型，33 分钟）

| # | 模型档次 | 记忆策略 | 思考链 | 组耗时 | F1 |
|---|---|---|---|---|---|
| 1 | small | off | all_on | 268s | 1.000 |
| 2 | small | episodic | policy | 243s | 1.000 |
| 3 | small | episodic_semantic | all_off | **74s** | 1.000 |
| 4 | medium | off | policy | 281s | 1.000 |
| 5 | medium | episodic | all_off | **82s** | 1.000 |
| 6 | medium | episodic_semantic | all_on | 282s | 1.000 |
| 7 | strong | off | all_off | **84s** | 1.000 |
| 8 | strong | episodic | all_on | 383s | 1.000 |
| 9 | strong | episodic_semantic | policy | 281s | 1.000 |

**各因子对「耗时（单条中位）」的主效应**：

| 因子 | 水平均值 | **极差** |
|---|---|---|
| **思考链** | all_on 60s / policy 54s / **all_off 16s** | **44s** ← 主导 |
| **模型档次** | **small 37s** / medium 41s / strong 53s | 16s |
| 记忆策略 | off 42s / episodic 46s / episodic_semantic 43s | 4s（≈噪声） |

**各因子对「F1」的主效应：全部 0.000**（9 组 F1 都是 1.000）

**★ 结论：最强的模型不是必要的**

```
效果：三个因子对 F1 都无影响（全部 1.000）
成本：思考链（44s）> 模型档次（16s）> 记忆策略（4s）
```

推荐 **`small / episodic_semantic / all_off`**（单条 15s，F1 1.000）。
最贵组合（`strong / episodic / all_on`，77s）**效果相同但慢 5.2 倍**。

**这正好印证 MIT 的结论**："能力最强、成本最高的配置反而表现最差"
—— 本任务里表现为"**效果相同但慢 5 倍**"。

**优化优先级因此明确：思考链 > 模型档次 > 记忆策略。**
换小模型省 1.4 倍，关思考链省 3.75 倍。

**★ 实验中暴露的度量问题（靠重新分析才发现）**

用 **token** 当成本时，各组合几乎区分不出来（10628 ~ 13446，差 1.27 倍），
而**耗时差了 5.2 倍**。

根因：`total_tokens = 输入 + 输出`，**输入占大头**（各组上下文相同），
**输出端的差异被淹没了** —— 而输出才是配置真正影响的地方。

> **成本代理的选择会决定你能看到什么。** 选错了会觉得"怎么配都一样"。

**★ 实验有效性检查**（防止"跑了但没测到东西"）

- `NullMemoryStore` 记录被调用次数 → 验证"关记忆"组确实生效（实测 18 次）
- 预置情景记忆 → 否则"开记忆"组没东西可召回，会得出"记忆没用"的错误结论
- 差异 < 0.1 的因子标注"不具统计意义" → 自由度不够就不该下结论

**★ 诚实的边界**

- 5 条样本 × 每组 1 遍 —— **筛选性**实验，不是确证性实验
- 9 组只有 8 个自由度，分给 3 个因子后留给误差的很少
- **"关思考链无损"受样本选择影响**：这 5 条含较简单的 issue（Docs / Build 类），
  而 `docs/05` F3 证明过**关思考链会让困难 case 失败** ——
  所以该结论**不能推广**，只能说"简单任务上关掉是安全的"
- 记忆策略几乎无影响，可能因为预置记忆只有 6 条 + 哈希伪向量

**★ 顺带发现的一个真实问题：接口漂移**

写 `NullMemoryStore` 时发现它缺了 `MemoryStore` 的 **6 个成员**
（`encoder`、`_embed_text` 和 P1-2 新增的 4 个语义层方法）。

更糟的是错误的**可误读性**：错误发生在"关记忆"组，
容易被读成"关掉记忆导致 Agent 不可用"——而真相是"空实现不完整"。

已加 `TestStoreInterfaceConsistency`：
**让"忘记同步"变成测试失败，而不是运行时 AttributeError。**

> 判断一个方法是"接口"还是"内部细节"，标准不是"有没有下划线"，
> 而是**有没有外部调用**（`_embed_text` 也以下划线开头但它被外部调用，
> 所以是接口；`conn` / `_row_to_mem` / `_lock_for` 是纯内部）。

#### P2-4 · 向量索引升级（IVF）✅ **已完成**

**为什么**：兑现"已知问题"里那条 —— 向量检索是全表扫描，上万条后是瓶颈。

**但动手后发现问题比记录的更严重**（详见下方）。

**已实现**：

| 组件 | 实现 | 位置 |
|---|---|---|
| IVF 索引 | 纯 Python（k-means 聚类 + 倒排表 + nprobe 搜索） | `memory/index.py` |
| 集成 | `MemoryStore.build_index()` / 两条检索路径 | `memory/store.py` |
| 评测 | 精度-速度权衡 + 加速比 + 保持率 | `scripts/bench_vector_index.py` |
| 索引健康度 | 簇大小不均衡度、空簇数（**静默失效的信号**） | `IndexStats` |

**验收结果**（`python scripts/bench_vector_index.py --n 5000`）：

```
规模        5000 条 × 256 维，nlist=70

暴力搜索    163.36 ms/次
IVF         22.21 ms/次   →  7.4x 加速，保持率 99%（nprobe=8）
SQL 候选池  2.00 ms/次    →  快，但保持率只有 1.0%
```

**nprobe 的精度-速度权衡**：

| nprobe | 延迟 | 加速比 | 保持率 |
|---|---|---|---|
| 1 | 11.6ms | 14.1x | 50.0% |
| 2 | 15.2ms | 10.8x | 80.0% |
| 4 | 18.3ms | 8.9x | 93.0% |
| **8** | **22.2ms** | **7.4x** | **99.0%** |
| 70（=nlist） | 171ms | 1.0x | 100%（精确） |

**★ 发现的更严重问题：候选池是按时间取的，不是按相关性**

`docs/06` 原本只记了"慢"。但去看 `recall()` 的实现会发现：

```sql
SELECT * FROM memories WHERE ... ORDER BY created_at DESC LIMIT ?
                                    ^^^^^^^^^^^^^^^^^^^^
                                    按时间排序取候选池
```

**所以记忆库一大，"旧但相关"的记忆根本进不了候选池** ——
连算相似度的机会都没有。

**实测印证**：SQL 候选池的保持率只有 **1.0%**（5000 条时），
几乎等于"没有召回到任何正确答案"。

```
SQL 候选池  保持率 1.0%     ← 按时间取候选
IVF 索引    保持率 99.0%    ← 按向量邻近取候选
```

**所以"向量索引"的价值有两层**：

```
快（7.4x）—— 这是文档里记的那层
召回质量更好（1.0% → 99%）—— 这才是关键，但文档里没记
```

> **慢是可见的（用户会抱怨）；漏召回是不可见的
> （你以为"没有相关记忆"，其实有）。**

**教训**：**"已知问题清单"不是终点，是线索。**
文档里写的是当时看到的那一面，真正动手修时会发现更深的层次。

**★ 顺带修掉的两个性能问题（都是实测发现的）**

| 问题 | 现象 | 修法 |
|---|---|---|
| k-means 全量训练 | 2000 条建索引要 **17.6 秒** | 改用**小采样**训练簇心（`nlist × 10`）→ **4.6 秒** |
| 迭代轮数过多 | 20 轮是纯浪费 | 降到 8 轮（k-means 通常 5~10 轮就收敛） |

**采样没生效那次**：第一版用 `nlist × 40 = 1760`，而总量才 2000 ——
**等于没采样**（17 秒没变）。教训：**采样量要看相对比例，不看绝对值。**

**★ 几个诚实的边界**

- **构建成本是纯 Python 的量级**（440 点 × 44 簇 × 8 轮 ≈ 4000 万次运算 ≈ 1.5 秒）。
  生产用 faiss（C++ + SIMD）同样规模在毫秒级。
  **本模块的价值是讲清原理和权衡，不是提供生产级性能。**
- **IVF 的增量能力是弱点**：新向量只能塞进最近的簇，但簇心不会更新 ——
  加多了簇心就偏了。生产里通常"攒一批后重建"。
- **N < 5000 时不必上索引**：全表扫描够快，而索引的构建成本和
  失效风险（增量导致簇心偏移）反而不划算。

**★ 索引健康度指标（防止静默失效）**

`IndexStats.imbalance`（最大簇 / 平均簇）> 3 说明**聚类退化** ——
此时查询命中巨簇就退化成全表扫描，**索引建了等于没建，而且不会报错**。

这是 k-means 类索引最典型的静默失效，所以把它放进了统计而不是日志。

**工作量**：约半天

#### P2-6 · PR 风险阈值标定（用真实分布）✅ **已完成**

**为什么**：`pr_review.py` 里的大改动阈值是 **500 行** —— 一个"看起来合理"的经验值。

但实测发现真实 PR 的改动量中位只有 **75 行**（已合并）/ **27 行**（未合并），
**所以 500 行这个阈值几乎从不触发** —— 一个 44 文件、+252 行的 PR 仍被判"低风险"。

**这是"阈值没有数据支撑"的第二次出现**（第一次是记忆召回阈值，P0-3 修过）。

**已实现**：

| 组件 | 实现 | 位置 |
|---|---|---|
| 标定脚本 | 分布统计 + 信号有效性检验 + 阈值扫描 | `scripts/calibrate_pr_threshold.py` |
| 未合并 PR 采集 | `--outcome unmerged`（被拒绝的样本） | `scripts/collect_prs.py` |
| 应用标定结果 | 默认阈值 500 → **100**（两处同步） | `pr_review.py` + `registry.py` |

**★ 标定方法：先定目标，再看分布**

阈值不该"取分布的某个分位数"，而应该**由目标决定**：

```
目标：让"高风险"这个标签有区分度 —— 也就是「值得人优先看的那一小部分」

阈值太低 → 全部判高风险 → 标签失去意义（人还是要全看）
阈值太高 → 从不触发     → 等于没有规则（但你会以为"没有高风险 PR"）
```

**推荐区间 10%~20%** —— 对应"人工优先看能承受"的量级
（一天 20 个 PR → 优先看 2~4 个）。脚本把它做成参数，因为不同团队的
review 能力不同。

**标定结果**（60 个真实 PR：30 已合并 + 30 未合并）：

| 阈值 | 高风险数 | 比例 | 已合并中 | 未合并中 |
|---|---|---|---|---|
| 10 | 54 | 90.0% | 26 | 28 |
| 50 | 26 | 43.3% | 16 | 10 |
| **100** | **12** | **20.0%** | **10** | **2** ← 标定值 |
| 150 | 8 | 13.3% | 6 | 2 |
| 200 | 7 | 11.7% | 5 | 2 |
| 300 | 4 | 6.7% | 3 | 1 |
| **500** | **3** | **5.0%** | 2 | 1 ← 原值，几乎不触发 |

**改动量分布（这就是"数据支撑"）**：

```
已合并 PR（n=30）  p25  20　p50  75　p75 139　p90 242　p95 644
未合并 PR（n=30）  p25  20　p50  27　p75  60　p90  93　p95 202
```

**★ 信号有效性检验：两组分布有差异，且方向符合预期**

已合并 p50 = 75，未合并 p50 = 27 —— **已合并的改动量更大**，
说明"改动量大"和"被拒绝"之间**没有正相关**。

**这个结果的含义需要精确表述**：

```
「改动量大」→ 值得被人优先看（工作量分配）   ← 仍然成立，阈值就是为这个
「改动量大」→ 更容易被拒绝（预测性）         ← 不成立
```

**这两个目标不该混为一谈**。本项目的阈值服务于前者（把人的注意力
导向复杂改动），**不宣称它能预测 PR 会不会被拒**。

**★ 一次有价值的"翻车"：样本量从 18 → 60 后结论变了**

第一次标定只采了 8 + 10 = **18 个样本**，推荐阈值是 **300**。
扩到 30 + 30 = **60 个**后，推荐值变成 **100** —— 差了三倍。

原因：18 个样本时，p90 落在 218；60 个样本时 p90 是 202，
但样本更分散（未合并的最大值 2097 被采到了），导致比例分布完全不同。

**教训**：
> **样本量会改变结论，而且改的是推荐值本身，不只是置信区间。**
> 要标定一个阈值，样本量至少要到"每档能看出趋势"的程度。
> 18 个样本得出的 300 和 60 个得出的 100，**前者完全是噪声**。

**★ 顺带修掉的一个数据丢失隐患**

`calibrate_pr_threshold.churn_of()` 优先用已存的 `additions`/`deletions` 字段，
**缺了就回退到从 diff 现算**。

为什么需要回退？因为数据是不同时间采集的，早期版本可能没有这些字段。
**直接 `KeyError` 会让那些样本被静默丢掉** —— 而丢样本会让统计失真，
且你不会知道丢了。

| 组件 | 实现 | 位置 |
|---|---|---|
| 五种污染类型 | 枚举 + 各自的检测难度说明 | `eval/poison.py` |
| 注入器 | **走正常写入路径**（不加特殊标记） | `PoisonInjector.inject()` |
| 暴露追踪 | 从 trace 的 `memory_recalled` 检出 | `detect_exposure()` |
| 派生追踪 | 记录"基于污染写下的新记忆" | `record_derived()` |
| 纠正机制 | 软纠正（归档 + 降置信度），保留追溯 | `mark_wrong()` / `correct_derived()` |
| 实验脚本 | 五阶段：基线 → 注入 → 测量 → 派生 → 纠正 | `scripts/run_poison_experiment.py` |

**验收结果**（`python scripts/run_poison_experiment.py --mock --limit 5`）：

```
✓ 有明确的注入方案
    —— 五种类型，各带检测难度说明（见下表）
✓ 能报出"纠正所需反馈次数"
    —— 平均 2.00 次（范围 2~2）
✓ 能定位记忆污染影响的历史判断范围
    —— 如 stale 类污染影响了 4 个判断（trace_id 可列）
```

**★ 五种污染类型（注入方案）**

| 类型 | 说明 | 检测难度 | 为什么危险 |
|---|---|---|---|
| `WRONG_RESOLUTION` | 处置写错 | 中 | 照错方法做，失败后可能归因到别处 |
| `WRONG_ROOT_CAUSE` | 根因写错 | 中 | 误导诊断方向，让人查错地方 |
| `WRONG_TAGS` | 标签打错 | **高** | **被错误召回** —— 内容看起来对，只是匹配错对象 |
| `STALE` | 曾经对、现在过时 | **最高** | 内容完全合理，**只有知道版本变更才能发现** |
| `OVER_GENERALIZED` | 个案当通则 | 高 | 单看每条都对，**组合起来是错的** |

**★ 注入方案的关键约束：每条错内容都必须"看起来完全合理"**

```
✗ 错误示范：注入"解决方法：rm -rf /"
   → 现实中没人会写这种记忆，人工一眼就能发现，测出来的"纠正次数"毫无意义

✓ 正确示范（WRONG_RESOLUTION）：
   症状：read_csv 读取大文件时内存暴涨 OOM
   错内容：调大 JVM 堆内存（-Xmx8g）即可缓解
   → 读起来像一条正常建议，但对 Python 场景是错的
```

**真实污染的特征是「内容正常，只是不对」。** 这是实验有效性的前提。

**★ 核心发现：纠正需要 2 次反馈，不是 1 次**

```
第 1 次反馈：标记原污染为错误
  ↓ 但污染已派生出新记忆（Agent 基于它写过"经验"）
  ↓ 派生记忆**独立于原污染存在**，继续误导
第 2 次反馈：清理派生记忆 → 才真正收敛
```

**实测：5 种污染全部需要 2 次反馈。**

**所以"纠正所需反馈次数"衡量的是污染的传染深度**，而不是"删一条记忆有多难"。
删除原污染只需 1 次；传染深度决定了还要几次。

> **这是"记忆系统"这个卖点自带的风险面** ——
> 一个没有记忆的 Agent **不会因为记忆而犯错**。有了记忆，
> 就出现了一类全新的失败模式：**错误在系统内部自我强化**。

**★ 一个有意思的实测观察**

`STALE` 类污染的暴露次数（4 次）明显高于其他类型（都是 0 次）。
推测原因：它的内容**更详细、更有说服力**（"iteritems 将在 2.0 移除但暂时可用"），
因此更容易和多个 issue 匹配上。

**含义：写得越"像样"的污染，暴露面越大。**
这和"假消息比真消息传播快"是同一个道理 —— 精致的内容更容易被采信。

**★ 软纠正而非物理删除**

纠正时**不删记忆**，而是标记 `archived` + 降置信度。理由：

**如果直接删除，就无法回答"这条错误记忆当初影响了哪些判断"** ——
而那正是这个实验要测的东西。

（与 P1-2 的 `pending_promotions` 同一个思路：
**删除是最差的状态表达方式，它丢掉了过程信息。**）

**★ 数据来源：trace 的可观测性**

"影响了哪些判断"这个信息来自 trace 的 `memory_recalled` / `memory_used` ——
**记忆六环节里已经记了，所以本实验不需要改任何生产代码**。

> **能被观测的系统才能被诊断。**
> 如果 trace 不记"用了哪些记忆"，这个实验根本做不了。

**★ 实验的诚实边界**

- **Mock 模式下 F1 数据不可用**（MockLLM 是规则版，对真实 issue 无效，
  基线 F1 就是 0）—— 但**结构性指标（暴露 / 派生 / 反馈次数）是可信的**，
  因为它们只依赖记忆检索和追踪逻辑，不依赖模型质量
- 当前用哈希伪向量，**召回不准**，可能低估真实暴露范围
- 派生记忆是**显式模拟**的（真实系统由记忆六环节产生）

**工作量**：约 1 天

**验收结果**（`python scripts/demo_a2a.py`）：

**服务拓扑**：

```
│  · A2AClient         │ ←───────────────── │  · A2AServer         │
│  · 读 Card 判能力     │   Task / Artifact  │  · AgentExecutor     │
└──────────┬───────────┘                    └──────────┬───────────┘
           │            共享记忆池 (HTTP)                 │

                              ▼
                 ┌─────────────────────────┐
                 │  MemoryService 进程      │
                 │  · SQLite + 向量检索     │
                 └─────────────────────────┘
```

**★ 一个必须在文档里说清的边界**

A2A 的设计原则明确包含「**不暴露内部状态、记忆、工具实现**」——
它针对的是**跨组织**场景（不同公司/厂商的 Agent），记忆必须隔离，那是信任边界。

本项目的"共享记忆"是**应用层扩展**，模拟的是**同一组织内**的两个 Agent：

```
协议层  完全遵守 A2A（Agent Card / Task 生命周期 / JSON-RPC）
记忆共享 应用层扩展，不在协议边界内
```

**面试追问"你到底遵守了 A2A 还是改了它"时，这个区分就是答案。**

**★ 实现范围的诚实说明**

```
✅ Agent Card 发现 / Task 生命周期 / JSON-RPC / Message-Part / Artifact
❌ 流式更新（SSE）      —— Card 里声明 streaming: false
❌ 推送通知（webhook）  —— Card 里声明 pushNotifications: false
❌ 鉴权                —— 真实缺口，所以默认只监听 127.0.0.1
❌ gRPC binding
```

**"声明了不支持"不等于"忘了做"** —— A2A 要求 Agent **如实声明能力**，
客户端会据此走轮询而不是尝试建流。
**诚实的降级优于虚假的能力声明。**

**★ 顺带修掉的一个严重并发 bug**

并发写入测试发现：8 线程 × 5 条 = 40 条，**只成功 26 条**（静默丢 14 条）。

根因：`sqlite3.connect(..., check_same_thread=False)` **只是关掉线程检查，
不代表线程安全** —— 多线程共用连接会互相踩游标，而且失败是**静默的**。

修法（SQLite 官方推荐）：**每线程一个独立连接（thread-local）+ `busy_timeout`**。

| | 修复前 | 修复后 |
|---|---|---|
| 写入成功 | 26/40（丢 14 条） | **40/40** |
| 耗时 | 80ms | 419ms |

**"快"如果是靠丢数据换来的，那不叫快。**

> **这类 bug 单线程测试永远发现不了，而且失败不报错。**
> 所以"并发写入测试"是共享存储的**必测项**，不是可选项 ——
> 如果没有 P2-2，这个 bug 会一直躺在代码里。

#### P2-3 · CodeAgent 方向延伸（读 PR diff 做初审）✅ **已完成**

**为什么**：编码 Agent 是国内数据最硬、招人最多的场景。
加了这一块，简历上就有了 CodeAgent 经历。

**已实现**：

| 组件 | 实现 | 位置 |
|---|---|---|
| diff 解析 | 自己解析 unified diff（不依赖 git 命令） | `tools/pr_review.py` |
| **敏感文件表** | 6 大类（依赖 / CI / 构建 / 安全 / 核心结构 / 序列化） | `SENSITIVE_PATTERNS` |
| 缺测试判断 | 改了源码但没改测试 → 提示 | `review_pr()` |
| 风险分级 | 任一命中即升级（不做加权求和） | 同上 |
| 工具注册 | `review_pr_diff`（支持 `pr_id` 和 `diff` 两种输入） | `tools/registry.py` |
| 演示 | 三个典型 PR 覆盖低/中/高风险 | `scripts/demo_pr_review.py` |

**验收结果**（`python scripts/demo_pr_review.py`）：

```
✓ 加了一个工具读 PR diff    —— review_pr_diff（工具总数 6 → 7）
✓ 输出含改动范围 / 是否缺测试 / 是否动敏感文件
✓ 不改架构                —— 只多注册一个工具 + 一个独立模块
```

**演示结果**（三个典型 PR）：

| PR | 改动 | 风险 | 缺测试 | 敏感文件 |
|---|---|---|---|---|
| PR-1001 | 文档 + 测试 | **低** | 否 | 0 |
| PR-1002 | 两个核心源码文件 | **中** | **是** | 0 |
| PR-1003 | 依赖 + CI + pickle + token 校验 | **高** | **是** | **4 处** |

PR-1003 的 4 处敏感文件全部被正确识别：
`pyproject.toml`（依赖声明）、`pandas/io/pickle.py`（序列化与求值）、
`.github/workflows/ci.yml`（CI 配置）、`pandas/_libs/security_utils.py`（安全相关）。

**★ 这个工具的全部价值在两张表，不在代码**

```
代码：解析 diff + 正则匹配 + 计增删行数  → 简单
难点：知道什么该担心                      → 领域知识
```

| 表 | 内容 |
|---|---|
| `SENSITIVE_PATTERNS` | 依赖声明 / CI 配置 / 构建脚本 / 安全相关 / 核心数据结构 / 序列化与求值 |
| 改动范围与测试覆盖的对应 | 改了源码没改测试 → 缺测试；纯文档 → 不需要 |

**换个语言/项目，表要重写；但"用一张表把资深工程师的直觉固化下来"
这个方法是不变的。**

**★ 两个刻意的设计决定**

| 决定 | 理由 |
|---|---|
| **风险分级用"任一命中即升级"**，不做加权求和 | 风险**不可互相抵消**：改 1 行依赖声明 vs 改 500 行文档，前者更该被人看。加权平均会把这种信号抹平。**风险筛查里取最大值比取平均安全。** |
| **自己解析 diff**，不调 git 命令 | 输入可能来自任意地方（粘贴、API、文件），不一定有本地仓库。**让工具只依赖输入数据，不依赖运行环境** —— 这也是它能进沙箱的前提。 |

**★ 必须讲清的能力边界**

```
能回答：这个改动「看起来」危不危险（风险筛查）
不能答：这个改动「实际上」对不对（正确性审查）
```

工具**不读代码内容**，只做结构筛查。这条限制**写在工具描述和报告里**
（`to_dict()` 的"说明"字段 + `format_review()` 的末尾警告）。

**为什么必须写明？** 否则会被误用成"工具说低风险 = 这个 PR 没问题" ——
那是危险的理解。**风险筛查的价值在于把人的注意力分配到最需要的地方，
不是替代人。** 演示里 PR-1003 被判"高风险"不是因为代码写错了，
而是因为它**改的地方值得多看两眼**。

**★ 为什么这个方向值得做**

编码 Agent 是招聘数据最硬、岗位最多的场景。而这个工具的定位是
**CodeAgent 最现实的落地方式**：

> 不是"让 AI 写代码"，而是"**把 review 的第一遍粗筛自动化**" ——
> 人只看得过 AI 筛出来的高风险改动。

**★ 顺带修正了一条测试的设计缺陷**

原有一条测试断言"工具必须恰好 6 个"（源自 Gartner 的"50+ 工具是失败模式"）。
P2-3 加了工具后它失败了 —— **但这次失败不是 bug，是测试写得太死。**

```python
✗ self.assertEqual(len(names), 6)      # 快照式断言，每加工具都要改
✓ self.assertLessEqual(len(names), 10) # 约束式断言，表达"要克制"的真实意图
```

> **数量类断言应该表达"约束"而不是"快照"。**
> 快照式断言改多了就麻木了，反而失去了提醒作用。
> （真加到第 11 个工具时，应该**停下来重新想架构**，而不是顺手改这个数字。）

**工作量**：约半天（原估"成本很低"，实测确实低）

### 3.1 已解决（曾经的真实问题，保留记录以便追溯）

| 问题 | 曾经的后果 | 怎么解决的 |
|---|---|---|
| **哈希伪向量判别力不足** | duplicate F1 天花板 0.5 | ✅ 接语义 embedding（P0-2，1024 维） |
| **合成数据指标虚高** | 数字不能写进简历 | ✅ 换真实数据（P0-1，pandas 79 条 holdout） |
| **Mock 的记忆使用是规则分支** | warm 组优势不明显 | ✅ 接真实模型（P0-2） |
| **阈值没有数据支撑** | 阈值是个"经验值" | ✅ 用 `sweep_threshold.py` 数据标定（P0-3） |
| **gold 标注口径错误** | 模型答对被判 0 分（F1 虚低） | ✅ 区分"无标签"和"被过滤掉"，加标题前缀推断 |

| **SQLite 共享连接非线程安全** | 同上 | ✅ 同上 |

### 3.2 设计取舍（不是缺陷，是刻意的选择，且有理由）

| 取舍 | 为什么这么选 |
|---|---|
| **语义层无自动触发** | `scan()` 要遍历全表（O(n)），而 SOP 提炼是低频动作。挂在主循环是浪费 —— **正确的入口是 cron / 人工**（见 P1-2 说明） |
| **沙箱是进程内轻量实现** | 不是真隔离。**生产应换容器** —— 但对本项目，"沙箱分级 + 幂等 + 可回滚"这三个机制才是要演示的重点 |
| **A2A / 记忆服务无鉴权** | **真实缺口**，所以两者默认只监听 `127.0.0.1`（不是 `0.0.0.0`）。**默认安全 > 默认方便** —— 要对外暴露必须显式声明并自行加鉴权层 |
| **长程压测未分离"轮数"和"长度"** | 当前两者同时增长，所以说不清漂移的根因是哪个。**但这是个"下一步"而不是"缺陷"** —— 见第四节延伸 1 |

### 3.3 生产补课项（知道该做，有明确路径，但本项目不做）

| 项 | 影响 | 路径 |
|---|---|---|
| **向量检索是全表扫描** | 上万条后是瓶颈 | 换 HNSW / IVF（faiss、milvus、pgvector）。**这是最先会遇到的瓶颈** |
| **SQLite 单写锁** | 高并发下写入排队 | 换 Postgres + 连接池（实测：并发写下耗时 80ms → 419ms） |
| **服务鉴权** | 任何人可对 A2A 服务派活 | mTLS / token |
| **每路由延迟直方图** | 现在只有请求日志，够调试不够运维 | OpenTelemetry + Prometheus |
| **完整优雅关闭** | 现在是"停止 accept" | 停止接收新请求 → 等在途完成 → 关数据库 |

**这张表的意义**：它证明我**知道一个生产级系统还需要什么** ——
而不是"以为自己做完了"。

### 长程一致性压测已完成，但还有两个延伸方向

基础版本做完了（`scripts/run_longhorizon.py`），如果想做更严谨的版本：

**延伸 1 · 分离"轮数"和"长度"两个变量**

当前实验里，轮数和 token 长度是**同时增长**的。
所以无法回答："到底是轮数多了导致漂移，还是上下文长了导致的？"

要分离它们，需要构造两个独立的实验组：
- 组 A：轮数多但每轮很短（总 token 少）
- 组 B：轮数少但每轮很长（总 token 多）

**这个区分有实际意义**：如果漂移主要由长度导致，那解法是"压缩"；
如果主要由轮数导致，那解法是"减少往返次数"（比如批量调用工具）。
两种解法完全不同，搞错方向就会白做优化。

**延伸 2 · 用真实模型测漂移率**

当前用的是规则版 Mock（全有全无）。真实模型应该测出**部分遵守**的模式：

```
真实模型可能的观察结果：
  第 10 轮：遵守 3/3 条约束
  第 30 轮：遵守 3/3 条
  第 50 轮：遵守 2/3 条        ← 开始漏
  第 80 轮：遵守 1/3 条
```

如果真实模型也能测出这种渐变，那状态卡的价值就更明确了
（它把"渐变"变成"稳定"）。

**工作量**：延伸 1 约 3 天，延伸 2 取决于 API 预算。
