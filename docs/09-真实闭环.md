# 09 · 最小真实闭环（前瞻验证 + 持续运行）

> 把 Agent 从"离线评测的项目"变成"**对真实仓库持续跑、并回头对账**的系统"。
>
> 这是"作品"和"系统"的分界线，也直接消灭面试里最容易被戳的那个弱点。

---

## 一、设计思路

### 1.1 要解决的那个弱点

前面所有评测都有一个共同的软肋：

```
run_eval.py  → 在**已关闭**的历史 issue 上算 F1
              gold 标签是**已经发生的事实**
              → 这是在**解释过去**
```

面试官一句话就能戳穿：

> **"你的指标是算在历史数据上的 —— 怎么知道线上真的有用？"**

要回答这个问题，唯一的方法是**让预测发生在事实之前**。

### 1.2 双轨设计（关键决策）

原方案的形态是"每天抓 20 条，跑两周" —— 但它有个致命问题：**两周内没有产出**。

风险太大（搭 1-2 天 + 干等 14 天），所以拆成两轨：

| 轨道 | 做法 | 产出时间 | 作用 |
|---|---|---|---|
| **A · 历史回溯** | 抓 2~10 周前创建、**现在已有标签**的 issue，用创建时信息预测，对照后来真实打上的标签 | **当天** | 立刻拿到数字 |
| **B · 真前瞻** | 每天增量抓新 issue → 预测入库 → 几天后回填真实标签 | 持续积累 | 证明"这是个在跑的系统" |

**两轨用同一份标签映射和同一套预测逻辑** —— 所以轨道 A 的结论对轨道 B 也适用。

> **A 是"用过去的数据模拟前瞻"（准前瞻），B 是真正的预测未来。**
> A 立刻给结论，B 给"系统"的证明。只做 B 的话，半个月没产出，风险太大。

### 1.3 ★ 信息隔离：这是实验有效性的前提

**Agent 只拿到标题 + 正文**（这两个字段在 issue 创建时就有了）。**刻意不给**：

| 不给的字段 | 为什么 |
|---|---|
| `labels` | 那是要预测的目标 —— 给了就是作弊 |
| `gold_labels` | 同上 |
| `state`（open/closed） | 最终状态是"后来的结果"，会泄露信息 |
| 评论、后续讨论 | 那些是**维护者判断之后**才出现的 |

**如果不做这个隔离，评测会虚高，而且虚高得毫无意义** ——
因为真实场景里，Agent 面对的确实只有标题和正文。

实现上就是 `to_issue()` 里显式清空这几个字段，并在注释里写明原因。

## 二、实现

### 2.1 三个脚本

| 脚本 | 职责 |
|---|---|
| `scripts/collect_prospective.py` | **轨道 A 采集**：抓 issue + 查 timeline 定位首个类型标签 |
| `scripts/eval_prospective.py` | **轨道 A 评测**：跑预测 + 对账 + 出报告 |
| `scripts/daily_triage.py` | **轨道 B**：每日循环（抓新 + 预测 + 回填），有状态 |
| `.github/workflows/daily-triage.yml` | 定时触发（每天一次） |

### 2.2 轨道 A 的关键：必须查 timeline

**GitHub 的 issue API 只给"当前有哪些标签"，不给"标签是什么时候打的"。**

而时间正是这个实验的核心：

```
标签在创建后 1 天打的  → 维护者当时就是基于创建时的信息判断的 ✓ 可用
标签在 3 个月后打的    → 那时已有大量讨论，标签反映的是讨论后的结论 ✗ 不可用
```

所以必须走 `/issues/{n}/timeline`，它返回 `labeled` 事件及时间戳。

**没有这一步，就只能拿"当前标签"当 gold** —— 那会**高估** Agent 的能力。

### 2.3 轨道 B 的关键：它是有状态的

之前每个脚本都是"跑一次、出报告、结束" —— 那是**脚本**。
轨道 B 要长期跑，所以必须解决四个"脚本不需要管"的问题：

| 问题 | 做法 |
|---|---|
| **幂等** | `issue_id` 作主键，已存在的直接跳过 |
| **增量** | 每天只抓"最近 N 天新开的"，靠幂等去重 |
| **对账** | 预测后等几天，回头查真实标签回填 |
| **可恢复** | 全程事务写入；Actions 用 `concurrency` 防重入 |

**状态用 SQLite 而不是 JSON 文件**：

```
① 幂等   要"按主键查存在性" —— 文件要全量加载再判断，O(n)
② 并发   Actions 可能重入，需要事务 —— 文件做不到
③ 查询   "还有多少没对账" —— 文件要遍历
④ 跨周累积  每天重写全量文件，中间崩溃就丢历史
```

**"持久化状态该用数据库"是不需要犹豫的判断。**

### 2.4 状态库的两张表

```sql
predictions(
    issue_id      主键（幂等的依据）
    predicted_at  预测时间
    predicted     预测出的粗标签（JSON）
    predicted_raw 模型原始输出（留着排查用）  ← ★ 见下方说明
    gold          ★ 对账结果（NULL = 还没对账）
    lag_days      创建 → 首个标签的间隔
)

runs(  -- 每次运行留一行
    run_at, mode, n_new, n_reconciled
)
```

**两个设计点值得说明**：

① **`predicted_raw` 和 `predicted` 分开存**
原始输出是 `['bug', 'regression', 'needs-triage']`，
归一化后是 `['Bug', 'Regression']`。
**两个都留** —— 因为归一化规则以后可能改，留原始数据才能重算。
（这是 `docs/05` F6 那条教训的实践：**存逐条原始数据，支持未来重算**。）

② **`gold = NULL` 表示"还没对账"，不表示"失败"**
不能把"维护者还没打标签"写成"未知"或"失败"——
那样"尚未分诊"和"分诊了但没类型标签"就混在一起了，而它们的含义完全不同。

## 三、方法论的三个关键点

### 3.1 标签粒度对齐（最容易错的地方）

**踩过的坑**：第一版直接拿 `predicted_labels` 和 gold 比，**结果全错**。

```
Agent 输出：['bug/crash']      ← 细分格式
pandas gold：['Bug']           ← 粗标签
→ 字符串不相等 → 判为错误
```

**根因是两个粒度层级不同**：

```
主项目评测    两边都是细分 → Metrics.normalize_label 取"有区分度的那一段"
              'bug/crash' → 'crash'，'bug/segfault' → 'segfault'

前瞻验证      预测是细分、gold 是粗 → **要归到粗的那一端**
              'bug/crash' → 'bug' → 'Bug'
```

**如果照搬主项目的 `normalize_label`**，`bug/crash` 会变成 `crash`，
而 gold 是 `bug` —— **依然对不上，而且错得很隐蔽**（字母都对，只是不是同一个词）。

> **对齐标签之前，先确认两边的粒度。**

实现见 `eval_prospective.py` 的 `to_coarse()`：
按第一段（而不是最后一段）查映射表，归不到就返回 `None`（= 未给出预测）。

**`None` 和"预测错误"必须分开统计**：

```
"预测成别的类型"   = 判断错误      → 能力问题
"没给出类型判断"   = 没回答        → 可以通过改提示词解决
```

### 3.2 "无类型标签"是信息，不是噪声

采集结果里有一栏"无类型标签"：

```
候选 issue 90 → 有效样本 61，无类型标签 28（31%）
```

**这不是数据质量问题** —— 它说明**不是所有 issue 都会被分诊**。

**如果只报"有效率"，就会掩盖这个事实。** 所以报告里必须留着这一栏。

（这类"负面数字"在项目里出现过很多次：
`docs/07` 里"缺测试率 0%"、"关思考链无损只在简单样本上成立" ——
**主动暴露对自己不利的数字，比只报好看的数字更能建立可信度。**）

### 3.3 对账要等几天（这个值来自实测）

`daily_triage.py` 的 `--min-age-days 3` 不是拍脑袋 ——
它来自采集阶段的实测数据：

```
分诊延迟（创建 → 首个类型标签）
  中位 0.0 天　最快 0.0 天　最慢 7.2 天
```

**中位数就是最小观测窗口。** pandas 的 triage 很快（有 bot + 活跃维护者），
所以 3 天已经足够宽松。

**这个数字决定"真前瞻"实验要等多久才能对账** ——
如果不测这个，可能会以为要等两周，白白拉长周期。

✗ #67983  CI: setup-pixi action's environment input description ... → Build

**把标题前缀和真实标签交叉统计**，规律一目了然：

```
前缀 BUG   → Bug          33 条   基本一致
前缀 ENH   → Enhancement   8 条   一致
前缀 DOC   → Docs          8 条   一致
前缀 PERF  → Performance   3 条   一致
前缀 CI    → Build         3 条   ← ★ Agent 不知道 CI = Build
前缀 BLD   → Build         1 条   ← ★ 同样不认识
前缀 BUG   → Build         1 条   ← ★ 前缀误导（BUG: 不代表类型是 Bug）
前缀 API   → Bug           1 条   ← ★ 同上
```

**这不是"能力不足"，是"领域知识缺失"** —— 具体两处：

① **pandas 的 `Build` 标签涵盖 CI / 构建 / 打包**，但提示词里
   `Build` 的描述太笼统，Agent 不知道"CI 相关的问题算 Build"

② **`CI:` 和 `BLD:` 这两个前缀根本不在 Agent 的标签词典里**
   （它认识 `BUG:` / `ENH:` / `DOC:`，因为那些前缀和标签同名）

**关键推论：这是可以修的** —— 把"CI/BLD 前缀 → Build"写进提示词即可。
**修完再跑一遍，就是一次完整的"发现问题 → 定位 → 修复 → 验证"闭环。**

### 4.1.1 ★★ 一个比数字更值钱的方法学发现

**前瞻验证暴露了离线评测的一个系统性偏差：gold 是怎么来的。**

对比一下两边的 gold：

```
离线评测（prepare_dataset.py）   从**标题前缀**推：
                                 BUG: → Bug，DOC: → Docs

前瞻验证（本实验）               用**维护者真实打的标签**：
                                 CI:  → Build
                                 BUG: → Build（也可能）
```

**所以离线评测的 gold 有系统性误差**：

> 用"标题前缀"当 gold，会漏掉"维护者真实判断"的差异。
>
> `BUG:` 前缀只表示"**这是一个缺陷报告**"（中性前缀），
> 不表示"**类型标签是 Bug**" ——
> 一个 `BUG:` 开头的 issue 如果涉及构建系统，维护者会打 `Build`。

**这个偏差在离线评测里永远发现不了** —— 因为离线评测的 gold 本身就是那么构造的，
**它无法质疑自己的 gold**。

**只有前瞻验证（用外部真实标签对照）才能暴露它。**

> **这正是"用创建时信息预测、对照维护者真实标签"这个设计的价值所在** ——
> 它不只是"更硬的证据"，它还是一个**检验评测体系本身的工具**。

**行动项**：`prepare_dataset.py` 的 gold 构造里，
`BUG:` 前缀的样本要允许后续被真实标签覆盖（或至少标记出来）。

### 4.1.2 辅助观察：维护者的分诊动作

```
有状态标签的样本 16/61
  Needs Triage        8
  Needs Discussion    7
  Duplicate Report    1
```

**这代表维护者的另一种判断**："要不要退回给作者" / "需不需要讨论"。

**我们的 Agent 目前不预测这些** —— 这是一个诚实的边界：
"打什么类型标签"和"要不要退回"是两个不同的判断。

（如果要做，思路和 `docs/06` 的 P2-1 一样：
把"维护者退回"当成一个可对照的信号来验证。）

### 4.1.3 ★★ 完整闭环：发现问题 → 定位 → 修复 → 验证

**这是本实验最有说服力的部分** —— 它证明"前瞻验证"不只是产出数字，
而是**能驱动系统改进的**。

#### ① 发现问题

前瞻验证的分层命中率里，`Build` 类只有 **20%**（1/5），而其他类都是 100%。

**4 个错误全部是"该打 Build 却打了别的"**：

```
✗ #67985  BUG: validate_test_dependencies.py is blind to pixi ... → Build
✗ #67983  CI: setup-pixi action's environment input description ... → Build
✗ #67982  CI: pixi-version is pinned in three places and depen ...  → Build
✗ #66735  BLD: build failures of xsimd code on linux               → Build
```

#### ② 定位根因（挖了三层）

**第一层（表面）**：提示词里把 `Build` 放在了**"细分标签"**里，
还标注"**仅当非常明确时才用**"。

```
· 主标签（强烈优先）：Bug / Docs / Enhancement / Performance / Regression
· 细分标签（仅当非常明确时才用）：... Testing / Build / CI 等
```

而 pandas 的真实体系里 **`Build` 和 `Bug` 是平级的类型标签**。

→ **根因是"标签体系的层级划分没跟真实仓库对齐"** —— 自己拍一个层级，
会让 Agent 系统性地漏掉某一类。

**第二层（更深，改完第一层才发现）**：改完提示词后重跑，**命中率毫无变化**。
顺着调用链查，发现：

```
triage(prompt_variant="default")   ← 默认值
run_eval.py 显式传 "tuned"          ← 离线评测用 tuned
eval_prospective.py 没传            ← 前瞻验证用了 default
```

**两套评测用的根本不是同一个提示词** —— 而我改的是 `tuned`（没被前瞻验证用到）。

> **这个不一致在数字上完全看不出来**（两边都给出"合理"的结果）。
> 只有"改了什么却没变化"才会暴露它。
>
> 教训同 `docs/05` 的 D2：**两条路径要逐字对齐配置**。
> "我以为是一致的"是最危险的状态。

**第三层（评测侧自己的 bug）**：`to_coarse()` 的映射表里少了 `ci` / `bld`。
模型输出的是 `['CI', 'config', ...]`，归一化后变空 ——
**被算作"未给出预测"，而真相是"给了但归一化失败"**。
**这是评测侧的 bug，不是模型的错。**

#### ③ 修复（四处）

| # | 改什么 | 位置 |
|---|---|---|
| ① | 把 `Build` 从"细分标签"移到**主标签**，并写明"涵盖 CI/BLD 前缀" | `config.LABEL_GUIDE` |
| ② | 加"规则 2.5：小心标题前缀的陷阱"——说明 `BUG:` 只表示"这是个缺陷报告" | `react.SYSTEM_PROMPT_TUNED` |
| ③ | `to_coarse()` 补 `ci` / `bld` → `Build` 的映射 | `eval_prospective.py` |
| ④ | 评测脚本**显式传** `prompt_variant="tuned"`（对齐离线评测） | `eval_prospective.py` + `daily_triage.py` |

**② 的说明尤其重要** —— 它来自真实数据：

```
· `BUG:` 只表示"这是一个缺陷报告"，不表示"类型是 Bug"。
  如果这个缺陷涉及构建 / CI / 打包 / 依赖，应该打 `Build`。
· `CI:` / `BLD:` 前缀 → `Build`
```

#### ④ 验证

**全量对比**（61 条，`python scripts/compare_prospective.py`）：

| | 修复前（v1） | 修复后（v2） | 变化 |
|---|---|---|---|
| **总体命中率** | 93.4%（57/61） | **100.0%（61/61）** | **+4 条** |
| 修好（✗→✓） | — | 4 条 | |
| **变差（✓→✗）** | — | **0 条** | |
| 一直正确 | — | 57 条 | |

**逐条对比（修复生效的直接证据）**：

```
issue     修复前预测              修复后预测         真实
#66735    []                    ['Build']        Build
#67982    []                    ['Build']        Build
#67983    ['Docs', 'Bug']       ['Build']        Build
#67985    ['Bug']               ['Build']        Build
```

**按标签分层（检查有没有"修好 A 弄坏 B"）**：

| 标签 | 样本 | 修复前 | 修复后 | 变化 |
|---|---|---|---|---|
| Bug | 35 | 100% | 100% | +0% |
| Docs | 10 | 100% | 100% | +0% |
| Enhancement | 8 | 100% | 100% | +0% |
| **Build** | **5** | **20%** | **100%** | **+80%** |
| Performance | 3 | 100% | 100% | +0% |

**没有**任何类别变差 —— 修复是"净改进"（**在「命中」口径内**）。

> ⚠️ **但这个结论只在命中口径内成立 —— F1 口径下有 1 条变差。**
>
> `#68433`（`ENH: move the postgresql extra from psycopg2 to psycopg 3`）：
>
> ```
>        预测                         F1       hit
> v1     ['Enhancement']              1.000    True
> v2     ['Enhancement', 'Build']     0.667    True    ← 多打了一个 Build
> ```
>
> **`hit` 两次都是 True**（Top-1 都是 Enhancement），所以上面那张「逐条变化」
> 表里它落在"一直正确"里，`broke` 计数为 **0**。而它的 **F1 从 1.000 掉到 0.667**。
>
> #### 定性：**真实副作用，不是评测假象**
>
> 两版的 `predicted_raw`（粗化**之前**的原始输出）原文对比：
>
> ```
> v1  raw = ['enhancement', 'dependencies', 'postgresql']
> v2  raw = ['Enhancement', 'Build']                        ← Build 是 v2 新增的
> ```
>
> v1 的原始输出里**根本没有 build 类标签** —— 所以这**不是**
> "映射缺失被修好之后显形"（那种情况两版 raw 会相同，只是 v1 被截断）。
> 是**模型在 v2 里真的多输出了一个 `Build`**：
> 把 Build 提为主标签、并加「前缀陷阱」说明之后，
> 对这个 Enhancement 类 issue 产生的**真实副作用**。
>
> 旁证：v2 的整体行为确实变了 —— `steps` 中位数 3 → 1（14/61 条为 0 步），
> `tokens` 也大幅下降。提示词是**全局干预**，行为变化是全面的，
> 这条过度标注正是其中一处代价。
>
> #### 两个口径各自成立，不矛盾
>
> | 口径 | 变差数 | 结论 |
> |---|---|---|
> | 命中（Top-1 对不对） | **0 条** | "净改进"在其口径内**仍然成立** |
> | F1（标签集合匹配度） | **1 条** | 净收益 +5.0/61，含这一条 −0.333 |
>
> **为什么必须并排报**：hit 只问"Top-1 对不对"，
> 所以**"多打了标签"型回归它看不见** —— 一条样本只要 Top-1 仍对，
> 哪怕多打三个标签，hit 依然是 True。
> 只报命中口径的 0 条会让人以为"修复零副作用"。
>
> **换一个合理口径就露出来的东西，说明它一直在那里。**
> （这正是 `docs/04` 里"多口径"那条纪律的又一例证；
> 已在 `compare_prospective.py` 补上 F1 口径的变差统计，
> 两个口径的变差数现在会一起打印。）

> **为什么一定要逐类看**：提示词是**全局干预**，可能修好 A 类的同时弄坏 B 类。
> 只报"总体从 93% 到 100%"是不负责任的 ——
> 如果某个类从 100% 掉到 80%，总体可能还是提升的，**但问题被掩盖了**。
>
> （同构于 `docs/05` 的"多口径"那条：单一汇总数字会掩盖结构。）

#### ★ 关于"100% 命中率"的诚实说明

**按 `docs/05` 的第 1 条原则（"完美等于可疑"），100% 本身就是可疑信号** ——
应该先怀疑"样本是不是太简单"，而不是先庆祝。

**这里的原因确实是样本偏简单**：

```
这 61 条是"**已被维护者快速分诊**"的 issue
  → 分诊延迟中位 0 天（说明问题清晰、易于归类）
  → 天然偏简单

而那 31%（28 条）一直没被打标签的 issue
  → **根本不在样本里**
  → 而它们才可能是"真正难分诊"的那部分
```

**所以"100%"应该读作**：

> **"在 61 条**清晰、被快速分诊的** issue 上，命中率 100%。"**
>
> 不是"所有 issue 都能 100%"。

**要得到更真实的数字，下一步应该**：
把"30 天以上仍未被打标签"的 issue 也纳入评测 ——
它们的 gold 是"**维护者也不知道该归哪类**"，那才是真正的硬骨头。

#### ★ 这个闭环的价值

它把项目的性质从"**一个做出来的东西**"变成了"**一个会自我改进的东西**"：

```
普通项目   发现问题 → 修 → 说"修好了"
本项目     发现问题 → 定位（挖了三层）→ 修 → 用数据验证 → 且检查副作用
```

**而且三层根因里有**两层**是"改完才发现"的** ——
第一层的修复（改标签分级）看起来就够了，但它是**无效的**（因为用错了提示词版本）。
**如果没有"改完必须验证"这一步，会误以为已经修好了。**

> **这正是"验证"这一步不可省的原因**：
> 不是验证"改对了没"，而是验证"改动真的生效了吗"。
> （同 `docs/05` 的第 7 条原则。）

## 五、踩到的四个坑（都值得记）

### 坑 1：翻页上限拍得太小

**现象**：翻满 10 页（500 条）**一条候选都没抓到**。

**根因**：pandas 每天新增 issue + PR 约 30~50 条（issues API 会把 PR 一起返回），
所以 500 条只覆盖了最近**约 12 天** —— 还没走到"14 天前"这条线。

**教训**：

> **按时间倒序 + 过滤时间窗口时，"翻几页够用"取决于数据产生速率，不能拍数字。**
> 估算法：`窗口天数 × 每天新增量 ÷ 每页条数 = 最小页数`。

### 坑 2：`since`/`until` 命名歧义导致判断整个反了

**现象**：修好翻页后仍然抓不到 —— 因为过滤条件反了。

**根因**：`t_since = now - 28天`（更早）而 `t_until = now - 14天`（更晚），
所以 `t_since < t_until`，**和我脑子里"since < until"的直觉相反**。

**教训**：

> **变量的命名要防止歧义。** 改成语义明确的 `earliest` / `latest` 后，
> 时间轴上的位置一眼可见，不可能再搞反。

### 坑 3：标签粒度不匹配（见 3.1）

**这个坑最值得记** —— 因为它**错了但不报错**，只是数字难看。
而且照搬主项目的归一化函数会**依然错**，因为两个场景的粒度关系不同。

### 坑 4：Mock 在真实数据上不可用

**现象**：用 Mock 跑轨道 A，**大部分预测是空的**（`needs-triage` → 归一化后为空）。

**根因**：Mock 是规则版 —— 它的"快速路径"依赖**记忆命中**，
记忆没命中就判断"信息不足"。而真实数据里，标题正文的表述方式
和 Mock 的规则匹配不上。

**这不是 bug** —— 它再次印证了那条老教训：

> **Mock 能验机制，不能验效果。**
> 所以轨道 A 的正式数据必须用真实模型跑（61 条 × 64 秒 ≈ 65 分钟）。

## 六、这个实验在面试里怎么用

**30 秒版本**：

> "我的评测分两层：离线用历史 holdout 算 F1，
> 另外还有一套**前瞻验证** —— 拿 issue 创建时的信息预测，
> 对照维护者后来真实打上的标签。
>
> 两者证据等级不同：前者是**解释过去**，后者才是**预测未来**。
>
> 而且我把前瞻验证做成了**持续运行的系统**：每天增量抓新 issue、
> 预测入库、几天后回填真实标签对账。状态用 SQLite 管理，
> 挂在 GitHub Actions 上每天跑 —— 是'系统'不是'脚本'。
>
> 做的时候踩到最深的坑是**标签粒度**：Agent 输出的是 `bug/crash`
> 这种细分格式，而仓库的标签是 `Bug` 这样的粗标签。
> 对齐粒度这件事，**错了不会报错，只会让你的数字难看**。"

**为什么这个回答强**：

1. **主动区分了"解释过去"和"预测未来"** —— 这个区分本身就说明你懂评测
2. **有"系统"而不只是"脚本"** —— 状态管理、增量、对账、定时
3. **有真实的踩坑**（标签粒度）—— 不是背的
4. **主动暴露负面数字**（31% 无标签）—— 建立可信度
