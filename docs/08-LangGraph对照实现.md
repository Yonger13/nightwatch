# 08 · LangGraph 对照实现

> 用 LangGraph 重写 Nightwatch 的一条核心链路，与手写版做**逐项对照**。
>
> **目的不是"改用框架"** —— 主项目依然零依赖。目的是：
> 把"手写 vs 框架"这件事从**观点**变成**实测**。

---

## 一、设计思路

### 1.1 为什么要做这个对照

Nightwatch 的核心链路全是手写的（ReAct 循环、可靠性、记忆、上下文预算）。
这个选择有明确理由（见 `requirements.txt`），但它有个**明显的风险**：

> **"我没用框架"和"我不会用框架"从外面看是一样的。**

面试官没法区分。而这两者的差别很大：

```
判断力驱动的不用框架  →  加分（说明你知道框架替你做了什么）
能力不足的不敢用框架  →  减分
```

**要证明是前者，唯一的方法是"两个都做过，并且能讲出差异"。**

所以这个对照实验要产出的是**差异清单**，不是"哪个更好"的结论。

### 1.2 对照什么

选**一条**链路，只改**一个**变量。

**链路**：issue 分诊的 ReAct 循环

```
输入 issue
  → 记忆召回（一次性）
  → 循环：拼提示词 → 调模型 → 解析动作
      ├─ 有工具调用 → 执行 → 追加观察 → 回到循环
      └─ 无工具调用 → 解析最终分类 → 结束
  → 超过步数上限 → 兜底结束
```

**唯一变量**：**编排方式**（`while` 循环 vs 图 + 条件边）。

### 1.3 ★ 怎么保证对照公平（这是最关键的一节）

对照实验的第一原则是**只改一个变量**。而"编排方式"很容易被其他差异污染。

**所以设了三条硬约束**：

| 约束 | 具体做法 | 如果不这么做会怎样 |
|---|---|---|
| **同一套组件** | 复用主项目的 `ToolRegistry` / `LLMClient` / 记忆存储 | 对比变成"比谁的工具写得好"，不是"比循环怎么搭" |
| **同一份提示词和解析逻辑** | 全放在 `shared.py`，两版强制共用 | 差异可能来自提示词，而不是编排 |
| **同样的能力边界** | 手写版也要有步数上限、异常兜底、无工具调用即终止 | 手写版偷懒省功能，然后说"框架版代码多" |

**这三条对应 `docs/05` 里"D2 对照组设计缺陷"那条教训** ——
那次我以为只改了一个变量，其实改了两个，于是结论完全不可信。

**还有一个容易忽略的点：用 MockLLM。**

因为对照测的是**编排**，不是模型能力。用真实模型的话，
两版的输出差异会和"模型采样随机性"混在一起 ——
**你会分不清"结果不同是因为图搭得不一样，还是因为这次采样"**。

MockLLM 是确定性的规则版，同样输入必然同样输出。
**所以如果两版结果不一致，那一定是编排差异导致的。**

### 1.4 目录结构与依赖隔离

```
experiments/langgraph_compare/      ← 独立目录，不在 src/ 下
├── shared.py          两版共用的部分（提示词/解析/组件/样本）
├── custom_agent.py    手写版（基线）
├── graph_agent.py     LangGraph 版
├── compare.py         对比运行器
├── README.md          怎么跑
├── graph.mmd          导出的流程图（运行时生成）
└── compare_result.json 对照结果（运行时生成）
```

**为什么放 `experiments/` 而不是 `src/`？**

因为主项目的核心卖点之一是**零第三方依赖**。
把 langgraph 的引入限制在一个独立目录里，`src/nightwatch/` 依然零依赖 ——
**`pip install -r requirements.txt` 不会拉 langgraph。**

```bash
# 主项目（零依赖，能跑）
python scripts/run_tests.py

# 对照实验（需要 langgraph，独立安装）
pip install langgraph
python experiments/langgraph_compare/compare.py
```

**这个隔离方式本身就是个工程判断**：
"我想用某个工具做实验"和"我想让项目依赖它"是两件事。

## 二、实现步骤

### 步骤 1：写 `shared.py`（两版共用的部分）

**先写共用部分，再写两版** —— 顺序很重要。

如果先写手写版，很自然会把"提示词、解析、工具构造"都写进去；
到了写框架版时，要么复制粘贴（埋下"两份可能不同步"的雷），
要么回头重构（浪费时间）。

**先抽出共用部分，两边就都只能用它** —— 这是**用结构保证公平**，
而不是靠"我记得要写一样"。

`shared.py` 的内容：

```python
MAX_STEPS = 4                     # 循环上限，两版共用

@dataclass
class AgentState:                 # 状态定义
    issue: Optional[Issue]
    memory: list                  # 只写一次
    history: list                 # 只追加 ← 在框架版里需要 reducer
    step: int
    final: list

def build_prompt(state) -> list[dict]     # 提示词模板
def parse_action(text) -> dict | None     # 动作解析（None = 结束）
def parse_final(text) -> list[str]        # 最终分类解析
def setup_tools()                          # 记忆库 + 工具集
def make_llm(use_mock)                     # LLM
def recall_memory(issue, store)            # 记忆召回
def sample_issues() -> list[Issue]         # 固定测试样本
```

### 步骤 2：写手写版（`custom_agent.py`）

**写法上刻意让"控制流"最显眼**：

```python
memory, _ = recall_memory(issue, store)        # ① 召回
state = AgentState(issue=issue, memory=memory, history=[])

for step in range(MAX_STEPS):                  # ② 循环 ← 一个语句
    state.step = step + 1
    messages = build_prompt(state)
    resp = llm.complete(messages, task="agent_step")

    action = parse_action(resp.text)
    if action is None:                         # ③ 终止 ← 一个布尔判断
        result.predicted = parse_final(resp.text)
        result.terminated_by = "final_answer"
        break

    tr = tools.call(action["name"], action.get("args", {}))
    state.history.append({...})                # ④ 状态推进 ← 一个 append
else:
    result.terminated_by = "max_steps"         # ⑤ 兜底 ← for-else 语法糖
```

**这五处标记，就是后面要逐项翻译到 LangGraph 的东西。**

### 步骤 3：写 LangGraph 版（`graph_agent.py`）

**关键的一步是把 `AgentState` 翻译成 `TypedDict`**：

```python
def _append(old: list, new: list) -> list:
    return (old or []) + (new or [])           # ★ 自定义 reducer

class GraphState(TypedDict, total=False):
    issue: Any
    memory: list
    history: Annotated[list, _append]          # ★ 只追加 → 必须声明 reducer
    step: int
    final: list
```

**然后建图**：

```python
g = StateGraph(GraphState)
g.add_node("recall", recall_node)
g.add_node("think", think_node)
g.add_node("fallback", fallback_node)

g.add_edge(START, "recall")
g.add_edge("recall", "think")
g.add_conditional_edges("think", route_after_think, {
    "continue": "think",       # ← 回边 = 循环
    "end": "fallback",
})
g.add_edge("fallback", END)
app = g.compile()
```

### 步骤 4：写对比运行器（`compare.py`）

产出五类数据：

| # | 对比项 | 怎么测 |
|---|---|---|
| ① | 功能等价性 | 两版对同一批 issue 的预测结果是否一致 |
| ② | 编排代码量 | 只算**代码行**（排除注释和空行） |
| ③ | 运行时开销 | 中位耗时（多次重复取中位，抵消抖动） |
| ④ | 框架多给什么 | 逐条**实测验证**（不引用文档） |
| ⑤ | 框架藏起什么 | 从实写过程中遇到的摩擦点提取 |

**②的计算方式值得说明**：只算代码行，不算注释。

因为"LOC"很容易被操纵 —— 多写注释就能让任何方案显得更重。
**这个坑在技术圈很常见：拿总行数吹工程量的项目，一多半是注释。**

## 三、关键代码说明

### 3.1 ★ 最重要的一处：`Annotated[list, _append]`

**这是整个对照实验里最值得记的一点。**

手写版里，状态推进长这样：

```python
state.history.append({...})       # 就地修改
```

**语义隐含在代码顺序里** —— 你看到 `append` 就知道它是"追加"。
没有人需要"声明"这个语义，因为它就是 Python 的 list 行为。

LangGraph 里，节点返回的是**状态更新片段**：

```python
def think_node(state) -> dict:
    return {"history": [{...}]}   # 这是"更新"，不是完整状态
```

框架要回答一个问题：**"两个节点都动了 history，怎么合并？"**

```
默认行为：覆盖（后写的赢）
这里需要：追加（保留全部）
```

**如果不声明 reducer，`history` 会被最后一个节点的返回值覆盖掉 —— 而且不报错。**
你只会发现"历史怎么只有一条"，然后花时间排查。

**为什么这是个"值得记"的点？**

因为它揭示了框架的一个**根本约束**：

> **框架把"状态怎么变"从隐含变成了显式。**

代价是啰嗦（要写 `_append` 和 `Annotated`）。
收益是**可推理** —— 状态更新成了一个可以单独审视的函数。

**而这个"显式化"是 checkpoint（状态持久化）的前提**：
如果状态的更新语义不明确，框架无法安全地"序列化 + 恢复"。

**所以这不是框架找麻烦，是它提供的能力倒逼出来的要求。**

### 3.2 循环的表达：回边 vs `for`

| | 手写版 | LangGraph 版 |
|---|---|---|
| 表达 | `for step in range(MAX_STEPS)` | `add_conditional_edges("think", route, {"continue": "think"})` |
| 循环上限在哪 | 循环语句里（一眼可见） | **两个地方**：路由函数里判断 + 常量 `MAX_STEPS` |
| 可画图 | 不能（要自己维护） | 能（`draw_mermaid()`） |
| 大图里找循环 | 搜 `for` | 顺着边找 |

**一个反直觉的发现**（**我原以为的结论是错的**）：

写之前我以为"LangGraph 版的代码会更少"，理由是"条件边省掉了循环控制"。
**实测结果相反**：

| 口径 | 手写版 | LangGraph 版 | 差 |
|---|---|---|---|
| 全部代码行 | **89** | **163** | **+74（+83%）** |
| 其中「资源生命周期」（DI/构造/关闭） | 11 | 15 | — |
| **扣掉生命周期后的「纯编排」** | **78** | **148** | **+70（+90%）** |

> ⚠️ 这些数字**随代码演进会变**，本表在 2026-10-11 改过两次
> （更早是 79 vs 146，然后是 89 vs 168，现在是 89 vs 163）。
> 所以比数字本身更重要的，**是"为什么差"的机制** —— 见下。
> 而且无论怎么改，**方向没变：框架版更多。**

##### ★★ 一个被实测推翻的假设（比结论本身值钱）★★

改依赖注入之前，我有个猜测：

> "框架版多出来的行，可能大部分是**我自己加的收口补丁**（模块级收集器 +
> `_track` + 逐个关闭）—— 而不是框架本身的声明成本。"

理由看起来充分：那堆补丁确实有 20+ 行，而且**是我写的、不是框架要求的**。
如果这个猜测成立，那"+89%"就是个**假结论**，应该被改写成"我绕路绕出来的"。

**于是做了两件事**：① 用 `config.configurable` 把补丁删掉；
② 在源码里用 `# [lifecycle]` / `# >>> lifecycle: begin` 标记这类行，
让 `compare.py` 能把两类开销**分开算**（否则这个数字靠人读代码判断，不可复现）。

**实测结果：猜测不成立。**

```
                    全部代码行          扣掉生命周期后的"纯编排"
手写版                  89        11        78
LangGraph 版           163        15       148
差                    +74              +70
百分比                 +83%             +90%   ← 反而更高了
```

- 补丁**确实被删掉了**（168 → 163，-5 行；那个模块级全局变量 `_OPEN_STORES` 整个消失）
- 但**扣掉生命周期后，百分比反而从 +83% 升到 +90%** ——
  因为手写版的生命周期占比（11/89 = 12.4%）**比框架版（15/163 = 9.2%）还高**
- 所以 **"+89% 是收口补丁造成的"这个说法是错的**。

> **教训：这个假设值得提出来、也值得去验，但不能直接写进结论。**
> 它听起来"对自己不利"（不像是自夸），所以**特别容易通过自我审查** ——
> 人天然觉得"对自己不利的推断大概是真的"。
> 而实测是：**框架的声明开销是真实存在的，不是补丁撑出来的。**
>
> 这正是本项目反复强调的那条：**任何结论都要有实测出处**，
> 哪怕它看起来谦虚。**"谦虚的猜测"和"自夸的猜测"一样需要验证。**

**为什么框架版更多？** 三处开销（第四处已证实不是原因）：

1. **状态定义**：`TypedDict` + reducer + 类型标注（手写版一个 `@dataclass` 就够）
2. **节点拆分**：三个节点函数各自的开销（参数、返回值、docstring）
3. **兜底节点**：框架要求路由函数是纯函数，所以"往状态里写东西"必须
   单独开一个节点（手写版在 `for-else` 里顺手就做了）

**所以正确的说法是**：

> **框架把代码从"控制流"挪到了"声明"。**
> 控制流变少（省掉 `for`/`break`/`for-else`），
> 声明变多（状态类型、reducer、节点边界）。
>
> **总数取决于流程复杂度** ——
> 本次这个简单流程（1 个循环 + 2 个工具）上，声明多于控制流，所以总数更多。
> 如果流程有十几个节点、多种分支，条件边的收益会反超。

**★ 这个"我原以为 → 实测相反"的过程，正是做对照实验的价值。**

如果只看文档、只凭直觉，我会带着一个**错误的判断**去面试 ——
而那个判断经不起一句"你实测过吗"的追问。

（这也是 `docs/05` 反复出现的同一个模式：
  **一个看似合理的推断，可能完全经不起实测。**）

### 3.3 终止条件的表达：纯函数 vs `break`

手写版：

```python
if action is None:
    break                    # 直接改变控制流（命令式）
```

LangGraph：

```python
def route_after_think(state) -> str:      # 纯函数
    if state.get("final"):
        return "end"
    if state.get("step", 0) >= MAX_STEPS:
        return "end"
    return "continue"
```

**框架强制这个函数是纯函数**（不产生副作用，只决定"去哪"）。

**后果**：往 state 里写东西必须放进节点 —— 所以要多一个 `fallback_node`。

```
手写版：在 for-else 里干啥都行
框架版：路由只决定"去哪"，写状态是节点的职责 → 强制职责分离
```

**表面上是"多写了一个节点"，实质是框架逼你做了职责划分。**
而好处是：`route_after_think` 变成了**可直接断言测试**的纯函数。

```python
# 手写版的终止逻辑不好单测（和循环体耦合）
# 框架版可以直接测：
assert route_after_think({"final": ["Bug"]}) == "end"
assert route_after_think({"step": 4}) == "end"
assert route_after_think({"step": 1}) == "continue"
```

### 3.4 状态必须可序列化

手写版的 `state` 可以是任意 Python 对象（含文件句柄、数据库连接等）。

LangGraph 想要 checkpoint（把状态存下来以便恢复），就要求状态**可序列化**。

**结果**：dataclass 要变 TypedDict，复杂对象要拆成基本类型。

**这个约束在"用不上 checkpoint"时是纯负担。**

所以要问的问题是：**你真的需要中断续跑吗？**

- 需要（比如"人工审核后继续"）→ 接受这个约束，用框架
- 不需要 → 这个约束就是白付的成本

**对应到 Nightwatch**：`P1-2` 的语义记忆层有个**人工闸门**
（待审核的 SOP 提案）。如果那个闸门做成"Agent 停下来等人批准再继续"，
那就**正是需要 checkpoint 的场景** —— 而现在是自己实现的（用数据库存 pending 状态）。

**所以这里有个真实的取舍**：
自研 pending 表 vs 框架的 checkpoint。这两个方案的差异值得在面试里讲。

### 3.5 节点的"名称"有价值

框架强制你把流程拆成**有名字的节点**：

```python
g.add_node("recall", recall_node)
g.add_node("think", think_node)
g.add_node("fallback", fallback_node)
```

手写版里这三个阶段可以塞进一个函数（因为没人拦你）。

**"给阶段起名字"这个动作本身会逼你想清楚每步在干嘛。**

这是个**隐性收益** —— 它不在框架的文档里，但实写时会感受到。

## 四、与原方案的对照关系

### 4.1 逐项对照表

| 维度 | 手写版（`custom_agent.py`） | LangGraph 版（`graph_agent.py`） | 谁更好 |
|---|---|---|---|
| **循环** | `for step in range(N)` | 条件边回边（`think → think`） | 小流程手写，大流程框架 |
| **状态** | `dataclass`，就地修改 | `TypedDict` + `Annotated` reducer | 框架更严格但更可推理 |
| **终止** | `if ... break`（命令式） | `route(state) -> str`（声明式纯函数） | 框架（可单测） |
| **兜底** | `for-else` 语法糖 | 独立的 `fallback_node` | 框架（职责分离） |
| **流程可见性** | 一条直线读到底 | 要拼"图定义 + 节点 + 路由"三处 | 小流程手写 |
| **可画图** | 不能（要手工维护） | `draw_mermaid()` 一行 | 框架 |
| **中断续跑** | 自己写（几十行） | 挂 checkpointer | 框架 |
| **节点级调试** | 打日志 | 单独 invoke 节点 | 框架 |
| **依赖** | 零 | langgraph + langchain-core + ... | 手写 |
| **代码行数** | 见实测数据 | 见实测数据 | 见实测数据 |
| **上手成本** | 会 Python 就行 | 要先理解图 / 状态 / reducer | 手写 |

### 4.2 与主项目其他模块的关系

这个对照实验**不是孤立的** —— 它和主项目里三处设计**直接相关**：

| 主项目里的设计 | 和 LangGraph 的关系 |
|---|---|
| `loop/react.py` 的手写循环 | **就是本对照的手写版**（这里是简化版，只保留 2 个工具） |
| `loop/reliability.py` 的四层可靠性 | 框架版**没有对应物** —— 重试/熔断/循环检测要自己写或用 LangChain 的组件 |
| `memory/lifecycle.py` 的记忆六环节 | 框架不提供记忆管理，这部分**两版完全一样**（共用） |
| **P1-2 的人工闸门** | 这是"需要 checkpoint 的典型场景" —— 见 3.4 的讨论 |

**一个重要的观察**：

> **这个对照只覆盖了"编排"这一层。**
>
> Nightwatch 里真正花时间的部分（记忆生命周期、上下文预算、
> 可靠性四层、评测体系）**框架不提供，两版都要自己写。**

**所以"用不用框架"这个问题，影响面比想象中小** ——
它只影响"编排"这一层，而那一层在总代码量里占的比例不高。

**这个结论对面试回答很重要**：它把"用不用框架"从信仰问题
变成边界问题 —— **框架管编排，不管别的。**

### 4.3 实测数据

> 运行 `python experiments/langgraph_compare/compare.py` 生成。
> 数据存在 `experiments/langgraph_compare/compare_result.json`。

**① 功能等价性**

见运行输出。两版应该给出**相同**的分类结果 —— 否则说明编排差异
影响了行为，需要逐个排查（这本身有信息量）。

**② 编排代码量**（只算代码行）

| 文件 | 代码行 | 其中生命周期 | 纯编排 |
|---|---|---|---|
| `custom_agent.py`（手写编排） | **89** | 11 | **78** |
| `graph_agent.py`（框架编排） | **163** | 15 | **148** |
| `shared.py`（两版共用，不计入对比） | 289 | — | — |
| **差** | **+74（+83%）** | — | **+70（+90%）** |

**★ 这份数字在 2026-10-11 改过两次**：

⚠️ **"扣掉生命周期后差得更多"是反直觉的，但它是真的**：
手写版的生命周期占比（12.4%）比框架版（9.2%）**还高**。
所以那条"框架版多出来的行是我自己加的补丁"的猜测**被实测推翻了** ——
详见 4.3 节里"一个被实测推翻的假设"。

**③ 运行时开销**

```
手写版        中位  1 ms
LangGraph 版  中位  5 ms
额外开销      +4 ms

扣掉两版都要付的那一次组件构造（≈1.06 ms）后：
  手写版纯编排   ≈ 0.0 ms
  LangGraph 纯编排 ≈ 3.9 ms
  纯编排差价     +4 ms      ← 这才是"选哪种编排"的代价
```

**★ 旧的"2ms / 8ms"为什么不能信**（这是本次改造的直接动因）：
那时框架版**每个节点都建一次组件**，一次运行重建 `1 + 步数` 次；
实测单次 `setup_tools()` ≈ 1.06 ms，所以 1 步的样本多花 ≈2.1 ms、
3 步的多花 ≈4.2 ms —— **旧差值 6ms 里有一半以上是"组件重建"**，
不能归因给编排。

改造后两版都是**一次运行建一次组件**（`config["configurable"]` 注入），
差值才可归因。**同一个数字，改前改后的含义完全不同。**

（仍然要谨慎：绝对值是毫秒级，+4ms 在真实链路里被模型调用完全淹没。
它的价值不在于"框架慢"，而在于**把开销归因清楚**。）

**④⑤ 框架多给 / 藏起的** —— 见下一节。

### 4.4 最终结论

**不是"谁更好"，而是"什么场景用什么"**：

```
流程 < 5 步、分支少        → 手写（图的间接成本 > 收益）
流程 > 10 步、或要中断续跑  → 框架（手写最难补的是"中断续跑"）
原型阶段                  → 框架（改结构快）
要抠性能 / 极致可控        → 手写
```

**★ 这个结论里"步骤数"这个标准是实写之后才敢说的。**

写之前我的判断是"框架总是更啰嗦"，实测**方向一致但幅度比想象的大**：

```
本次实测（2026-10-11，改依赖注入后重测）：
  LangGraph 版 163 行代码 vs 手写版 89 行（+83%）
  扣掉"资源生命周期"那几行后：148 vs 78（+90%）

★ 我一度以为"+89% 是我自己加的收口补丁撑出来的"，
  实测推翻了 —— 补丁删掉后，扣掉生命周期反而差得更多（+90%）。
  **声明开销是真实存在的。**
```

**所以"框架更啰嗦"在本次这个简单流程上是对的** —— 但原因是
**声明开销 > 控制流节省**，而不是"框架天然啰嗦"。

如果流程有十几个节点、多种分支，条件边的收益会反超。
**但这个"如果"我没测** —— 所以我只能说"在本次这个规模上框架更重"，
**不能说"框架总是更重"**。

**这就是为什么要做对照，而不是"看文档觉得"。**

## 四之二、本次实写中踩到的两个坑

**这两个坑比上面的结论更有价值** —— 因为它们是"只有真写过才会遇到"的东西。

### 坑 1：我"为了公平"自己重写了一份解析，结果两版一起偏离了真实

**现象**：第一次跑对照，两版的预测**全是空列表** —— 而"一致率 100%"还通过了。

**根因**：我在 `shared.py` 里自己写了一套解析（正则匹配 `工具调用：xxx`），
想的是"两版都用这份就公平"。

**但主项目和 MockLLM 用的是 JSON 格式**：

```json
{"thought": "...", "action": "search_similar_issues", "action_input": {...}}
```

**我写的格式和它不一致** —— 于是两版都解析不出动作，都返回空。

**这个 bug 的可怕之处**：**"两版一致"这个检查通过了**。
因为两版都错得一样 —— 对照实验的"等价性检查"完全没能发现问题。

**教训**：

> **"共用"应该是"复用同一份实现"，而不是"写两份一样的"。**
>
> 我以为"把公共部分抽到一个文件"就保证了公平。但因为那份实现是**我重写的**，
> 它和真实系统（主项目）的行为不一致 ——
> **于是"公平"只存在于两版之间，而两版一起偏离了真实。**
>
> 这是对照实验的一个**隐蔽陷阱**：
> 只关心"两版之间一致"，忘了问"和真实实现一致吗"。

**正确做法**（如果继续做）：把 `TriageAgent._parse_decision` 提取成独立函数，
让主项目和本实验都 import 它 —— **真正的单一份实现**。
本次为了不改动主项目（避免引入风险），采用了"对齐格式的简化实现"，
并在 `shared.py` 里明确标注了差异。

### 坑 2："统一收口"的设计让 fallback 覆盖了正确答案

**现象**：修好坑 1 后，手写版能出结果了，但 LangGraph 版**仍然全是空** ——
一致率只有 40%，而且失败的 3 个都是"手写版有答案、框架版没有"。

**根因**：我设计成"所有路径都收口到 fallback 节点"（看起来更整洁）：

```python
add_conditional_edges("think", route, {
    "continue": "think",
    "end": "fallback",       # ← 正常结束也要过 fallback
})
```

而 `fallback_node` 无条件返回 `{"final": []}` ——
**think 节点写好的分类，走到 fallback 时被空列表覆盖了。**

**为什么会被覆盖？因为 `final` 没有 reducer，语义是"覆盖"。**

回头看 `GraphState` 的定义：

```python
history: Annotated[list, _append]     ← 追加（我显式声明了 reducer）
final: list                            ← 覆盖（默认行为，我没声明）
```

**"没显式声明"不等于"没有语义"** —— 它有一个**默认语义（覆盖）**，只是你没看见。

**这和 3.1 节讲的是同一个机制，但这次是它的反面**：

```
3.1 节：声明了 reducer → 得到"追加"语义（符合预期）
这个坑：没声明     → 得到"覆盖"语义（不符合预期，而且不报错）
```

**手写版不会有这个问题**，因为：
- 手写版没有"所有路径收口"这个结构（`break` 直接跳出去）
- 就算有，`state.final = []` 这种覆盖在代码里**是看得见的**

**修法**：兜底节点必须先检查再写。

```python
def fallback_node(state) -> dict:
    if state.get("final"):
        return {}          # 已有答案 → 什么都不做（空 dict = 无更新）
    return {"terminated_by": "max_steps", "final": []}
```

**修完一致率 100%。**

### 坑 3（2026-10-09 复查发现）："等价性通过"不等于"对照有效"

**现象**：一致率 100%，看起来对照成立。但把报告拆开看：

```
#901 ['Bug'] ['Bug'] ✓      #903 ['Bug'] ['Bug'] ✓      #905 ['Bug'] ['Bug'] ✓
#902 []      []      ⚠      #904 []      []      ⚠     ← 两版都空
```

**两件事被 100% 这个数字盖住了**：

① **2/5 样本两版都返回空。**
   根因是两层不匹配：**字段名**（MockLLM 输出 `predicted_labels`，
   而 `parse_final` 只认 `labels`/`label`/`classification`/`answer`）
   和**标签体系**（MockLLM 输出 `bug/timeout`，解析只认 `Bug`/`Docs`/…）。
   于是路径 ① 全落空，靠路径 ② 的**文本子串匹配**兜底 ——
   `bug/timeout` 里含 "bug" 就被判成 `['Bug']`，`needs-triage` 什么都不含就成了 `[]`。

   所以那 3 个"✓"也是假的：**`#901` 期望 `Build`、`#903` 期望 `Performance`
   、`#905` 期望 `Build`，全被判成了 `['Bug']`。**
   **准确率其实是 0/5** —— 只是这个实验本来就不测准确率，所以没人发现。

② **0/15 次运行走到第 2 步 —— 循环一次都没执行。**
   `MAX_STEPS = 4`，但每个样本都在第 1 步 `finalize` 了。
   因为记忆一旦命中，MockLLM 走的是"无需重复检索 → 直接 finalize"的捷径。

**为什么 ② 致命**：这个实验对照的**就是循环编排**（`for` vs 回边）。
循环没跑，意味着**回边和 fallback 分支一次都没走到** ——
而"框架版多了 67 行"里，相当一部分正是 fallback 节点和条件边。
**结论建立在从未被执行的代码上。**

**教训（比坑 1 更普遍）**：

> **"一致"只证明两版行为相同，不证明两版都在正常工作。**
> 两版可以在同一个地方一起失败，然后拿到 100% 的一致率。
> 所以对照实验必须单独报**有效一致率**和**关键路径覆盖率**，
> 而不是只报一个一致率。

**已加的防线**（`compare.py`，2026-10-09）：

- 一致标记从两态变三态：✓ 一致且非空 / ⚠ 一致但都空 / ✗ 不一致
- 新增"有效一致率"（排除两版都空的样本）
- 新增"循环覆盖"：统计有多少次运行走了 ≥2 步；为 0 时直接告警
- 两个指标都写进 `compare_result.json`

**样本本身还没改**（所以现在跑会看到两条告警）——
这是诚实的现状：**报告现在会告诉你"对照不成立"，而不是假装成立。**

**★ 这三个坑说明的事**：

```
坑 1  →  "公平对照"的实现方式本身可能引入偏差
坑 2  →  框架把"状态更新"从隐含变显式，但**默认值仍然是隐含的**
坑 3  →  "一致率 100%"可以来自"两版一起失败"，也可以来自"循环根本没跑"

三个坑都不是"读文档能避免"的 —— 只有真写过才会遇到。
```

### 坑 4（2026-10-11 修复）：修"循环没跑"的过程中，又挖出三层根因

**背景**：坑 3 加了两条告警，报告开始说"对照不成立"。接下来的任务是
**真把循环跑起来**，而不是继续报告问题。

验收标准（用户给的，很明确）：

```
循环覆盖率 > 0
两版步数分布一致
不再出现"循环从未被执行"告警
若一致率掉了，逐个排查，不要调松阈值
```

最后那句是关键：**"不要调松阈值"**堵掉了最容易的退路，
逼着去找根因 —— 而根因确实不在阈值。

---

#### 第 1 层：`recall()` 没有相似度阈值 → "不命中"这个状态不存在

`store.recall()` 的 `_rank()` 只做"排序后取 top_k"，**没有任何下限**。
所以**只要记忆库非空，任何 issue 都会"命中"**。

实测：连"安装依赖报编译错误"这种和 h1~h4 毫无重叠的 issue，
也会召回 h3(0.43) / h1(0.37) —— 分数低，但**没有东西把它过滤掉**。

而 `build_prompt` 只要记忆列表非空就打 `[语义相似]` 标记，
MockLLM 看到标记就 finalize。两件事合起来：

> **"记忆不命中"这个状态在系统里根本不存在** ——
> 所以"加几条症状不同的样本"治不了本。

**修法**：在召回那一层加 `MIN_RECALL_SIMILARITY` 过滤。

---

#### 第 2 层：实验自己写死的 `dim=64` → **阈值怎么调都不对**

> ⚠️ **这一节在 2026-10-11 晚做过一次修正。** 原版写的是
> "**维度太低**…把嵌入维度从 64 **提到 1024**"，并暗示 64 是默认值。
> 补了 dim 单变量对照（`dim_sweep.py`）之后发现：
> **"维度太低"这个诊断方向是对的，但参照点错了** ——
> 出问题的是实验自己写的 64，而**主项目的默认值是 256**，
> 256 其实分得开。详见下面的对照表。

加了阈值，我第一反应是"调一个能分开的阈值"。但探针测试打出了这个：

```
样本                        TOP1 相似度
"UI 按钮错位 / flex 布局…"   0.587   ← 和 CI 构建完全无关
#904 merge 行数（该命中）     0.592
#901 CI 构建超时（该命中）    0.473
```

**无关样本的分数比"该命中"的还高** —— 分布是重叠的，
而**阈值只能切分分布，不能把重叠的分布切开**。

诊断（这一步是关键，因为症状完全不像"维度问题"）：

```
重合 bigram: 只有 ['i ']          ← 字面上只共有一个"i 空格"
q buckets: 26 个   m buckets: 18 个
intersect: 10 个桶相撞
```

**只重合 1 个 bigram，却有 10 个桶相撞** —— 碰撞不是来自真实重合，
而是来自**维度太窄**：64 个桶装几百个 bigram，平均每桶塞 5~6 个 token，
于是"毫不相干的字符对"落进同一个桶就被算成相似。

##### 补做 dim 单变量对照（`experiments/langgraph_compare/dim_sweep.py`）

**只改 `dim` 一个变量**，记忆库 / 样本 / 编码算法 / 召回逻辑全部共用：

| dim | 相关组区间 | 无关组最高 | 空档 | 结论 |
|---|---|---|---|---|
| 64 | [0.473, 0.668] | 0.587 | **−0.115** | 重叠，切不开 |
| **256** | [0.355, 0.568] | 0.293 | **+0.061** | 分得开（余量小） |
| 1024 | [0.366, 0.550] | 0.222 | +0.144 | 分得开（余量充足） |

★ **`dim` 是 `HashEmbedding` 的构造参数，主项目默认 256**
（`src/nightwatch/memory/store.py:199`）。64 从来不是默认值 ——
它是实验脚本 `setup_tools()` 早期自己写死的。

| 维度 | 相关组均值 | 无关组均值 | 全体均值 |
|---|---|---|---|
| 64 | 0.579 | 0.480 | 0.524 |
| 256 | 0.454 | 0.233 | 0.331 |
| 1024 | 0.442 | 0.147 | 0.278 |

**修法（修正后）**：把 `EMBED_DIM` 设成 **256**，
即**对齐主项目默认值** —— 而不是另造一个 1024。

**为什么"对齐默认值"比"自己挑个更好的数"更对**：

1. **减少一个变量** —— 实验和主项目共用嵌入参数，
   差异就只剩"编排方式"（这是本实验唯一要测的变量）
2. **发现的问题更可能是真的** —— 实验用自己的参数时，
   观察到的行为可能**是实验自己造出来的**
3. **用"够用的最小值"而不是"最宽松的值"** ——
   1024 的宽空档（+0.144）不是"更对"，只是"更宽松"。
   **把实验调得比真实系统更稳健，就测不出真实系统的脆弱点。**
   这和"测试环境不该比生产宽松"是同一条原则。

**代价（诚实清单）**：256 的空档只有 +0.061。
而这个阈值**必须重标定** —— 因为 `MIN_RECALL_SIMILARITY` 是和
`EMBED_DIM` **绑定**的：

> **0.30 是按 dim=1024 的空档 [0.222, 0.366] 取的中点**（中点 0.294，取整到 0.30）。
> 换成 256 后空档变成 [0.293, 0.355]，中点 0.324 ——
> **0.30 已不再是任何中点**，且它到下限只剩 **+0.007**（0.300 − 0.293），
> 几乎贴着探针。

**重标定结果：0.32**（中点 0.324 往"危险的那一侧"让 0.004）：

| 阈值 | 到下限（阈值−无关组最高） | 到上限（相关组最低−阈值） | 说明 |
|---|---|---|---|
| 0.300 | +0.007 | +0.055 | 旧值：下限只剩千分之七 |
| **0.320** | **+0.027** | **+0.035** | **当前值** |
| 0.324 | +0.031 | +0.031 | 严格中点 |

★ **为什么取 0.32 而不是严格中点**：阈值降低会让"到下限"变小、
"到上限"变大。0.32 < 0.324，所以它的到下限（+0.027）**比中点还小** ——
**它是让危险的一侧更紧，不是更松**。取它的理由是它仍显著优于 0.30：
把下限余量从 +0.007 提到 +0.027（约 4 倍），而付出的只是上限从 +0.055
降到 +0.035（仍宽裕）。

真正的原则是：**余量要按"两边的代价"分配，不是平均分。**
本项目实测过边界是**单侧**的（只对"无关样本变热"敏感），
误召回那一侧才是真会破的，所以让它多留。
**"取中点"是默认策略，不是最优策略** —— 只在两侧代价相等时中点才最优。

⚠️ 提到 0.32 **不等于这个坑消失了**：实测把 #906 措辞改到 0.329 时，
**仍然越过新阈值**。它只是把安全垫从千分之七加厚到百分之二点七。

**破坏性验证（2026-10-11 第二轮，阈值 0.32 / dim=256）**：
每条守卫都反向验过，实测输出：

| 破坏方向 | 期望 | 实际 | 报错信息 |
|---|---|---|---|
| 阈值 → 0.40（漏召回） | 报错 | 报错 | `worst = -0.045` |
| 阈值 → 0.20（误召回） | 报错 | 报错 | `worst = -0.093` |
| 无关样本措辞 → 靠向记忆 | 报错 | 报错 | 两组重叠 0.355 < 0.400 |
| 无关样本正文 → 靠向记忆 | 报错 | 报错 | 两组重叠 0.355 < 0.366 |
| 探针 → 加上 h1 的词 | 报错 | 报错 | 两组重叠 0.355 < 0.358 |
| 阈值 → 0.324（严格中点） | 通过 | 通过 | `worst = +0.031` |
| 阈值保持 0.32 | 通过 | 通过 | `worst = +0.027` |
| `EMBED_DIM` → 1024 | 报错 | 报错 | `assertEqual` 拦住 |

★ **报错信息分两类，暴露两种不同的失效**：

- **第一类（余量被吃掉）**：#906 加「超时」→ 升到 0.300/0.329，
  仍**小于** 0.355 → 两组不重叠，走 `worst > 0.02` 报错。**更隐蔽。**
- **第二类（边界被击穿）**：#907 整条改成 h4 措辞 → 升到 **0.400**，
  **超过** 0.355 → 两组重叠，走 `low_hit > high_miss` 报错。

**两条断言缺一不可** —— 只断言"分得开"会漏掉第一类。

⚠️ 一个**差点踩进去**的坑：做破坏验证时如果"只改一处、隔离测分数"，
量出来的数**不可比** —— 它没和完整记忆库+其余样本一起参与召回，
top-1 命中对象都不一样。本次差点把 #907 的 0.380（隔离测）
当成真实值，而它在完整样本集里其实只有 0.287（**根本没击穿边界**）。
**破坏验证必须在和生产同一套口径下跑。**

##### ★ 别忘了：dim 提高会改变**分数尺度**

维度提高 → 每个桶分到的质量变稀 → **所有**余弦分数普遍下降：

```
#901 从 0.473（dim=64）→ 0.366（dim=1024）
探针 从 0.587（dim=64）→ 0.169（dim=1024）
```

两组都降，但**无关组降得狠得多**（0.480→0.147，降 0.333；
相关组只降 0.137）。**相对关系反转**才是"分得开"的真正来源 ——
所以「区分度出现」里**含有尺度变化的成分，不是纯碰撞消除**。

两个实际后果：
- **跨维度比较绝对分数没有意义**（"0.5 算高分吗"在不同 dim 下答案不同）
- **阈值必须随维度重新标定**，不能把一个维度上调好的搬过去

**教训**：

> **当"调阈值"怎么调都不对时，先检查信号本身有没有区分度。**
> 阈值是切分工具，不是分离工具。
>
> 而且这个教训是被"不要调松阈值"这句话逼出来的 ——
> 如果当时允许我调阈值，我会调到 0.6，让无关样本不命中、
> 同时把 #901 也一起牺牲掉，然后**得到一个能跑但前提错误的实验**。

**★ 还有一条更细的教训（写注释时才发现）**：

> 我把"实验自己写死的 64"说成了"默认值"，还据此写下
> "为什么从默认的 64 提到 1024"。**这是事实陈述错误**，
> 不是参数选错 —— 它会让读者以为主项目就这么窄，
> 从而得出"主项目召回质量差"的错误结论。
>
> **"我拍的数"和"系统默认值"必须分开说。**
> 前者可以随便改，后者改了会影响别的调用方 ——
> 把两者混为一谈，等于给自己发了一张"随便改"的许可。

#### 第 4 层：Mock 关键词表缺了"结果不正确"这整整一类

修好渲染后，`#901/#902/#903/#904` 都正常了，但 `#906/#907` 走完 2 轮
工具调用后**仍然**输出 `needs-triage` → `parse_final` 得到 `[]`。

追踪 `MockLLM._tags()`：它的关键词表全是"程序报错/资源不足"类 ——

```

但它恰恰最危险（不报错，只给错答案），
在 pandas/numpy 这类库的用户报告里是**最高频的一类**。

**修法**：加 `incorrect` 类别（时区/夏令时/偏移/NaN/精度/溢出/截断/类型转换），

否则新标签会在归一化时被丢掉，**变成"未给出预测"**。

⚠️ **这是"上下游有隐式契约"那个坑的第三次**
（前两次：`ci`/`bld`、`depr`/`tst`/`ref`）。
两边各维护一份标签表，靠"记得同步"保证一致 ——
而"记得同步"不是一种机制。

另外 `#907` 还暴露了一个次生问题：`_extract_symptom` **只从标题取症状**
（正文不参与标签推断），所以标题里必须有那个关键词。
把标题从「分组聚合时自定义函数的返回值被忽略」改成
「分组聚合结果返回 NaN」—— 这不是"迁就 Mock"，
**用户本来就会这么写标题**。

#### 第 5 层：两版的 `steps` 统计口径都错了（而且是**对称地**错）

修到这一步循环覆盖率已经 > 0 了，但调试时发现：
一条真正跑了 3 轮的样本，`steps` 报的是 **1**。

根因：手写版用 `state.step`，框架版用 `final_state["step"]` ——
**两个都是"最后写入的值"而不是"执行了几步"**。

```
手写版：for step in range(MAX_STEPS): state.step = step + 1
        → 循环结束时 state.step = 最后一次迭代的步号

框架版：think_node 返回 {"step": s.step}，s.step = state.step + 1
        → 最后一个节点写入的值
```

**因为错误是对称的，一致率照样 100%，只是步数分布整体偏小** ——
而"步数分布"正是判定循环覆盖率的依据 → **覆盖率被低估**。

**这是"指标算错比指标难看更危险"的典型**：
一个算错的指标会给出一个看起来合理的错结论，
而你不会去质疑一个"看起来合理"的数字。

**修法**：两版都用独立的计数器（`executed_steps` / `steps_executed`），
不搭业务字段 `step` 的便车 ——
`step` 的语义是"当前步号"（给提示词用的），不是"跑了几步"。

# 第一版（错的）

self.assertGreater(min(hs) - max(ms), 0.05)

循环论证。阈值怎么错，分组就跟着怎么错，断言永远成立。

```

阈值 0.40（会漏召回）    → 拦住 ✓
阈值 0.20（会误召回）    → 拦住 ✓

★ 这一条是**"怎么知道你的测试是有效的"** 的答案：**破坏它，看它会不会红。**
一条从不失败的断言，和没有断言是同一个东西。

测试只用**标定样本**（#906/#907）量余量，漏掉了
`dim_sweep.py` 里的 3 个探针。实测两套口径：

|---|---|---|

而真正卡住阈值下限的是**探针**「UI 按钮错位」= 0.293，
比标定样本 #906（0.286）**还高 0.007**。

> **守卫必须测"最危险的那个数"。**
> 只测乐观口径 = 给守卫配了一个比现实更宽的边界，于是它守不住真会发生的翻车。

**根因**：`PROBES` 定义在 `dim_sweep.py` 里，测试 import 不到 ——
"同一件事"有了两份实现，各自长出不同口径。
这和前面 `parse_action` / `_format_memory` 是**同一个坑**：
**"共用"要复用实现，不要各写一份。**

**修法**（两处）：

1. `PROBES` 上提到 `shared.py`，新增 `shared.separation_margin(store)`

2. 余量断言从 `gap > 0.05` 换成 **`worst > 0.02`**

★ **为什么 gap 不够**：`gap` 是两个方向余量**之和**，
会掩盖单边贴地 —— 可能一边 +0.040、另一边 +0.002，
gap 有 0.042 看着挺宽，实际某一侧已贴着悬崖。
本项目实测边界是**单侧**的，所以该守 `min(两侧)`。

另加一条断言 `n_unrelated == 5` —— 防止哪天有人把探针从
`separation_margin` 里去掉，测试**悄悄退化成乐观口径**而数字看着都正常。

#### ★★ 补上"准确率"：一致率 100%，准确率 **50%** ★★

"坑 2"里写过一句话：

> 那 3 个"✓"也是假的：`#901` 期望 `Build`、`#903` 期望 `Performance`，
> 全被判成了 `['Bug']`。**准确率其实是 0/5** —— 只是这个实验本来就不测准确率，
> **所以没人发现。**

这句话就是本节要拆的雷：**"没人发现"不是一个可以接受的结局。**

于是补了一个和"一致率"并排的指标：

| 指标 | 回答的问题 | 实测 |
|---|---|---|
| 预测一致率 | 两版**行为一样**吗？ | **100%**（6/6） |
| 有效一致率 | 排除两版都为空之后呢？ | 6/6 |
| **准确率（Top-1）** | 两版**都对**吗？ | **50%**（3/6）← 两版都是 50% |

**一致率 100% + 准确率 50% = 两版一起错。**
这种组合下说"功能等价"是自欺 —— 真正的含义是"**两版错得一样**"。
所以报告里加了一条硬规则：

```
若 一致率 100% 且 准确率 < 100%
→ 显式告警"等价性结论无效"，并且**不再打印**"✓ 两版功能等价"
```

判据本身写成 `shared.equivalence_valid(consistency, acc_custom, acc_graph, covered=...)` ——
放在 shared 里是为了让**报告、JSON、测试用同一份实现**
（否则又是"同一件事两份实现"，本项目在这个坑上已经栽过四次）。

##### 参照（`expected_label`）怎么放才算数

准确率的参照必须满足两条，缺一条这个指标就是假的：

1. **硬编码**（不能从被测逻辑推出来 → 那是循环论证）
2. **在被测对象之外**

第 2 条具体到实现上：设计意图放在**模块级字典** `shared.EXPECTED_LABELS`，
而**不是**挂在 `Issue` 对象上。因为 `Issue` 会**被传进被测代码**，
主项目里 `react.py:1081` **就真的读** `issue.gold_labels` 来判误诊。

> 今天的实验路径不读它 —— 但**"今天不读"不是保证**。

这条还写成了测试（`test_准确率参照不依赖被测对象`）：
**把 `gold_labels` 清空，看预测变不变**。变了就说明被测逻辑读了标准答案。

##### 根因：标签体系三层不匹配（**修复另开一轮**）

| 层 | 问题 | 在哪 |
|---|---|---|
| ① | `parse_final` 不认 Mock 输出的 `predicted_labels` 字段 → 路径①永远失效 | 实验侧 |
| ② | 退化到**子串匹配** → `bug/timeout` 含 "bug" 就判 `['Bug']` → **预测成了常数** | 实验侧 |
| ③ | `MockLLM` 注释写"记忆优先"、实现是"记忆兜底"，且所有标签被无条件加 `bug/` 前缀 | **主项目** |

实测三种修法的上限（模拟 + 真实跑）：

| 方案 | 准确率 |
|---|---|
| 现状 | 3/6 = 50% |
| 只修实验侧（①②） | 3/6 = **50%**（没救回来） |
| 实验侧 + 主项目（③） | 6/6 = **100%** |

**只修 ①② 救不回来** —— 因为 `#901`/`#903` 的正确答案（`Build`/`Performance`）
本来就只能从**记忆里已验证的标签**来，而它被 Mock 现场猜的 `timeout`/`oom` 覆盖了。

**★ 本轮的决定：度量先落地，修复另开一轮。**
理由是 ③ 会改动**主项目**的推断行为，得单独评估对主项目自身评测的影响，
不该混在"补指标"这一轮里顺手做掉（那正是"顺手改一处"导致结论失真的典型）。

所以测试里现在断言的是 **`准确率 >= 0.5`（下限，不是满分）**，
并在 docstring 里写明"**修复那轮请把这个下限提到 1.0**"。
用 `>=` 而不是 `==` 是本项目的原则：**断言约束，不断言快照** ——
`== 0.5` 会在修好的那一刻假失败，`>= 0.5` 则自动容纳改进。

> **一条永远通过的断言比没有断言更糟。**
> 但一条"因为写着当前值、所以修好就红"的断言，也只是在给未来添麻烦。
> —— 用`>=` 记下"底线在哪"，用注释记下"目标在哪"。

## 五、这个实验在面试里怎么用

**30 秒版本**：

> "我的主项目是手写 ReAct 循环，零依赖。但我另外用 LangGraph
> 把同一条链路重写了一遍做对照 —— **同一套提示词、工具、样本，
> 只改编排方式**。
>
> 结果有两个反直觉的发现：
>
> ① **框架版的代码反而更多**（163 vs 89 行，+83%；
>    扣掉资源生命周期那几行是 148 vs 78，+90%）。
>    我原以为条件边能省掉循环控制，实测相反 ——
>    **声明开销（TypedDict + reducer + 节点边界）超过了省下的控制流**。
>    流程变复杂后这个结论可能反转，但那个我没测，
>    所以只说"在这个规模上框架更重"，不说"框架总是更重"。
>
>    ★ 这里我差点犯一个更隐蔽的错：我一度怀疑"+83% 是因为我自己
>      加了资源收口补丁撑出来的"—— 那个猜测听起来**很谦虚**，
>      所以特别容易直接写进结论。但我真去测了：把补丁删掉之后，
>      **扣掉生命周期反而差得更多（+90%）**，因为手写版的生命周期
>      占比比框架版还高。**假设被推翻了。**
>      教训是：**"对自己不利的猜测"和"对自己有利的猜测"一样需要验证** ——
>      人天然觉得"自我批评大概是真的"，那也是一种未经检验的直觉。
> ② **框架把'状态怎么变'从隐含变成了显式** ——
>    手写时 `list.append` 是就地改，图里必须声明 reducer，
>    否则**静默覆盖**。而这个显式化是 checkpoint 的前提。
> ③ **框架把'资源生命周期'变复杂了 —— 但这是可以解决的**（这条最少人提，最实用）。
>    第一版我让每个节点各自 `setup_tools()`，于是每轮回边都重建组件，
>    想管住就得靠**模块级全局收集器** —— 那是绕过，不是解决
>    （不线程安全，生产里会让 QPS 掉得很惨）。
>
>    后来改成框架自带的注入通道 `config["configurable"]`：
>
>         def recall_node(state, config):
>             store = config["configurable"]["store"]      # 框架注入，不自己建
>
>    → 组件生命周期和手写版对齐了（一次运行建一次）。
>
>    **所以这条的结论不是"框架让资源管理更麻烦"，而是"我第一版没用它
>    提供的机制"。** 代价换了个形式：注入通道是**约定式**的
>    （key 名写错只能运行时发现），而手写版的闭包是**词法可见**的。
>    我加了测试钉住"一次运行只建一次组件"—— 因为一旦有人又把
>    `setup_tools()` 写回节点里，耗时结论会悄悄失真，而报告不会有任何异常。
>
> ④ **而且这个改造直接改变了耗时结论。**
>    改之前实测是"手写 2ms / 框架 8ms"，看着像"框架慢 4 倍"——
>    但那个差值里混着**组件重建**（单次 ≈1.06ms，1 步的样本重建 2 次、
>    3 步的重建 4 次）。改完生命周期对齐后重测是 **1ms / 5ms**，
>    再扣掉两版都要付的那一次组件构造，纯编排差价是 **+4ms**。
>    **同一个对比，改前改后的数字含义完全不同** ——
>    改前那个 8ms 里有一半以上在骂我自己写的补丁。
>
> 所以我不觉得这是'用不用框架'的问题，而是**边界问题**：
> 框架只管编排，记忆管理、上下文预算、评测这些它都不管 ——
> 那些部分两版都要自己写。
>
> ★ 顺带一个我认为比上面都重要的发现：这个实验的**一致率 100%，
>   但准确率只有 50%** —— 两版一起错。我后来专门加了准确率指标，
>   就是为了让这种情况**自己暴露出来**，而不是靠我记得去看。
>   （详见下面那段。）"

**★ 还有一段更值钱的（"我怎么知道这个结论是真的"）**：

> "这个实验我返工过 —— **第一版跑出来的'一致率 100%'是假的**。
> 报告正常生成、脚本正常退出，但把数字拆开看：
> **循环一次都没跑**（0/15 次走到第 2 步），而且 6 个样本里
> 2 个两版都返回空。
>
> 换句话说，那个 100% 建立在'两版都在第 1 步就结束'上，
> 而'框架版多出来的行'里有相当一部分是**从未被执行的代码**。
>
> 修它的时候剥了五层：召回没阈值 → 实验用的嵌入维度和主项目不一致
> → 共用提示词的渲染格式没和主项目对齐 → Mock 关键词表缺了
> '结果不正确'整整一类 → 两版的步数统计口径都错了（而且是对称地错，
> 所以一致率照样 100%）。
>
> 每一层修完只暴露下一层。而且**如果当时允许我'调松阈值让报告变绿'，
> 后面四层永远不会被发现** —— 我会带着一个能跑通但前提全错的实验去面试。
>
> 还有一件事我印象更深：修完之后我补了一组**故意破坏**的验证，
> 才发现自己写的那条余量断言**根本没有保护作用** ——
> 它用被测的那个阈值来分组，再断言分组分得开，是循环论证。
> 把阈值改成明显会漏召回的值，测试照样绿。
>
> **一条永远通过的断言，比没有断言更糟** ——
> 没有断言时你知道自己在裸奔，有一条假断言时你会以为自己有保护。
>
> 修完这个我以为就完了，结果**同一组测试又发现第二个假保护**：
> 分组是对的了，但量余量时**只用了我标定过的样本**，
> 漏掉了一组"探针"（没参与标定、故意和记忆无关的输入）。
> 含探针的真实余量 0.061，测试量出来的是 0.069 —— **偏乐观**。
> 而真正卡住阈值的恰恰是探针，不是标定样本。
> **守卫必须测"最危险的那个数"**，不然它守的不是真的那条边。
> 根因是探针定义写在另一个脚本里，测试 import 不到 ——
> "同一件事"长出了两份口径。**这和我前面踩的"共用要复用实现"
> 是同一个坑，只是这次落在测试上。**
>
> 所以我现在对'实验跑通'这件事的判断是：
> **先看覆盖率，再看一致率** —— 覆盖率是前提，一致率是结论。
> 前提不成立时，结论再好也没意义。
>
> 另外还有一个我觉得挺关键的细节：**阈值和嵌入维度是绑定的**。
> 我一开始把阈值调好了，后来把维度改成和主项目一致，
> 才发现**旧阈值压根不能沿用** —— 因为它是在另一个维度的空档里取的中点。
> 维度一变，所有余弦分数的尺度都跟着变，空档的位置和宽度全变了。
> 所以这两个参数必须一起重标，改一个而不管另一个，
> 就会掉进'阈值怎么调都不对'—— 而那其实是分布本身没分开。"

**为什么这段比第一段更能打**：

因为它回答的不是"你做了什么"，而是**"你怎么知道你做的是对的"** ——
后者才是面试官真正想验的（也是 AI 应用岗最缺的能力：
大部分人能跑通 demo，少数人能说清 demo 为什么可信）。

**为什么这个回答有说服力**：

1. **有实测数据**（不是"我觉得"）
2. **有反直觉发现**（"框架代码更多" —— 和我写之前的预期相反）
3. **指出了框架的边界**（把信仰问题变成工程问题）
4. **诚实**（承认框架在某些场景更合适）
5. **有返工记录**（证明"我会验证自己的结论"，而不是"我会讲结论"）

> ★ **这段原本是错的，2026-10-09 修正；数字 2026-10-11 再次更新**：
> 更早一版写的是"框架版代码**更少**"，而实测数据是 146 vs 79（**多** 85%）。
> **数字对，形容词错** —— 而且同样的错在 `compare.py` 的结论段里也有一份
> （都是"实测前的预期"被当成"实测后的结论"留了下来）。
>
> 这不是笔误，是本项目在 `docs/05` 里反复批评的同一个模式：
> **一个看似合理的推断，被当成结论写进了文档。**
> 只是这次它落在**面试话术**里 —— 照着说，一句"你实测过吗"就会被打穿。
>
> 修法不是改一个字，而是**让形容词由数据算出来**（见 `compare.py` 的
> `loc_verdict`）—— 这样以后数字变了也不会再出现"文本和数据打架"。
>
> ⚠️ 顺带说明：`docs` 里凡是引用了 **代码行数 / 测试数 / 脚本数** 的地方
> 都会随代码演进过期。**改代码后要全文搜索这些数字** ——
> 这是本项目记录在案的一条维护约定（见 `docs/06`）。

**改了样本或记忆措辞之后**，一定要重跑第 2、3 步 ——
当前 `dim=256` / 阈值 0.32 下，**到下限只有 +0.027**、到上限 +0.035，
余量很薄，措辞一动就可能让"不命中"样本变命中
（`compare.py` 的循环覆盖率会掉，测试里的余量守卫也会报错）。

**看 `compare.py` 输出时的顺序**（前提不成立时结论无意义）：
```
① 循环覆盖     → 6/18 才有循环可测；0 就说明回边和 fallback 都没跑到
② 一致率       → 两版行为一样吗
③ 准确率       → 两版**对不对**（一致但都不对 = 等价性不成立）
```
**② 和 ③ 必须一起看**：只看一致率会被"两版一起错"骗过去（见上节）。

**改 `EMBED_DIM` 时不要只改那一处** —— 阈值和维度是绑定的，
必须按"改 dim → 跑 dim_sweep 看新空档 → 取新中点 → 重跑 compare + 测试"
的顺序走。详见 `shared.py` 里 `MIN_RECALL_SIMILARITY` 的注释。
（否则循环覆盖率会从 6/18 掉到 3/18。）

**改 `graph_agent.py` 的节点时**别把 `setup_tools()` 写回节点里 ——
组件必须靠 `config["configurable"]` 注入，否则耗时会重新混入重建开销，
而报告不会有任何异常（`test_组件在一次运行里只建一次` 会拦你）。
