## 〇、结论先行

**当前系统没有任何一处逻辑与"仓库内容变更"挂钩。**

现有的"更新 / 失效 / 清理"全部是**语义维度和时间维度**的，没有**代码状态维度**：

| 现有机制 | 触发条件 | 与仓库变更的关系 |
|---|---|---|
| 合并 `Writer.commit()` | 新记忆与旧记忆相似度 ≥ 0.92 | ✗ 无关（是去重，不是更新） |
| 冲突消解 `Resolver.resolve()` | 两条记忆**互相矛盾** | △ 间接（要先有人报新 issue） |
| 衰减 `Decayer.decay_all()` | 时间流逝（半衰期 90 天） | ✗ 无关（只看日历，不看 diff） |
| 污染纠正 `mark_wrong()` | **人工反馈** | ✗ 事后（人要自己先发现） |

**最根本的断点在数据模型层**：`MemoryRecord` 只有 `repo: str`（仓库名字符串），
没有 `commit_sha`、没有 `file_paths`、没有 `code_refs`。
所以从结构上就**不可能**回答"这条记忆是基于哪个版本的代码得出的"。

而项目自己已经把这个问题写进了评测 —— `eval/poison.py` 里 `PoisonType.STALE`
（曾经对、现在过时）的检测难度被标为**"最高"**，且实测暴露 4 次（其他类型都是 0 次）。
**我们承认了它最难查，然后就没再管它。**

## 一、现状盘点：现有的"更新 / 失效 / 清理"逻辑

### 1.1 更新：只有一条路径 —— 语义合并

`lifecycle.py :: Writer.commit()`（`merge_similarity = 0.92`）

```
幂等键命中 → skipped_duplicate
相似度 ≥0.92 → merged（_merge 策略：symptom 取更长、tags 取并集、actions 累加去重）
否则        → inserted
```

`_merge()` 写得不错（不是简单覆盖，人工反馈按权威性继承）。
**但它回答的是"同一件事是不是被记了两遍"，不是"旧记忆还成不成立"。**

一个具体反例：仓库把 `iteritems` 删了。
旧的「iteritems 在 2.0 移除但暂时可用」和新的「iteritems 已彻底删除」，
字面上都含 iteritems，相似度可能过 0.92 → **被合并成一条自相矛盾的记忆**，
而不是判定为"旧的失效了"。

> 这就是"合并"和"失效"被混为一谈的代价：**合并会让过时信息获得新的生命周期**。

### 1.2 失效：最接近的机制是冲突消解，但触发不了

`Resolver.detect_conflict()` 的判据：

```python
sim >= 0.75                        # 是同一个问题
且 (根因都存在且 Jaccard < 0.3      # 对根因判断不一致
    或 处置都存在且 Jaccard < 0.25)  # 处置方式不一致
```

**它需要一个前提：必须先产生一条内容相反的新记忆。**

现实路径是：仓库改了 → 有人踩坑 → 报了新 issue → Agent 处理 → 抽出新记忆 → 撞上旧记忆 → 才触发。
**前三步都不是我们能控制的。** 如果仓库改完一个月没人报 issue，
这条过时记忆会一直以满权重（decay_weight ≈ 1.0）参与召回。

### 1.3 清理：只有时间衰减，而且还没接上调用入口

`Decayer.decay_all()` 的权重公式：

```
weight = 时间衰减(0.5^(age/90)) × 有效性修正(0.5+0.5×use/access) × 权威性加成
         + 人工确认过的记忆保底 0.25
低于 archive_threshold(0.15) → archived=1（不参与向量召回，仍可精确查询）
```

两个问题：

① **公式里没有任何仓库相关项。** 仓库昨天被大改 → 昨天的记忆权重仍是 1.0；
   仓库一年没动 → 一年前的记忆降到 0.06 被归档。**时间和"过时"不是一回事。**

② **`decay_all()` 只在测试里被调用**（`tests/test_smoke.py:194/214`），
   主链路和任何定时入口都没接。
   这是项目自己在 P1-2 里批评过的"写好了但没人调" —— **衰减环节目前同样如此**。

### 1.4 还有哪些"看起来像但不是"的东西

| 东西 | 为什么不算 |
|---|---|
| `store.delete()` | 只有 HTTP 服务暴露了它（`service.py:174`），主链路无调用；且项目三处明确写了"删除是最差的状态表达方式" |
| `archived` 字段 | 是衰减的结果，不是失效的判定；且 `find_similar()` 也过滤 `archived=0`，归档后连合并都参与不了 |
| `pending_conflicts` | 是"两条记忆互相矛盾"的队列，**没有"记忆与仓库矛盾"这一类** |
| `read_code` 工具 | Agent 会读代码文件，但**读过的路径没有落到记忆上** —— trace 里只有 `memory_recalled` / `memory_used`，没有 `files_read` |

**最后一条是关键的可惜之处**：证据其实在主链路里流过（`ToolCall.tool_input["path"]`），
只是没人把它记下来。这是成本最低的一处改进。

## 二、为什么这件事值得做（不只是"补个功能"）

### 2.1 项目自己的实验已经给出了理由

`docs/06` P2-1 的污染注入实验实测：

- `STALE` 类污染**暴露 4 次**，其他四类都是 **0 次**
- 推测原因：STALE 的内容**更详细、更有说服力**，更容易被匹配上
- 结论原文：「写得越"像样"的污染，暴露面越大」

**也就是说：越像真的过时记忆，危害越大，而我们目前只能等人踩坑后反馈。**

### 2.2 现有纠正路径的代价已经被量化

实验测出：**纠正一条污染需要 2 次反馈，不是 1 次**
（第 1 次标记原污染 → 但它已派生出新记忆 → 第 2 次清理派生记忆才收敛）。

**这条链路的起点是"必须有人先发现它错了"。**
仓库变更检测要做的事，就是把这个"等人发现"换成"系统主动发现"——
它削掉的是**第一个反馈之前的那段暴露期**，而那恰恰是最长的。

### 2.3 面试价值

这是"记忆系统"这个卖点**自带的风险面**。
能讲清"我的记忆会自己跑偏，我知道它会在什么情况下跑偏，并且我有机制"
——比"我做了记忆"高一个量级。

## 三、方案

### 前置：所有方案都依赖的第一步 —— 给记忆打锚点

不管走哪条路，都需要先补三个字段（`models.py :: MemoryRecord`）：

```python
code_refs: list[str] = field(default_factory=list)  # ["pandas/io/parsers.py", "src/nightwatch/memory/store.py"]
base_rev: str = ""        # 当时的 commit sha；空 = 未知
validated_at: str = ""    # 上次做"前提校验"的时间
```

**锚点从哪来（三个来源，按可靠性排序）**：

1. **trace 里 `read_code` 的调用参数** —— 最可靠，是客观发生的证据，零 LLM 成本
   （见 §1.4，这是现成但被丢弃的数据）
2. **issue 的 `stack_trace`** —— 正则解析文件路径，覆盖率取决于 issue 质量
3. **LLM 抽取时多要一个 `code_refs` 字段** —— 覆盖纯文本型记忆，但会引入抽取噪声

> ⚠️ **必须遵守项目 B3 教训**：「上游少输出一个字段，下游一个模块整个失效」。
> 所以 `code_refs` **允许为空**，scanner 对空锚点的记忆必须**直接跳过**而不是崩掉或误判。
> 空锚点 = 不做判断，这是唯一正确的处理。

---

### 方案 A · 定时扫描式失效（Repo Anchor + StaleScanner）

**做什么**：新增 `memory/staleness.py :: StaleScanner`，定时（cron，每天一次）
拉取 `repo` 在两个版本间的变更，反查哪些记忆的锚点被碰了。

**分级判定（不是二值，这是设计要点）**：

| 级别 | 判据 | 处理动作 |
|---|---|---|
| **L3 锚点消失** | `code_refs` 里的文件被删除 / 重命名 | `archived=1` + `decay_weight *= 0.3` + 进 `pending_conflicts` 交人工 |
| **L2 锚点被改** | 文件出现在 `changed_files` 里 | `decay_weight *= 0.6`，保持可召回但排序靠后 |
| **L1 邻域被改** | 同目录/同模块其他文件被改 | 只记 `stale_score`，不动权重 |

**为什么分级**：STALE 污染的特征是"内容看起来完全合理"，
**单一阈值一定会误伤**。分级让"确定失效"和"可能失效"走不同的处理强度 ——
L3 直接下线（有人工兜底），L2 只降权（还能用，但排在后面）。

**优点**
- 改动面小：3 个字段 + 1 个模块，复用现成的 `decay_weight` 通道和 `pending_conflicts` 闸门
- 与项目"不信全自动"的调性一致：L3 仍然进人工队列
- 不需要改主链路，**不增加任何在线延迟**

**缺点**
- 覆盖不到没有锚点的记忆（纯流程/配置类）
- 需要 git 元数据接入：要么 `subprocess` 调 git CLI，要么 GitHub API
  （项目已有 `NW_GITHUB_TOKEN`，**GitHub API 更符合零依赖约定**）
- 定时扫描意味着**有延迟**（最长一个扫描周期）

**适用**：**首选**。性价比最高，且是其他方案的基础。

---

### 方案 B · 召回时前提校验（Lazy Re-validation）

**做什么**：在 `MemoryStore.recall()` 的 `_rank()` 之后加一道轻量校验：
对进入 top_k 的记忆，检查它 `code_refs` 里的符号在当前仓库是否还存在。
不存在 → 当场降权 + 标记 `stale_suspect`，**并写进 trace 供人工复核**。

**优点**
- **懒执行**：只对"真的要被用"的记忆付费，不做全库扫描
- 覆盖面比 A 宽 —— 可以用关键词去仓库搜，不依赖预先抽好的 `code_refs`
- 天然带 `validated_at` 缓存，同一条记忆不会反复校验

**缺点**
- **增加主链路延迟**（每次 recall 多一次 IO）—— 必须设超时（比如 200ms）和降级
- 校验逻辑本身是新假阳性来源：函数改名了但记忆仍然对（比如只是内部重构）
- 如果每条记忆都要验，就退化成全量校验，成本失控

**适用**：作为 A 的**补充**，做"召回到被采用之前"的最后一道闸。
**不要单独用**。

---

### 方案 C · 证据重放（Evidence Replay）

**做什么**：记忆里的 `actions` 已经存了当初的工具调用（含 `ok` / `error`）。
定期挑出**只读类**调用（`read_code` / `search_issues` / `search_docs`）重放一次。
当初 `ok=True` 的调用现在失败或结果变了 → 判定前提变了。

**优点**
- **不依赖 LLM、不依赖 git**，是"可执行的证据"，误判率最低
- 判定依据是客观失败，不是启发式猜测

**缺点**
- **覆盖面窄**：`actions` 里大量是 `apply_labels` / `post_comment` 这类**写操作，不可重放**。
  只有只读调用能重放，实际覆盖率可能不到 20%
- 重放有副作用风险，必须走现有 `Sandbox`（项目已有，可直接复用）
- 重放成本高：一条记忆平均 3~5 次调用，全库重放很快就不划算

**适用**：**只作为 A / B 的交叉验证**，不单独成方案。
它的价值在于"当 A 判定 L2 不确定时，用重放结果做二次确认"。

---

### 方案 D · 变更驱动（Change-driven Invalidation）

**做什么**：从"定时扫全库"改成"事件来了才动"。
订阅仓库 push / PR merge 事件 → 拿到 `changed_files` → 反查引用了这些文件的记忆。

**优点**
- **时效性好**：改完立刻知道，没有扫描周期延迟
- 粒度到文件，判定精度比定时扫描高
- **和现有资产天然衔接**：`tools/pr_review.py` 已经能解析 PR 的 `changed_files`
  （P2-3 的 PR 初审工具），同一份 diff 可以复用 ——
  **"这次改动会影响哪几条记忆"是 PR review 的自然延伸**

**缺点**
- 需要 webhook 或轮询基础设施（**这是本项目目前最缺的一块**）
- 大仓库一次 push 改 200 个文件 → 可能命中几百条记忆，需要限流和优先级排序
- 依赖 A 的 `code_refs` 字段（顺序上必须 A 先行）

**适用**：仓库变更频率中等、且已经有 PR 数据流的场景。
本项目的 `collect_prs.py` 已经在采真实 PR，接起来不算远。

---

### 方案 E · 语义记忆到期复审（SOP TTL）

**做什么**：给 `MemoryTier.SEMANTIC` 的记忆加 `valid_until`，
到期自动重新生成一条 `PendingPromotion` 进人工队列（状态标 `re-review`）。

**优点**
- **成本极低**：语义记忆条数少（几十条量级，不像情景记忆上千）
- 复用现成的 `pending_promotions` 表 + `review_promotion()` 审核流程，几乎不用写新代码
- **保护的是风险最大的那一层** —— 项目自己的判断是：
  「情景记忆错了只影响一次召回，语义记忆错了会污染所有后续同类任务」

**缺点**
- TTL 是**时间启发式，不是真的变更感知** —— 可能复审一堆根本没变的 SOP
- 不解决情景记忆的问题（量大，不能全走人工）

**适用**：**建议最先做**，因为它最便宜且保护的是风险最高的一层。

### 3.6 方案对比

| 方案 | 改动量 | 覆盖率 | 时效性 | 误判风险 | 是否依赖 A |
|---|---|---|---|---|---|
| **E · SOP TTL** | 极小（1 字段 + 复用审核表） | 低（仅语义层） | 差（到期才知道） | 低 | 否 |
| **A · 定时扫描** | 中（3 字段 + 1 模块） | 中（限有锚点的） | 中（一个周期） | 中（分级缓解） | — |
| **D · 变更驱动** | 大（+webhook 基础设施） | 中高 | **好** | 中 | **是** |
| **B · 召回校验** | 中（改主链路） | **高** | **好** | **高**（假阳性） | 否（但更好） |
| **C · 证据重放** | 中 | **低（<20%）** | 差 | **低** | 否 |

**性价比排序：E → A → B →（D）→（C）**

## 四、建议的落地顺序

```
第一步  E · SOP TTL              半天    最便宜，先保护风险最高的一层
第二步  补 code_refs 锚点         半天    ★ 从 trace 的 read_code 调用里取，零 LLM 成本
第三步  A · StaleScanner         1~2 天  主力方案，含 L1/L2/L3 分级
第四步  接上 decay_all() 的定时   半天    ★ 顺手修现有的"写了没接上"
第五步  B · 召回校验（可选）      1 天    只在 A 跑通、指标稳定之后再加
```

**第二步为什么值得单独做**：`read_code` 的调用路径已经在 `ToolCall.tool_input` 里了，
只是没落库。这是"零成本补齐证据"的机会 —— 但**只对之后新产生的记忆有效**，
历史记忆的锚点是空的（所以要允许空值，不能让 scanner 崩）。

## 五、怎么评测（这是本项目的强项，别浪费）

**复用 `eval/poison.py` 的 STALE 注入，做一个闭环回归：**

```
基  线：注入 STALE 污染 → 跑 N 个 issue → 记暴露次数（现测：4 次）
实验组：注入同样的 STALE 污染 → 模拟一次仓库变更（改掉它引用的文件）
        → 跑 scanner → 再跑同样的 N 个 issue → 记暴露次数
```

**目标**：暴露次数从 **4 → 0**，且**不需要任何人工反馈**。

**必须同时报的三个指标**（只报第一个会自欺）：

| 指标 | 含义 | 为什么必须 |
|---|---|---|
| `stale_detect_rate` | 真·过时记忆被标记的比例 | 主指标 |
| `false_invalidate_rate` | **没过时的被误标记的比例** | ★ 不报这个，把全库归档也能拿满分 |
| `feedback_needed` | 平均需要几次人工反馈才收敛 | 现测 2 次，目标是 0 次 |

> `false_invalidate_rate` 的必要性，和项目在判重里吃过的是同一个亏：
> 只看 recall 率，把阈值调到 0 也能"全召回"。
> **任何失效机制都必须同时报误伤率，否则它只是另一种形式的删除。**

## 六、诚实清单：这些做不到

1. **"语义过时"检测不了** —— 文件还在、函数还在、签名没变，但行为变了。
   这在 A/B/C/D 四个方案下**都是盲区**，只有运行时反馈能发现。
   **要明说这是天花板，不要包装成"我们解决了记忆过时"。**

2. **锚点抽取的覆盖率不会高** —— pandas 类项目里，多数 issue 不带堆栈、
   Agent 也不一定调 `read_code`。期望覆盖率给个诚实的估计：
   **乐观 40%~50%，保守 20%~30%**，需要实测标定（数字先留白，测完再填）。

3. **历史记忆无法补锚点** —— 只能靠重放或人工补，
   大规模补不现实。新机制**只对增量记忆生效**，这点要在文档里写清。

4. **git 接入会碰到"零第三方依赖"约定** ——
   用 `subprocess` 调 git CLI 不引入 pip 包，但要求环境有 git；
   用 GitHub API 则有 5000 次/小时的限制。**大仓库要设计增量拉取**。

5. **decay_all() 目前没接上入口** —— 这不是新功能的问题，是**现存缺陷**。
   在谈"变更驱动失效"之前，先把已有的衰减跑起来，否则新机制接上去也是空转。
