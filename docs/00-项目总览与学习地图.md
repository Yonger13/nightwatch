# 00 · 项目总览与学习地图

> 这篇文档回答三个问题：这个项目是什么、该按什么顺序读代码、每个模块能学到什么。

---

## 一、这个项目在做什么

一个 **Agent**，处理开源项目的 issue 队列：读一个新 issue，检索历史、
判断是否重复、给出分类和处理建议，交给维护者决策。

但这不是重点。**重点是它把三个真实的工程难题做成了可演示、可量化的东西：**

| 难题 | 为什么难 | 本项目的解法 |
|---|---|---|
| **Agent 会忘事** | 跑久了忘记最初的约束；跨会话不记得处理过什么 | 三层记忆 + 任务状态卡每轮重注入 |
| **Agent 会卡住** | 调三个工具开始死循环，合法的调用里烧完 token | 四层可靠性：重试 / 熔断 / 循环检测 / 带证据的兜底 |
| **Agent 会污染自己** | 一次误判写进记忆，之后反复复用这个错误 | 写入评分 + 冲突进 pending 队列交人工 |

**为什么选这个场景**：issue 分流是"高频 + 半结构化输入 + 输出可判定 +
有真实用户 + 有天然 ground truth（维护者的标签和关闭动作）"——
这五个条件同时满足的场景很少。

## 二、代码阅读顺序

按这个顺序读，每一步都能独立理解，不依赖后面的模块。

### 第一站：先看全景（30 分钟）

```
src/nightwatch/models.py        # 系统里有哪些东西
src/nightwatch/config.py        # 所有可调的设计决策
```

**读 `models.py` 时关注**：字段设计。每个字段都在回答"什么信息未来会有用"。
特别看三个标记了 ★ 的字段（`actions` / `human_verdict` / `access_count`）——
它们体现了这个项目和其他 RAG 项目的区别。

**读 `config.py` 时关注**：为什么参数要集中在一个文件。因为这些参数本身就是
设计决策（比如"给记忆分配多少上下文预算"决定了 Agent 在多大程度上记得住过去），
不是实现细节。

### 第二站：核心 —— 记忆（2 小时）

```
src/nightwatch/memory/lifecycle.py     ★ 最重要
src/nightwatch/memory/store.py
```

**这是整个项目的技术纵深所在。** 重点理解记忆的六个环节：

```
① 抽取 Extract      从轨迹里提炼候选
② 评分 Score        判断值不值得长期保留
③ 写入 Write        过阈值才落库，保证幂等
④ 合并 Consolidate  同一件事被记了两遍 → 合并
⑤ 消解 Resolve      两条记忆矛盾 → 三级裁决 → pending 队列
⑥ 衰减 Decay        时间让记忆降权，但不是删掉
```

配合阅读：[`02-记忆系统设计.md`](02-记忆系统设计.md)

### 第三站：上下文与可靠性（1.5 小时）

```
src/nightwatch/context/budget.py       # 上下文满了怎么办
src/nightwatch/loop/reliability.py     # Agent 失控怎么办
```

这两个模块回答的是同一类问题：**怎么让系统在资源受限/出现异常时体面地降级。**

**读 `budget.py` 时关注**：为什么工具有优先被卸载，而 system/task 不可压缩。
**读 `reliability.py` 时关注**：四层为什么是递进的 —— 每一层堵上一层的漏。

配合阅读：[`03-可靠性与上下文预算.md`](03-可靠性与上下文预算.md)

### 第四站：主循环（1 小时）

```
src/nightwatch/loop/react.py           ★ 把所有东西串起来
```

**读的时候关注**：
- 记忆预取为什么在**循环之前**，而不是当成一个工具调用
- 任务状态卡为什么每轮重建
- 工具调用被可靠性机制阻止时，为什么把"被阻止"作为观察结果告诉模型，
  而不是直接中断

### 第五站：工具与沙箱（40 分钟）

```
src/nightwatch/tools/registry.py
```

**读的时候关注**：工具 description 的写法（含用途 + 边界 + 反例）、
只读/写的分级、幂等账本、回滚。

### 第六站：评测（1 小时）

```
src/nightwatch/eval/metrics.py
src/nightwatch/eval/dataset.py
```

配合阅读：[`04-评测设计.md`](04-评测设计.md)

### 第七站（可选）：跑起来看

```bash
python scripts/run_demo.py       # 三段演示
python scripts/run_eval.py       # 完整评测
python scripts/run_tests.py      # 96 个用例

# P1/P2 新增能力的演示
python scripts/demo_service_split.py   # 记忆服务拆分 + 降级
python scripts/demo_semantic.py        # 语义记忆层 + 人工闸门
python scripts/demo_a2a.py             # A2A 委托 + 跨 Agent 共享记忆
python scripts/demo_pr_review.py       # PR diff 初审
```

### 第八站：★ 必读

```
docs/05-开发实录-真实缺陷复盘.md   30 个案例，含完整时间线与证据（深挖用）
docs/07-失败案例集.md              16 个精选，按"面试追问维度"分组（面试用）
docs/09-真实闭环.md                前瞻验证 + 持续运行（"作品"和"系统"的分界）
docs/10-记忆失效与仓库变更.md        仓库变更 → 过时记忆：调研 + 方案设计
docs/11-记忆时效性实现.md            上者的实现与验证
docs/12-Actions挂载指南.md         让每日任务自己跑起来
```

**这两篇比前面所有设计文档都重要。** 设计文档展示的是意图，
这两篇展示的是现实 —— 那些**"不会报错、只会静默出错"**的地方。

**两份的分工**：
- `docs/05` → 完整过程（1700 行），适合面试前深挖某几个案例
- `docs/07` → 精简版（16 个案例，每个 60 秒能讲完），按面试追问维度重组

### 第九站（进阶）：P1/P2 的架构深度

P0 做完后项目"能用"了。P1/P2 是让它**有深度**的部分：

| 项 | 一句话价值 | 代码位置 |
|---|---|---|
| P1-1 服务拆分 | **有状态的东西不该和计算绑在一起**；降级是架构保证不是"每处记得写" | `memory/service.py` `memory/remote.py` |
| P1-2 语义记忆层 | 三层记忆的**风险量级不同** → 语义层必须有人工闸门 | `memory/lifecycle.py` |
| P1-3 组合实验 | **交互效应**只能靠"让因子同时变化"发现 | `eval/doe.py` |
| P2-1 记忆污染 | 有了记忆就出现新失败模式：**错误在系统内部自我强化** | `eval/poison.py` |
| P2-2 A2A | 协议层遵守 A2A，**记忆共享是应用层扩展**（边界要讲清） | `a2a/` |
| P2-3 PR 初审 | CodeAgent 最现实的落地：**把 review 的第一遍粗筛自动化** | `tools/pr_review.py` |

## 三、每个模块能学到什么

| 模块 | 可迁移的知识 | 对应的面试问题 |
|---|---|---|
| `config.py` | 把设计决策集中管理；任务-模型匹配 | "你怎么控成本" |

## 四、三个刻意的"不做"

理解一个项目，也要理解它**为什么不做某些事**。

### 不用 Agent 框架（LangGraph / CrewAI）

**理由**：框架会把循环藏起来。而循环是 Agent 的心脏 ——
面试问"一次任务经历几次模型调用、每轮传什么进去"时，套框架的人答不上来。

**但读它的设计**：`memory/lifecycle.py` 里的状态流转参考了 LangGraph 的
StateGraph 思路，持久化参考了它的 checkpointer。这个"读了但不用"的说法，
比"我用了 LangGraph"有说服力得多。

### 不引入独立向量库

**理由**：情景记忆的检索天然是"结构化过滤 + 向量排序"的混合查询 ——
用一个 Postgres（或本项目的 SQLite）就能搞定，不用维护两套存储。

代码里给出了 pgvector 的迁移 SQL，说明这个取舍是想过的，不是偷懒。

### 不填任何假数字

**理由**：面试官一定会追问实验设置（样本量、对照组、跑几次、置信区间）。
编的数字撑不过三个问题，而答不上来的后果比数字难看严重得多。

所以项目里所有指标都是"要测什么 + 怎么测才公平"，具体数字必须自己跑出来。

## 五、这个项目和其他 Agent 项目的区别

| 维度 | 常见学生项目 | 本项目 |
|---|---|---|
| 状态 | 无状态，答完即忘 | 有状态，跨会话累积 |
| 记忆 | 单一向量库 | 三层 + 六环节生命周期 |
| 执行 | 单轮或两三轮检索 | 多步骤编排，能连续跑十几轮 |
| 副作用 | 只读 | 有写回 + 幂等 + 可回滚 |
| 评估 | 看几个例子 | 分层指标 + 对照实验 + 阈值标定 |
| 可靠性 | try/except | 四层机制 + 带证据的降级 |
| 可观测 | 打印 log | 全链路 trace + 占用分布 |
| 边界 | 声称全能 | 明确标注每题的限制与已知缺陷 |

最后一行是最重要的区别：**这个项目会告诉你它哪里不够好。**
（见 `README.md` 的"当前状态"和 `05-开发实录`。）
