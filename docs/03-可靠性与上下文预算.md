# 03 · 可靠性与上下文预算

> 这两个模块回答同一类问题：**怎么让系统在资源受限 / 出现异常时体面地降级。**

---

## 第一部分 · 四层可靠性

### 一条面试原题

> 「**Agent 调了三个工具开始死循环，你的异常处理写在哪？**」
> —— 某大厂 Agent 提前批一面（这道题挂了人）

**这道题为什么能挂人？** 因为它考的不是"你知道不知道 try/except"，
而是"你**有没有在真实系统里见过 Agent 失控**"。

没见过的人的答案通常是"加 try/except 捕获异常" —— 但这个答案解决不了问题，
因为**死循环里的每一次调用都是成功的**。没有异常可以捕获，
Agent 就是在一个合法的循环里反复干同一件没用的事，直到把 token 烧完。

### 四层是递进的

```
① 重试 Retry          单次调用失败（超时、限流）
   漏网：调用都成功，但整体在做无用功
      ↓
② 熔断 Circuit        某个工具反复失败（它可能已经挂了，别再浪费时间）
   漏网：工具没失败，但 Agent 在原地打转
      ↓
③ 循环检测 Loop       检测到重复的 (工具, 参数) 组合，主动中断
   漏网：没有完全重复，但是在缓慢地兜圈子
      ↓
④ 轮数上限 + 兜底      强制退出，并且带着已收集的证据转人工
```

### ① 重试：区分"可重试"和"不可重试"

这是最多人漏掉的一点。**不加区分的重试是有害的**：

| 错误类型 | 该重试吗 | 理由 |
|---|---|---|
| 超时 / 限流 / 连接失败 | ✓ | 可能是暂时的 |
| 参数错误 / 权限不足 | ✗ | 重试一万次结果一样 |

后者如果也重试，会让一个本该 100ms 返回的错误拖到 10 秒，
而且占着一个并发槽位 —— 在服务化场景里这是实打实的资源浪费。

```python
self.retryable_kinds = ("timeout", "rate_limit", "connection")
```

**加分项：在生产环境还应该加 jitter（随机抖动）。**

```python
delay = base * 2**attempt * (0.5 + random() * 0.5)
```

原因：如果 1000 个客户端同时被限流，它们会在同一时刻一起重试，
形成"惊群"，把服务再打挂一次。抖动把重试时间打散。

**这个点面试说出来能体现你有分布式系统的意识。**

### ② 熔断：Agent 的工具层就是微服务依赖图

重试解决"这一次失败"，熔断解决"这个工具整体已经不能用了"。

场景：某个工具连续 3 次超时，可能它依赖的外部服务挂了。
这时正确的做法不是继续重试（每次都要等超时），
而是**把它暂时摘掉**，让 Agent 用别的工具或走兜底。

**这个类比很有价值**：

> Agent 的工具层本质上就是一个微服务依赖图，
> 所以后端那套可靠性模式（重试、熔断、降级、隔离）可以直接迁移过来。

面试时说出这个类比，说明你理解 **Agent 工程的本质是分布式系统**。

### ③ 循环检测：判据的选择是关键

**直觉上会想"连续调两次同一个工具就算循环"。这是错的。**

正常业务里连续调同一个工具非常常见 —— 比如先用关键词 A 搜一遍，
觉得不对再用关键词 B 搜一遍。

**真正的循环特征是参数完全相同：**

```
search_issues(query="timeout")
search_issues(query="timeout")
search_issues(query="timeout")      ← 这才是卡住了
```

所以判据是归一化后的 (工具名, 参数) 三元组完全一致。

**归一化很重要**，因为同一次调用可能写成不同形式：

```python
{"query": "超时", "top_k": 5}
{"top_k": 5, "query": "超时"}       # 键顺序不同
{"query": "超时 ", "top_k": 5}      # 多了空格
```

这些在语义上完全是同一次调用，必须先规范化再比对。

```python
@staticmethod
def _signature(tool_name, tool_input):
    normalized = json.dumps(tool_input, sort_keys=True, ensure_ascii=False)
    normalized = "".join(normalized.split()).lower()   # 去空白 + 统一大小写
    return f"{tool_name}::{normalized}"
```

**下一个问题：误判怎么办？**

会产生误判。正常业务里也可能出现"参数一样但确实需要再调一次"
（比如查一个会变化的状态，第一次和第二次结果不同）。

处理方式**不是"想办法完全避免误判"**，而是：

1. 要求连续 N 次（默认 3）才判循环 —— 单次重复不触发
2. **把误判率记录下来，作为可观测指标**

第 2 点是态度问题：**承认检测器不完美，但要能量化它的不完美。**
这比"我的检测很准"可信得多。

### ④ 兜底：必须是"有产出的失败"

这是最容易被忽略、但业务上最重要的一点。

```
差的兜底：raise TimeoutError("超过最大轮数")
          → 上游收到异常，等于这次白干了，人也无从接手

好的兜底：return {"status": "unfinished",
                   "reason": "达到 20 轮上限",
                   "evidence": {...已查到的所有信息...},
                   "suggestion": "建议人工介入"}
          → 人拿着这些证据可以接着往下查
```

> **前者是技术的失败，后者是技术的降级。**
> 这两者在生产环境里差别巨大。

实现上，`evidence` 字段是核心：

```python
evidence = {
    "steps_executed": step,
    "tools_called": [...],          # 调过哪些工具、成功没有
    "partial_findings": [...],      # 已经获得的结论
    "circuit_open": [...],          # 哪些工具被熔断了
}
```

### 一个重要的业务区分：转人工不是失败

三种"看起来都是失败"的情况，实际含义完全不同：

| 类型 | 含义 | 是失败吗 |
|---|---|---|
| **ESCALATED**（转人工） | Agent 明确说"我判断不了，需要人来看" | **不是**，这是正确的自我认知 |
| **MISDIAGNOSED**（误诊） | 给出了明确分类，但和维护者判断不一致 | 是，因为它会误导后续处理 |
| **UNFINISHED**（未完成） | 达到轮数上限还没收敛 | 是（但是有产出的失败） |

**把 ① 和 ② 混在一起统计是错的**，会导致：

> 一个"凡事先说不知道"的保守系统，看起来和"总答错"的系统一样差 ——
> 而实际上前者可用得多（它只是效率低，不会造成错误决策）。

所以判定顺序是：**先看它有没有给出实质判断，再看判断对不对。**

```python
pred_set.discard("triage")          # "needs-triage" 等价于"没有实质分类"
if not pred_set:
    return Outcome.ESCALATED        # 没给实质判断 → 转人工，不是失败
if confidence < 0.3:
    return Outcome.ESCALATED
# 有 ground truth 时才判误诊
if issue.gold_labels and not (gold_set & pred_set):
    outcome = Outcome.MISDIAGNOSED
```

**这个区分修复了实测中 87.5% 的"误诊率"** —— 它其实是虚高的，
因为大量样本只是"诚实地说了不知道"。

## 第二部分 · 上下文预算

### 问题：窗口是硬的，任务是开放长度的

大模型的上下文窗口是**硬容量约束**，而 Agent 的任务是**开放长度**的
（一个问题可能调 5 次工具解决，也可能调 40 次）。

这两件事放在一起，必然导致"跑着跑着上下文满了"。

多数项目的处理很粗暴：

```python
if len(history) > N:
    history = history[-N:]        # 滑窗
```

**这叫滑窗，不是压缩。** 它会静默地丢掉信息，然后 Agent 开始失忆、
重复调用同一个工具、忘记最初的约束。

### 核心认知：各部分价值不对等

| 桶 | 内容 | 可压缩吗 | 超预算时 |
|---|---|---|---|
| system | 角色定义、工具 schema | ✗ | **不可动** |
| task | 当前目标、硬约束 | ✗ | **不可动** |
| memory | 召回的旧经验 | ✓ | 按相关性截断 |
| tools | 工具返回结果 | ✓ | **优先卸载** |
| history | 思考-行动-观察轨迹 | ✓ | 其次压缩 |

**两个关键的顺序决策：**

**为什么工具结果排在最前面被驱逐？**
因为它**体积最大，且最容易"真扔了也不怕"** —— 卸载不是删除，
是落盘 + 留一个指针，需要细节时能读回来。

**为什么 history 排在 tools 后面？**
因为 history 里有"我做过什么"的因果链。压掉它，
Agent 会重复调用同一个工具（因为它不记得已经调过了）。

### 卸载：不是删除，是留一个能回读的指针

```python
if estimate_tokens(text) > TOOL_RESULT_OFFLOAD_THRESHOLD:
    ref = self._offload(tool_name, text)
    preview = (f"[{tool_name}] 结果过大已卸载\n"
               f"摘要: {head}\n"
               f"文件指针: {ref}\n"        # ★ 单独一行，不要包在括号里
               + (f"尾部: {tail}\n" if tail else ""))
```

**两个细节：**

1. **摘要是"头 + 尾"，不是只给头。**
   因为工具输出的尾部经常有结论/统计，头部是原始数据。

2. **文件指针必须单独占一行。**
   最初写的是 `...(见 offload://xxx.txt)`，结果提取指针的正则会
   把右括号一起吃进去（因为 `)` 不是空白字符），导致读回时路径错误。
   而这种错误是**静默的** —— 读取失败返回空字符串，不抛异常。

   **教训：机器要解析的字段，用独立的、边界明确的格式。**
   不要为了排版好看而把它塞进句子里。

### 压缩：压中间，但真正的解法不在这里

压缩策略保守地保留"头（最初目标）+ 尾（刚发生的事）"，
把中间压成一行摘要。

为什么不压头和尾？因为：

- **头**：最初的目标和约束
- **尾**：刚刚发生的事
- **中**：被"挤到中部"的那部分，也正是**注意力最弱的地方**

这解释了一个现象：

> **为什么 Agent 跑久了会忘记最初的指令？**
> 不是模型记性差，是初始指令在上下文里被挤到中部了。

（业界观察到的现象：初始指令会随着上下文堆积逐渐漂移到中部，
而注意力机制在中部区域最弱。）

**所以真正的解法不是"压缩时小心"，而是第二层兜底：**

### ★ 长程一致性的核心机制：任务状态卡

把"当前目标、硬约束、已确认事实"做成一个**结构化的卡**，
每轮循环开始时重新注入：

```python
state_card = {
    "目标": "为该 issue 给出分类建议",
    "硬约束": ["判重优先于分类", "不得编造根因", "每条结论必须给出引用"],
    "当前 issue": {"编号": ..., "标题": ..., "报错堆栈": ...},
    "已完成步骤": [...],
}
```

**它放在 task 桶里，不参与压缩。** 所以即使 history 被压得只剩骨架，
约束还在 —— 因为约束不在 history 里，在 task 里。

**还有一个细节值得注意**：堆栈必须放进状态卡。

踩坑记录：如果堆栈只存在于工具返回里，那么当检索到多条历史 issue 时，
上下文里会同时出现**好几个不同 issue 的堆栈**。
此时任何"从上下文里找异常类型"的逻辑都会抓错。

实测表现：一个内容只有"用不了"的 issue，因为上下文里有别的 issue 的
堆栈（PermissionError），被误判成了权限问题。

**教训**：

> **"当前任务的关键事实"必须放在一个不会被混淆的位置**，
> 而不是散落在工具返回里和别人的信息混在一起。
> 这就是状态卡存在的意义 —— 它是唯一的、权威的、无歧义的。

### ★ 实测验证：状态卡到底有没有用

上面说的都是"设计意图"。要证明它真的有用，需要对照实验
（`scripts/run_longhorizon.py`）。

**为什么必须三组而不是两组** —— 这是踩坑换来的：

第一版只有 A/B 两组，在 Mock 上效果很好（差 66.67%），
但换到真实模型上几乎测不出差异。根因是：**`SYSTEM_PROMPT` 里本来就有一份约束**
（"判断准则"5 条），而 system 桶不可压缩 —— 所以对照组不是"没有约束"，
只是"少了一份每轮重申的强调"。

所以加了 C 组，构成真正的基线：

| 组 | system prompt | 任务状态卡 | 说明 |
|---|---|---|---|
| **A** | ✅ 有约束 | ✅ 每轮重注入 | **完整设计（生产用这个）** |
| **B** | ✅ 有约束 | ❌ 只在开头说一次 | 分离出状态卡的贡献 |
| **C** | ❌ 无约束 | ❌ | 真的没有任何保护 |

这样就能做**逐层贡献分解**：`C→B` = system prompt 的贡献，`B→A` = 状态卡的增量。

**真实模型结果**（每格 2 次取中位数）：

```
      轮数     A 完整设计     B 仅system     C 无保护
       0       100.00%      100.00%       66.67%
      30       100.00%      100.00%       66.67%
      60       100.00%       66.67%       33.33%
     100       100.00%       83.33%       66.67%

  趋势：  A 稳定(+0%)   B 下降(-16.67%)   C 稳定在 66.67%
```

**逐层贡献（100 轮时）**：`C→B +16.67%`，`B→A +16.67%`，合计 +33.33%。

**两个反直觉的发现**：

**① C 组不是在"违反约束"，而是根本完不成任务。**

看它的过程指标：**步数恒为 20（等于轮数上限）、引用 0 条、置信度 0.00**。
它跑满 20 轮在空转 —— 这比"给出错误的自信答案"更彻底地失败。

→ 说明 system prompt 里的约束不只是"提高遵从度"，
而是**让任务可完成的基础**。

**② 压力下才显出差异。**

0/30 轮（无驱逐）时 A 和 B 都是 100%，**状态卡没有增量价值**；
60/100 轮（触发驱逐 17/57 次）后 B 开始波动，A 保持 100%。

→ 这恰好符合设计假设：**状态卡对抗的是"长上下文导致的信息丢失"**，
没有信息丢失时它确实是多余的。

**证据链的干净程度**：三组的累计驱逐次数完全相同（17 / 57），
所以差异只可能来自"约束放在哪、有几份"，而不是"承受的压力不同"。

### Mock 与真实模型的对比（重要）

同一套脚本、同一个场景，两种模型的结果差很多：

| 组 | Mock @100 轮 | 真实模型 @100 轮 |
|---|---|---|
| A（完整设计） | 100% | 100% |
| B（无状态卡） | **33.33%** | **83.33%** |
| C（无保护） | 33.33% | 66.67% |

**Mock 高估了状态卡的价值**：它测出 B→A 差 66.67%，真实只有 16.67%。

原因：Mock 的 `has_constraint` 是字符串匹配，只认状态卡里那两个精确字符串，
所以状态卡一被驱逐它就"全盘漂移"；
而真实模型能读懂 system prompt 里的完整准则，即使状态卡没了也还记得要给出依据。

> **结论：Mock 的漂移是"全有全无"（开关式），真实模型的漂移是"渐变的、部分的"。**
>
> 所以 —— **Mock 能验证机制，不能验证效果；而且真实数据可能推翻 Mock 的结论。**
> 如果只跑 Mock 就宣称"状态卡带来 66.67% 提升"，这个数字在面试里站不住。

### 这个实验的边界（必须一起说）

它证明的是：

> **约束的可见性（有几份、放在哪、会不会被丢掉）决定了行为。**

它**不能**证明：

> 真实模型在任意场景下的漂移率。

因为：每格样本量只有 2~3 次，波动较大；任务类型单一（issue 分流）；
判定是规则化近似（只查"有没有"，不查"好不好"）。

**这个区分必须写进报告。** 一个实验的边界和它的结论一样重要 ——
面试时如果你能主动说出"这个实验能证明什么、不能证明什么"，
比报出一个漂亮的数字有说服力得多。

### 实验有效性检查：一个不能省的步骤

第一次跑这个实验时，所有组的遵守率都是 100%，看起来像"状态卡没用"。

但真正的原因是：**上下文压力根本没形成** ——
驱逐次数是 0，约束从未被判过"死刑"。

如果当时直接下结论"两组没差异"，那就是**用一个无效实验得出一个错误结论**。

所以脚本里加了一道前置检查：

```python
if total_evicted == 0 and total_compressed == 0:
    print("本次实验的结论不予采信 —— 上下文压力没有真正形成")
    print("怎么修：① 加大 --paddings　② 减小 --window")
```

**任何对照实验都该有这一步**：

```
先确认：处理组确实被处理了
再看：  效果有没有差异
```

如果第一步没过，第二步的结论**无论是什么都不能采信** ——
包括"两组没差异"这个看起来最保守的结论。

而且失败信息必须包含**下一步怎么做**，不能只说"实验失败"。

### 压缩丢了信息怎么发现

三层兜底：

1. **压缩时保留指针**（不真删，能回读）
2. **关键信息不参与压缩**（任务目标、硬约束抽成结构化状态卡）
3. **压缩过程可观测**

第 3 点是最容易被忽略的。每轮记录"压掉了什么、从多少 token 压到多少"：

```python
report.compressed.append(f"{name}:{before}→{b.tokens()}")
```

没有这个记录，压缩就是黑盒 —— 出了问题你无法定位到是哪次压缩丢了东西。

### Token 估算：为什么不引入 tokenizer

```python
def estimate_tokens(text: str) -> int:
    non_ascii = sum(1 for ch in text if ord(ch) > 127)
    ascii_chars = len(text) - non_ascii
    return int(non_ascii * 1.0 + ascii_chars / 4.0) + 1
```

因为这只是**调度用的相对量**，不需要精确。误差 20% 对"该不该卸载"的判断
几乎没有影响 —— 因为阈值本身就有缓冲（85% 触发，留 15% 余量）。

引入一个 tokenizer 依赖的代价（包体积、模型适配、版本问题）
大于它带来的精度收益。

**这是很典型的工程取舍：先问"我到底需要多准"，再决定要不要引入依赖。**

## 第三部分 · 面试速查

| Agent 死循环怎么处理 | 四层递进 + **判据是参数相同不是工具名相同** + 误判率要记录 |
| 上下文超了怎么压 | 分桶配额 → 驱逐顺序（tools 先）→ 卸载留指针 → 状态卡不参与压缩 |
| 压缩丢信息怎么办 | 三层兜底；重点是**可观测**（记录每次压缩前后的占用） |
| 兜底和失败的区别 | 兜底带 evidence，人能接着做；失败等于白干 |
| 转人工算失败吗 | **不算**，要单独统计（否则保守系统和错误系统看起来一样差） |
| 长程一致性怎么保证 | 状态卡每轮重注入 + 压测（5 轮 vs 50 轮的约束保持率） |
