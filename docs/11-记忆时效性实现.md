# 11 · 记忆时效性：两条信号线（实现）

> 补上项目原来**完全缺失**的一类信号通道：**判断"哪条记忆过时了"**。
>
> **两条互补的信号线**：
>
> ```
> 结构信号（memory/stale.py）    code_refs ∩ changed_files  →  文件被改了
> 语义信号（memory/feedback.py） 用了它之后判断错了          →  结果不对
> ```
>
> 前者**快、准、但覆盖窄**（只抓"文件路径变了"）；
> 后者**覆盖广但需要积累**（能抓"API 还在但语义变了"这类）。
> 两者**共用同一个待复核队列** —— 人看到的是一个队列，不关心来源。

> **姊妹文档**：[](10-记忆失效与仓库变更.md) ——
> 那份是**现状调研与方案设计**（五个看起来像、其实不是的机制、分层方案、红线论证）。
> 本文档是它的**实现与验证**。两份配合看：
> 先看 10 理解为什么，再看 11 看怎么做、做到了什么程度。

## 一、问题：一个从未被处理的失效模式

### 1.1 现状：记忆六环节全部是"内容闭环"

| 环节 | 处理什么关系 | **为什么处理不了"仓库变更导致的过时"** |
|---|---|---|
| ④ 合并（相似度 > 0.92） | 记忆之间的**重复** | 新旧记忆描述口径不同时（重构后换了说法）相似度不够，两条并存，**旧的照样被召回** |
| ⑤ 消解（冲突检测） | 记忆之间的**矛盾** | 这是**被动撞车**模型：需要两条记忆恰好在同一事实上给出不相容结论。而重构后的旧记忆**内容依然自洽**（"iteritems 可用"在写下时是对的），不会主动触发冲突 |
| ⑥ 衰减（半衰期 90 天） | 记忆与**时间**的关系 | 用**时间代理环境变化**，两个方向都错：<br>① 旧但对（`docs/02` B6：被确认的经验 400 天后权重 0.03 被归档）<br>② 新但已失效（昨天的记忆今天失效，权重仍接近 1.0） |
| 软纠正（`poison.mark_wrong`） | 记忆与**人工反馈**的关系 | 手段现成，但**触发全靠人点名** |
| 人工闸门（`PendingPromotion`） | 记忆晋升的审核 | 闸门在，但**没有针对过时记忆的入队条件** |

**结论**：记忆系统对外部世界（代码变更）**没有任何感知通道**。
这不是"漏了一个 if"，而是缺了一整类信号。

### 1.2 这个风险已经被项目自己证明过

`eval/poison.py` 的 **STALE 类型污染**（P2-1 实验）：

```
定义：  "曾经对、现在过时"
检测难度：**最高** —— "内容完全合理，只有知道版本变更才能发现"
实测：  暴露次数 4 次 vs 其他类型全部 0 次
纠正成本：需 2 次反馈（派生记忆独立存在，会继续误导）
```

**项目做了"证明它难"，但没做"自动检测"。** 本文档是补上后半截。

**还有一个 bug 级发现**（本次调研中确认）：

```
Decayer.decay_all() 在 src/ 和 scripts/ 里**零调用点**
grep 全库：只在 tests/test_smoke.py 里被调用 2 次
```

**精心设计的衰减公式在真实运行中从未执行过。** 这是"写好了没人调"的第二例
（第一例是 P1-2 之前的 `SemanticPromoter`）。

## 二、设计

### 2.1 ★★ 红线：标记可以自动，生效必须过闸门

**这是整个模块最重要的设计约束**，来自一个必须讲清楚的区别：

```
「变更波及」  ≠  「结论失效」
```

一个文件被改了，不代表引用了它的记忆就错了：

| 变更类型 | 记忆是否失效 |
|---|---|
| 改了注释、日志文案、不相关的函数 | **完全有效** |
| 重命名了被引用的类 / 改了下游依赖 | **可能失效** |
| **这两件事从"文件级"的变更信息里根本区分不出来** | ← 关键 |

所以：

```
检测可以自动   `code_refs ∩ changed_files` 是精确的集合运算，零误判
判断必须人工   "这个改动会不会让那条结论不再成立"需要理解语义
```

**如果自动化这一步**（按"文件被改过"就降权）—— 会重蹈 `docs/02` B6 的覆辙：
**那次是因为"时间"误伤了被确认的经验，这次如果因为"文件变更"犯同样的错，就白踩了。**

### 2.2 三阶段职责划分

```
① 检测（自动）   detect()   —— 谁被波及了？
                             精确集合运算，零误判、零成本、可复现
② 入队（自动）   mark()     —— 推进待复核队列
                             **完全不改变记忆本身**
③ 裁决（人工）   review()   —— 人确认后才降权 + 归档
```

**关键：② 和 ③ 之间，记忆完全不受影响** —— 它照常被召回、照常参与判断。
**队列只是"待办清单"，不是"已生效的惩罚"。**

（这个两阶段结构和 P1-2 的 `PendingPromotion` **完全同构** ——
连"标记自动、生效人工"这个模式都是复用的，不是新发明。）

### 2.3 两条信号线：互补而非替代

```
结构信号   code_refs ∩ changed_files
           ├─ 快、准（精确集合运算，零误判）、零成本
           └─ 但**只能抓"结构性过时"** —— 文件被改/被重构/路径变了

语义信号   "这条记忆被用了，但那次判断错了"
           ├─ **唯一不依赖"知道代码改了什么"**的信号
           ├─ 能抓"API 还在、签名没变、但语义变了"（如 dropna 默认行为改了）
           └─ 但需要**积累**，且有噪声（错误可能来自模型自己）
```

**为什么要两条**：它们抓的是**不同的失效模式**，交集不大。

| 失效场景 | 结构信号 | 语义信号 |
|---|---|---|
| 被引用的类被重命名 | ✅ 命中 | ⏳ 要等出错 |
| 模块被拆分重构 | ✅ 命中 | ⏳ |
| API 签名未变但**语义变了** | ❌ **完全不命中** | ✅ 命中 |
| 下游依赖升级导致结果变化 | ❌ | ✅ 命中 |
| 模型自己判断失误 | ❌（不关记忆的事） | ⚠️ **会误伤**（所以需要统计去噪） |

**★ 两者共用同一个待复核队列**（`pending_stale_reviews`），只是 `trigger` 不同：

```
trigger='repo_change'       来自 stale.py（结构信号）
trigger='feedback_misuse'   来自 feedback.py（语义信号）
```

**这是刻意的**：审核员不该关心"这条是怎么被发现的"，
只该关心"它是不是真的过时了"。**来源是系统内部的事，不该外泄成人的认知负担。**

### 2.4 为什么用"文件路径交集"而不是"让模型判断这条记忆是否过时"

因为**这件事不需要智能，需要的是准确**：

```
code_refs ∩ changed_files  →  零误判、零漏判、零成本、可复现

让模型判断"这个 diff 会不会让那条记忆失效"：
  · 要遍历每条记忆 × 每个 diff（成本高）
  · 判断结果有随机性（不可复现）
  · **而且它仍然只是"嫌疑"** —— 最终还是要人确认
```

**既然都要人确认，那前面的环节就别用模型了** ——
用最便宜、最准的方法把候选缩到几十条，才是把人的时间用在刀刃上。

（同 `tools/pr_review.py` 的思路：**结构风险筛查用规则，语义判断交给人**。）

## 三、实现

### 3.1 地基（方案 0）：给记忆绑定代码状态

**这是前提条件 —— 不做这个，后面全是空中楼阁。**

改动前 `MemoryRecord` **完全没有绑定任何代码状态**：

```python
repo: str = ""        # 只有"pandas-dev/pandas"一个字符串
                      # 没有 commit、没有文件路径、没有结构快照
```

**加两个字段**（`models.py`）：

```python
code_refs: list[str] = field(default_factory=list)
""""这条记忆**依赖过的代码文件路径**（相对仓库根）。

来源：处理该 issue 时调过 `read_code` 的那些路径。
（Agent 是只读的 —— 它判断的依据就是它读过的那些文件，
 那些文件变了，判断可能就不成立了。）
"""

repo_head: str = ""
"""写下这条记忆时，仓库的 commit / 快照标识。

★ 诚实说明：本项目**没有实现完整的代码快照比对**。
  这个字段现在只是个标识 —— 但**先把位置留出来**，
  否则以后要加时，历史数据全都是空的。
"""
```

**为什么 `code_refs` 抽的是"读过"而不是"依赖"**：

```
Agent 读了某个文件，不代表它的结论一定建立在这个文件上
（可能只是随手 read 了一下就否决了那条线索）

所以 code_refs 是**过度包含**的 —— 这个偏差方向是刻意选的：
  · 过度包含 → 复核队列多几条 → 人工多看一眼（成本可控）
  · 过度排除 → 漏掉真正失效的记忆 → 错误继续传播（代价高）

「宁可多查，不可漏查」。
```

### 3.2 抽取：从 trace 拿，不让模型"自己说"

```python
def _extract_code_refs(trace: Trace) -> list[str]:
    """从 trace 抽路径 —— trace 是事实记录，模型的自我报告是总结。"""
    for step in trace.steps:
        if step.action.tool_name != "read_code":
            continue
        p = step.action.tool_input.get("path")
        ...
```

**为什么从 trace 抽**：

| | trace | 模型自述 |
|---|---|---|
| 性质 | **事实记录**（客观发生过） | 总结（可能含糊、遗漏） |
| 格式 | 结构化路径，可直接比对 | 自然语言，格式不一 |
| 用于集合运算 | ✅ | ❌（做交集会大量漏判） |

**能用结构化数据就不要用自然语言** —— 同 `docs/05` 的"用痕迹而不是信号"。

### 3.3 存储：迁移 + 读容错

**加字段不只是改 dataclass** —— 已有的库必须走迁移：

```python
def _ensure_columns(self) -> list[str]:
    """增量迁移：给已有的表补上新增的列。

    `CREATE TABLE IF NOT EXISTS` 只在表不存在时生效 ——
    表已存在时新增的列**不会被加上**，
    新代码读旧库会 `OperationalError: no such column`。

    而 data/ 下的库是运行时产物（daily_triage.db 要跨周累积），
    不能靠"删库重建"解决。
    """
    cur = self.conn.execute("PRAGMA table_info(memories)")
    existing = {row[1] for row in cur.fetchall()}
    for col, decl in (("code_refs", "TEXT"), ("repo_head", "TEXT")):
        if col not in existing:
            self.conn.execute(f"ALTER TABLE memories ADD COLUMN {col} {decl}")
```

**两个原则**：

| 原则 | 理由 |
|---|---|
| **`ALTER TABLE ADD COLUMN`，不重建表** | SQLite 的 ADD COLUMN 只改元数据（廉价），且新列默认 NULL —— 正好符合语义。重建表要复制全部数据，中途失败就丢数据 |
| **读路径容错（`_safe_col`），写路径不** | 迁移期存在"代码已更新、库还没更新"的中间状态。读硬取新列 → 任何一次漏迁移都会让**整个模块不可用**，而"缺一个可选字段"本不该有这种后果 |

### 3.4 检测与闸门（`memory/stale.py`）

**核心逻辑**：

```python
def detect(self, changed_files: list[str], repo="") -> list[StaleSuspect]:
    changed = {self._norm(p) for p in changed_files}
    for mem in self.store.all_memories():
        if mem.archived:            continue    # 已归档的不再复核
        refs = mem.code_refs or []
        if not refs:                continue    # 没有代码引用的无法检测
        matched = [r for r in refs if self._norm(r) in changed]
        if matched:
            suspects.append(StaleSuspect(...))
    suspects.sort(key=lambda s: -s.priority)    # ★ 排序
    return suspects
```

**排序逻辑比检测逻辑更影响实际效果**（队列永远排不完）：

```
priority = 命中路径数 × 0.3 + 置信度 × 0.3 + 重要性 × 0.2
         + （人工确认过 ? +2.0 : 0）              ← 强制置顶
```

**为什么"人工确认过"要置顶**：它一旦失效，危害最大 ——
不只是"记错了"，而是"**人确认过的东西错了**"，更难被质疑。

**幂等键是 `(memory_id, trigger_detail)` 而不是只有 `memory_id`**：

```
① 有 pending                    → 跳过（已在队列）
② dismissed 且触发原因相同      → 跳过（**别重复问人**）
③ dismissed 但触发原因不同      → **重新入队**（这是新变更，上次的结论不能自动延续）
```

**只查 `memory_id` 会导致"一次 dismiss 之后永远不再复核"** ——
那是**漏检**，比"多问一遍"危险得多。

**`_norm()` 路径归一化**：

```python
'pandas/core/frame.py' / './pandas/core/frame.py' / 'pandas\core\frame.py'
→ 必须视为同一个文件
```

不归一化的话交集会**静默漏判** —— 而漏判的方向是"该复核的没进队列"。

### 3.5 人工闸门的落地形式（`scripts/review_stale.py`）

```bash
# 看队列（按优先级排序）
python scripts/review_stale.py --list

# 手动触发检测
python scripts/review_stale.py --detect pandas/core/frame.py

# 裁决
python scripts/review_stale.py --confirm sr_abc --by 张三 --note "重构后已失效"
python scripts/review_stale.py --dismiss sr_def --by 张三 --note "核对过，仍有效"

# 看覆盖率与检测质量
python scripts/review_stale.py --stats
```

**★ 为什么 `--dismiss` 和 `--confirm` 一样重要**：

`--confirm` 会改变记忆，`--dismiss` **不改变任何记忆** —— 但它同样被记录：

```
· 下次**同样的变更**再触发时直接跳过（不重复劳动）
· 累积起来能算"检测准确率"：dismiss 率高 → 检测太宽
```

**只记"确认"不记"否决"，等于强迫人做重复劳动**，而且丢掉了"检测质量"这个可优化指标。
（这和记忆召回的"无效召回率"是同一类指标：**衡量过滤器的质量**。）

### 3.6 结果反馈闭环（`memory/feedback.py`）

**这是两条线里覆盖更广的那条** —— 它不看代码，只看结果。

#### 核心公式：平滑误诊率

```python
suspect_score = misuse_count / (use_count + SMOOTHING)   # SMOOTHING = 3
is_suspect    = (misuse_count >= 2) and (score >= 0.25)
```

**为什么用比率而不是次数**：

```
记忆 A：用 100 次，错 2 次  →  2/103 = 0.019   健康
记忆 B：用 3 次，错 2 次    →  2/6   = 0.333   可疑

只看次数的话两者都是 2 —— **分不出来**，但性质完全不同。
```

**为什么加平滑项（+3）**：

```
用 1 次错 1 次 → 1/(1+3) = 0.25   不到高阈值（小样本证据不足）
用 2 次错 2 次 → 2/(2+3) = 0.40   过了
```

**为什么要求 `misuse >= 2`**：单次错误可能是**模型自己失手**，不足以定罪记忆。

#### 三个容易错的地方

**① 不做重复计数**

`use_count` 已经在主链路（`react.py` → `store.touch_access`）更新了。
本模块**只补那个主链路不产生的信号：误诊**。

> 两处都加 → `use_count` 翻倍 → 误诊率凭空减半。

**② 幂等键要用"稳定的类型标识"**

第一版把 `trigger_detail` 写成每次误诊的具体信息（`issue_id + evidence`）——
**每次都不同 → 幂等完全失效 → 队列膨胀**。

```
修法：trigger_detail = "feedback_misuse"（稳定）
      具体信息放进 misuse_events 明细表
```

**分工是对的**：
```
队列需要的是"该不该看"     → 去重维度 = 记忆身份
明细需要的是"为什么怀疑"   → 去重维度 = 无（全都要留）
```

**③ `memory_used` 为空时不该牵连任何记忆**

Agent 可能完全靠自己判断。那这次错误**和记忆无关** ——
**冤枉记忆比漏掉更糟**（把好记忆推进队列，浪费人的时间）。

#### 与"新变更要重新问"的区别

`stale.py` 里"新的变更要重新入队"，但 `feedback.py` 里"继续误诊**不再问**"：

```
新变更   → 记忆赖以成立的**前提**变了     → 值得重新评估 ✓
继续误诊 → 前提没变，只是结果不好       → 不必再问 ✓
```

**判断标准是"前提变了吗"，不是"结果好不好"。**

#### 接入点：`daily_triage.py` 的对账环节

对账有**两个产出**，第二个才是闭环的关键：

```
① 更新 gold —— 这是**评测**：知道"预测准不准"
② 记录误诊 —— 这是**反馈**：知道"哪些记忆在误导我们"
```

**第一版只做了 ①。** 加上 ② 之后，每天的自动对账就同时是
"评测跑分"和"记忆质检"。

**★ 一个前提：记忆库必须持久化。**

第一版 `build_memory()` 用的是 `:memory:` —— 每次新建。
这对"当天跑一次"没问题，但**结果反馈完全无法工作**：
误诊计数记在记忆对象上，库一关就没了，明天从 0 开始。

**"跨天积累"是这个机制的全部意义**，所以记忆库必须落盘（`data/memory.db`）。

## 四、验证

### 4.1 测试（19 条：`TestStaleDetection` 9 条 + `TestResultFeedback` 10 条）

| 测试 | 守什么 |

  ✓ 已入队 1 条（0 条已处理过，跳过）
  入队**不改变记忆** —— 需要人用 --confirm 裁决才生效。

$ python scripts/review_stale.py --db ... --confirm sr_cedb48aa --by 刘勇 --note "..."
  已确认过时  sr_cedb48aa

$ python -c "..."   # 召回 'merge 行数' → 只剩 ['mem_b']
```

**`mem_a` 已不再被召回** ✓ —— 闭环生效。

### 4.3 端到端验证（结果反馈闭环）

**场景**：模拟跨天的完整流程 —— 预测用到记忆 → 几天后对账发现错 → 记录误诊

```
day1 对账（第1次误诊）→ 入队: 0    ← 阈值未达（misuse=1 < 2）
day2 对账（第2次误诊）→ 入队: 1    ← misuse=2，score=0.29 > 0.25

复核队列（人看到的）：
  sr_a8743b5d  记忆=mem_stale
    症状: read_csv 慢，加 chunksize 解决
    触发: feedback_misuse

★ 嫌疑分对比（这就是"误诊率"的价值）：
  mem_stale    use= 4 misuse=2  score=0.29  ← 可疑
  mem_good     use=50 misuse=1  score=0.02  （正常）
       ↑ mem_good 也错了 1 次，但它被用了 50 次 → 率低 → 不怀疑

人裁决：确认 mem_stale 已过时
  confidence 0.80 → 0.10，archived=True

明细可追溯（哪几次误诊牵连了它）：
  #700  预测 Performance，真实 Bug
  #701  预测 Performance，真实 Build
```

**`mem_good` 那一行是整段演示最值钱的部分** ——
它证明了"用误诊率而不是次数"这个设计决策的实际效果：
**如果只看次数，`mem_good` 也会被怀疑**（它确实错了 1 次），
而那是**误伤**（50 次里错 1 次是很健康的记忆）。

## 五、诚实边界（这一节很重要）

### 5.1 地基覆盖率目前是 0

```
code_refs 是**新加的字段**，老数据的它必然是空的
（读路径容错保证了不会崩，但也不会有值）

→ 检测逻辑目前**不会命中任何老记忆**
→ 覆盖率只会随**新写入的记忆**积累而上升
```

**这不是 bug，是迁移的必然状态。** 但必须说清楚 ——
否则看到"检测命中 0 条"会误以为功能坏了。

`--stats` 里专门有一栏显示覆盖率，就是为了让这个状态**可见**。

### 5.2 `code_refs` 是"过度包含"的

Agent 读过≠依赖。所以队列里会有一些"读了但没用到"的误报。

**偏差方向是刻意选的**（宁可多查不可漏查），但它确实会产生噪声。

### 5.3 这个机制只能覆盖"有代码引用"的记忆

纯经验 / SOP（`SEMANTIC` 层）**没有 `code_refs`**，本方法**检测不到**。
它们的过时检测需要别的手段（本文档不做）。

**检测不到就返回空，不瞎猜** —— 有测试守着这一点。

## 六、面试怎么讲

**30 秒版本**：

> "记忆系统有个失效模式：**代码变了，旧记忆就过时了** ——
> 而且它比"记错了"更隐蔽，因为**内容完全自洽**。
> 我的项目里已经用污染实验证明过它是最难自动发现的类型。
>
> 我补的方案分三层：
> ① **地基**：给每条记忆绑定它依赖过的代码路径（从 trace 里的 read_code 调用抽，
>    不用模型自述 —— 因为要做集合运算，格式必须规整）；
> ② **检测**：`依赖路径 ∩ 本次改动的文件`，精确运算，零误判；
> ③ **闸门**：**检测自动、生效人工** ——
>    因为「变更波及」不等于「结论失效」，文件被改可能只是改了注释。
>    自动降权会重蹈我之前踩过的坑（被人工确认的经验被规则误伤）。
>
> 还有个细节：**'判定仍有效'也要记录** ——
> 它让下次同样的变更不再重复问人，而且能算出检测的准确率。"

**为什么这个回答强**：

1. **展示了对"自动化边界"的判断力**（不是所有东西都该自动）
2. **有对自身历史的引用**（"重蹈我之前踩过的坑"）
3. **主动区分了"变更波及"和"结论失效"** —— 这个区分本身就说明想清楚了
4. **提到了"判定仍有效也要记录"** —— 这是设计细节，不是背的
