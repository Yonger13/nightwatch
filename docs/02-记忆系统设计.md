# 02 · 记忆系统设计

> 这是整个项目的技术纵深所在。
> 一句话概括：**记忆系统的难点不在存储，在写入策略。**

---

## 一、先破一个误解

大多数"带记忆的 Agent 项目"是这样做的：

```python
# 存
vector_db.add(text)
# 查
results = vector_db.search(query, top_k=5)
```

这**不是记忆系统**，这是检索。区别在于：

| | 检索 | 记忆 |
|---|---|---|
| 回答的问题 | "哪段文本和这个查询像" | "过去发生过什么、当时怎么处理的、结果如何" |
| 有状态吗 | 无，每次独立 | 有，跨会话累积 |
| 会筛选吗 | 不会，有就存 | 会，判断值不值得记 |
| 会矛盾吗 | 不会，文档不会互相矛盾 | 会，两次记录可能冲突 |
| 会遗忘吗 | 不会 | 会（而且应该会） |

引用一句被反复提到的话：

> **"真正困难的不是存储，而是写入与读取策略。
> 什么值得保存？何时合并重复事实？怎样处理互相冲突的记忆？
> 检索多少条才不会挤压当前任务？错误记忆如何被纠正？"**

下面六节就是对这五个问题的回答。

---

## 二、三层记忆：不是随便分的

每一层解决一个**不同时间尺度**的问题：

| 层 | 解决的问题 | 时间尺度 | 载体 | 生命周期 |
|---|---|---|---|---|
| **工作记忆** | 本次会话里"我刚才做了什么" | 秒 ~ 分钟 | 上下文窗口内 + 溢出落盘 | 会话结束即失效 |
| **情景记忆** | "过去发生过什么" | 天 ~ 月 | 数据库 + 向量索引 | 长留存，按衰减策略归档 |
| **语义记忆** | "我们约定怎么处理这类问题" | 月 ~ 年 | SOP 文档 + 规则表 | 稳定，变更走审核 |

**为什么要分三层，而不是一个库？**

因为它们的**更新频率、可靠性要求、影响面**都不同：

- 工作记忆每秒都在变，丢了只影响当前这次任务
- 情景记忆按天累积，丢了影响"能不能学到经验"
- 语义记忆几乎不变，但**一旦错了会污染所有后续判断**

影响面不同 → 写入门槛必须不同。这就是下面第 6 节
"语义记忆要人工审核"的根本理由。

## 三、六个环节：记忆的完整生命周期

```
① 抽取 Extract      从"一次完整处理轨迹"里提炼候选记忆
② 评分 Score        判断这条值不值得长期保留
③ 写入 Write        过阈值才落库，且保证幂等
④ 合并 Consolidate  同一件事被记了两遍 → 合并而不是新增
⑤ 消解 Resolve      两条记忆矛盾时怎么裁决
⑥ 衰减 Decay        时间让记忆降权，但不是删掉
```

外加一条**升维通道**：

```
情景记忆（具体的事）──高频共性模式──▶ 语义记忆（抽象的 SOP）
                        ↑
                    人工审核闸门
```

### ① 抽取：抽什么、不抽什么

**抽**：症状、根因、处置动作序列、最终结论
**不抽**：寒暄、无关的中间对话、单次性的临时参数

判断标准只有一条：

> **"如果下次遇到类似问题，这条信息能不能让我少走弯路？"**

**关键设计 1：抽取是异步的。**

因为抽取的价值在未来，不在当下 —— 当前这次处理并不依赖"这次的经验有没有被存下来"。
所以没有任何理由让它阻塞主链路。

异步之后要处理三件事（这才是真实的工程问题）：
- **失败重试**：抽取失败不能影响工单本身
- **幂等**：重试时不能写两条（由数据库唯一索引保证，见 ③）
- **死信**：重试到上限还失败要记录下来，不能静默丢弃

**关键设计 2：允许根因为空。**

如果提示词里不说明"根因可以为空"，模型会硬编一个根因出来。
而"**未定位到根因**"本身是有价值的信息 —— 它意味着这个问题需要更深的排查。

这是一条通用原则：**不要让模型在"不确定"时被迫给一个看起来合理的答案。**

### ② 评分：为什么不用模型打分

评分函数是**可解释的加权和**，不是再套一个模型。两个理由：

1. **"为什么这条被记下来了"必须能回答。**
   如果评分是黑盒，你无法调试"为什么记忆库里全是垃圾"。
2. **模型打分有随机性，而写入决策需要稳定。**
   同一个候选今天 0.6、明天 0.5，库的行为就不可预测了。

四个因子（权重需要通过标注标定，不是拍脑袋）：

| 因子 | 含义 | 方向的说明 |
|---|---|---|
| 可复用性 | 未来还会再出现吗 | 同类症状的历史频次越高，分越高 |
| 因果完整性 | 定位到根因了吗 | 有根因 > 只缓解症状 |
| **人工反馈** | 工程师是否采纳 | **权重最高的客观信号** |
| 非平凡性 | 是不是"重启一下"这种常识 | 通用答案降分 |

**★ 人工反馈的映射有一个反直觉的点**：

```python
ACCEPTED: 1.0
EDITED:   0.7    # 修改后采纳：方向对但细节错
REJECTED: 0.0    # 不是 0.5
UNKNOWN:  None   # 不是 0.5
```

- `REJECTED = 0.0` 而不是 0.5：被驳回的记忆如果还写成中等分数，它就会进库、
  会被召回、会误导 Agent。**错误的记忆比没有记忆更危险。**
- `UNKNOWN = None` 而不是 0.5：**"没有信号"和"中性的信号"是两件事。**

第二条是踩坑后改的（见 [`05-开发实录`](05-开发实录-真实缺陷复盘.md) 的 B2）：
最初用 0.5 表示"没有反馈"，结果在没人反馈的场景下（离线评测、自动批处理 ——
**恰好是最常见的状态**），这一项恒定为 0.5，不携带任何信息，
却凭着 0.25 的权重**稀释**了其他三个真实信号，导致所有记忆都过不了阈值。

修复方式是让 `Scorer` 只对"有信号"的因子做加权平均：

```python
available = {k: v for k, v in scores.items() if k in weights and v is not None}
total = sum(weights[k] * v for k, v in available.items()) / sum(weights[k] for k in available)
```

### ③ 写入：幂等靠数据库，不靠 if 判断

```sql
CREATE UNIQUE INDEX idx_mem_idem ON memories(idem_key);
```

**为什么用数据库约束而不是应用层判断？**

因为应用层判断有竞态：两个异步任务同时检查"存在吗"、都得到"不存在"、
然后都写入。数据库的唯一索引是原子的，从根本上避免这个问题。

这也是"幂等"从概念落到代码的样子：**不是靠 if 判断，是靠约束。**

### ④ 合并：解决"同一件事记了三遍"

两条记忆相似度超过阈值（默认 0.92）就合并。合并策略不是简单覆盖：

| 字段 | 策略 | 理由 |
|---|---|---|
| symptom | 保留更长的 | 通常信息更全 |
| root_cause | 优先保留有的 | "没定位到"不如"定位到了" |
| tags | 取并集 | 信息不丢 |
| **actions** | **累加去重** | ★ 保留两次的失败尝试，这是最有价值的部分 |
| 访问计数 | 累加 | 历史热度要继承 |
| 人工反馈 | 取更权威的 | EDITED > ACCEPTED > UNKNOWN |

**合并率是个可观测指标**：合并率高说明抽取环节有重复产出（需要优化抽取）；
合并率为 0 说明相似度阈值太松。

### ⑤ 消解：三级裁决，但**不下最终结论**

当两条记忆在同一事实上矛盾时，按三级依据打分：

| 依据 | 权重 | 说明 |
|---|---|---|
| 新近度 | 0.35 | 时间近的更可能对 —— **但单独用很危险，新记录本身可能是错的** |
| **来源权威性** | **0.40** | 人工编辑 > 人工确认 > 自动抽取 |
| 证据强度 | 0.25 | 有工具调用日志佐证 > 仅模型推断 |

**关键设计：分差足够大才自动裁决；分差不足 → 进 pending 队列交人工。**

```python
if margin < resolve_min_margin:      # 默认 0.15
    store.add_conflict(PendingConflict(...))
    return None, conflict
```

**为什么不让 Agent 自己拍板？**

> 因为记忆系统不可能永远自洽。
>
> 如果让 Agent 覆盖，一旦拍错，错误会通过召回传播到后续所有相关判断 ——
> **错上加错**。把矛盾明确挂出来等人判，看起来慢，但可靠。

这个设计的另一层价值：它回答了一个可能的质疑 ——
"你的记忆系统会不会自己跑偏？" 答：会，所以我给影响力大的那一层加了人工闸门。

**★ 另一个容易做错的点：相似 ≠ 矛盾。**

共用一个问题（相似度高）是正常的。冲突的定义要更严格：
**它们在同一个事实上给出了不相容的结论。**

```python
# 判据：symptom 相似 且（根因都存在且差异大 或 处置都存在且差异大）
if sim < 0.75:
    return False          # 不是同一个问题，谈不上冲突
if a.root_cause and b.root_cause and overlap(a.root_cause, b.root_cause) < 0.3:
    return True
if a.resolution and b.resolution and overlap(a.resolution, b.resolution) < 0.25:
    return True
```

只看相似度就判冲突，会产生大量假阳性 → pending 队列被淹没 → 人工就不看了。
**这是设计"人工回环"时最容易犯的错。**

### ⑥ 衰减：三个容易做错的地方

**错误 1：把衰减做成删除**

正确的分层处理：

```
权重正常   → 参与召回
权重低     → 移入冷存储（仍可精确查询，不参与向量召回）
保留期满   → 归档（真实项目还要考虑审计要求，不能真删）
```

**为什么不能真删**：审计需求。"某次判断当时依据了哪几条记忆"这个问题必须能回答。

**错误 2：以为访问频次高就等于重要**

这是最反直觉的一点。有些记忆被频繁召回，仅仅因为它的向量"吸引"了很多
不相关查询（我们叫它**噪音吸铁石**）。

所以有效权重必须引入"召回后真的被用上了"的比例：

```python
effectiveness = use_count / access_count      # 而不是 access_count
eff_factor = 0.5 + 0.5 * effectiveness
```

**为什么不做成乘法（`× effectiveness`）**：那太狠 ——
一条从未被用过的记忆会被直接清零，而"从未被用"可能只是因为它还没遇到合适的问题。

**错误 3：忘记给人工资格加保护**

踩坑记录（见 [`05`](05-开发实录-真实缺陷复盘.md) 的 B6）：
一条被工程师明确 ACCEPTED 的经验，400 天后权重降到 0.03，被系统当垃圾归档了。

这在业务上是错的：
- **验证过是对的**，这件事本身价值很高，而且验证成本很高
- 这类经验通常描述**稳定事实**（架构缺陷），不是易变状态（客户配额）

所以加一个权重下限：

```python
if mem.human_verdict in (ACCEPTED, EDITED):
    weight = max(weight, 0.25)
```

**教训**：纯数学的衰减公式不知道"这条经验被人验证过"意味着什么。
**把领域知识显式写进公式，是设计工作的一部分。**

## 四、升维通道：情景 → 语义

高频共现的标签组合会被识别为"共性模式"，可以提炼成 SOP。

**关键在于：这条通道上有一道人工审核闸门，而且是 API 层面无法绕过的。**

```python
def promote(self, pattern, occurrences, samples, approved: bool):
    if not approved:
        return None      # 没有默认值 True —— 刻意的
```

**为什么语义记忆需要审核，而情景记忆不需要？**

因为**影响面不同**：
- 一条错误的情景记忆，只影响一次召回
- 一条错误的 SOP，会被所有后续任务召回 —— 污染面大得多

风险量级不同，门槛就该不同。这个"按影响面分级管控"的思路，
可以迁移到很多地方（发布流程、权限设计、配置变更）。

## 五、检索：为什么要混合

```python
store.recall(query, author="alice", top_k=5)
```

**两种查询意图需要两种信号**：

| 意图 | 需要什么信号 | 纯向量能做到吗 | 纯 SQL 能做到吗 |
|---|---|---|---|
| "这个作者以前报过什么" | 精确匹配 | ✗ | ✓ |
| "有没有人和他遇到一样的问题" | 语义相似 | ✓ | ✗ |

而这两件事经常要**同时做**。所以实现是两段式的：

```
第一阶段（粗排）：SQL 用索引条件把候选集缩小到 candidate_pool
第二阶段（精排）：在候选集内算向量相似度并排序
```

**为什么不全表算向量**：那是 O(N)，记忆库到 10 万条时会慢到不可用。

**★ 召回必须有门槛**（这是踩坑后加的）：

```python
if score < min_sim:      # 默认 0.30
    continue
```

因为**错误的召回比不召回更糟** —— 模型会相信上下文里的一切。
实测过：一个内容只有"有 bug"的 issue，因为注入了无关记忆，
被错误地分类成了 config 问题（正确答案是"转人工"）。

没有门槛的召回，等于往提示词里灌噪音，而且**噪音在主动误导模型**。

## 六、一个真实的教训：上游少一个字段，下游整个模块失效

这是本项目最值得记住的一条链式依赖（见 [`05`](05-开发实录-真实缺陷复盘.md) 的 B3）：

```
主循环的输出结构（summary 里没有"根因"这一行）
        ↓
记忆抽取抓不到 root_cause 字段
        ↓
causal_depth 只有 0.3（而不是 0.8）
        ↓
总分 0.535 < 阈值 0.55
        ↓
所有记忆都被筛掉 → 记忆系统等于不存在
```

**每个模块单独看都没问题，单测也全过。** 只有端到端跑并检查副作用才能发现。

**教训**：

> Agent 的最终输出结构不是"随便写写"，
> 它同时是**下游系统的输入契约**。

## 七、核心设计的速查表

| 问题 | 答案 | 在哪 |
|---|---|---|
| 什么值得记 | 四因子加权 + 阈值 | `lifecycle.Scorer` |
| 什么时候写 | 工单关闭 + 关键节点，异步 | `lifecycle.Extractor` |
| 重复了怎么办 | 相似度 > 0.92 合并，actions 累加 | `lifecycle.Writer._merge` |
| 矛盾了怎么办 | 三级裁决 + pending 队列 | `lifecycle.Resolver` |
| 怎么遗忘 | 半衰期 + 有效性修正 + 归档不删 | `lifecycle.Decayer` |
| 怎么检索 | 结构化过滤 + 向量精排 + 门槛 | `store.MemoryStore.recall` |
| 什么进语义层 | 高频模式 + **人工审核** | `lifecycle.SemanticPromoter` |

## 八、面试时怎么讲

**30 秒版本**（先说难点，再说解法，最后说验证）：

> 记忆系统最难的其实不是存储，是写入策略 —— 什么值得记、重复了怎么合并、
> 矛盾了听谁的。
>
> 我的做法是六环节生命周期：抽取、评分、写入、合并、消解、衰减。
> 其中两个设计我想特别说一下：
>
> 第一，**冲突消解我刻意不让系统自己拍板**。分差不够时进 pending 队列交人工。
> 因为记忆系统的错误会通过召回传播 —— 一次误判会影响后续所有相关判断，
> 这比知识库错一次严重得多。
>
> 第二，**衰减里我加了人工确认的保护**。因为纯时间衰减会让一年前被工程师
> 确认过的正确经验被当成垃圾归档，而验证成本是很高的。
>
> 验证方式是记忆效果对照实验：同一批 issue 分 fresh / warm 两组跑，
> 测步数和 token 的差异。

**可能被追问的三个问题**：

1. **"你怎么知道哪些记忆该记？"**
   → 讲评分函数 + 阈值标定过程（人工标一批"是否值得保留"，扫阈值看召回率/污染率）

2. **"记忆冲突了以谁为准？"**
   → 讲三级裁决 + **关键是要说"分不清时我不自己拍板"**

3. **"你怎么防止记忆污染？"**
   → 写入侧压制（REJECTED=0）、读取侧标注"这是参考不是事实"、
   纠正侧提供撤销接口并追踪受影响范围，再加一个污染注入实验

**要避免的说法**：

- ✗「我用了向量库做长期记忆」→ 这是检索，不是记忆
- ✗「我的记忆系统很准」→ 没有边界的自信是减分项
- ✓「我在哈希向量下测出 duplicate F1 只有 0.5，因为判别力不足，
     换语义 embedding 是必须的」→ 知道边界才可信
