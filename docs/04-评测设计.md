## 一、两组值得记住的数字

```
Gartner：到 2027 年底，超过 40% 的 Agentic AI 项目会被取消或降级
```

## 二、三条纪律（写在代码里，也被测试守住）

### 纪律 1 · 不报单次最好成绩

大模型有随机性，跑一次的结果没有意义。做法：

- 每个样本跑 N 次（默认 3）
- 报**中位数**，不报平均值（平均值受极值影响大）
- 同时报 P95（长尾才是用户体验）

### 纪律 2 · 不只报赢的那组对比

如果 warm 组（带记忆）没有明显更好，要**如实说明并解释原因**。

代码里就是这样的：

```python
f1_change = result["F1变化"]["百分比"]
if f1_change != "N/A" and float(...) <= 0:
    print("⚠ 说明：本次对照中 F1 没有提升。")
    print("  可能的原因（必须如实说明，不能藏起来）：")
    print("    ① 合成数据的重复性不够高，记忆没发挥空间")
    print("    ② Mock 模型的'使用记忆'是规则分支，不代表真实模型的行为")
    print("    ③ 召回精度不足（相似度阈值/向量质量问题）")
```

**不报失败结果的评测不是评测。**

### 纪律 3 · 所有指标注明样本量和版本

```python
"样本量": len(results),
"confidence_interval_note": (
    f"样本量 {len(results)}，F1 的 95% 置信区间约为 ±"
    f"{wilson_margin(len(results)):.2f}；"
    f"样本量偏小时该指标不宜下强结论"
),
```

> **面试官真正看的是"这个人知不知道自己数字的边界在哪"**，
> 不是数字好不好看。

一个说"这个指标我只测了 30 条，置信区间很宽，不能下强结论"的候选人，
比一个报出漂亮数字却答不出实验设置的候选人可信度高得多。

## 三、为什么必须分层报告

假设 70% 的 issue 是 timeout 类，模型表现很好（F1 = 0.9）；
30% 是配置类，模型表现很差（F1 = 0.2）。

**总分是 0.69，看起来"还不错"** —— 但实际上有一整类问题它处理不了。

```
分层                样本      中位F1      最低F1      中位步数
────────────────────────────────────────────────────
config             2     0.833     0.667       1.0
crash              2     0.833     0.667       1.0
dependency         2     1.000     1.000       1.0
duplicate          2     0.667     0.667       1.0
feature            2     1.000     1.000       1.0
permission         2     1.000     1.000       2.0
timeout            2     1.000     1.000       1.0
unclear            2     0.000     0.000       1.0    ← 一整类处理不了
```

**最低 F1 这一列是重点** —— 它告诉你"最差的那一类有多差"。

而"要不要分层"这个决定本身，就体现了你有没有真的做过评测。

### 分层怎么分

先枚举问题类型，每类保证最少样本数：

```python
STRATA = {
    "timeout":    "超时、限流、性能问题",
    "permission": "权限、鉴权、访问控制",
    "config":     "配置错误、环境问题",
    "dependency": "依赖冲突、安装失败",
    "crash":      "崩溃、异常退出",
    "duplicate":  "重复问题（用于测判重能力）",
    "feature":    "功能请求（非 bug，需要区分出来）",
    "unclear":    "信息不足，应转人工",
}
```

**分层要来自真实数据，不是拍脑袋。** 第 0 周采集的标签分布就是依据
（见 [`01-第0周-观察真实项目.md`](01-第0周-观察真实项目.md)）。

## 四、duplicate 检测：为什么必须分四象限

```python
tp / fp / fn / tn      # 而不是一个准确率
```

因为**两类错误的代价不对称**：

| 错误 | 后果 | 严重程度 |
|---|---|---|
| 漏报（FN）真重复但没识别 | 维护者重复处理一遍，浪费一点时间 | 轻 |
| **误报（FP）** 不重复却说是重复 | 新问题被标记为"已解决"，**永远不会被处理** | **重** |

**所以阈值应该偏保守（宁可漏报，不要误报）。**

这个取舍是"业务理解"在指标设计上的体现 —— 它说明你不是在机械地调 F1。

## 五、最有区分度的实验：记忆效果对照

### 实验设计

同一批 issue，分两组跑：

```
fresh 组：记忆库为空（或屏蔽召回）
warm  组：记忆库已积累历史经验
对比：步数 / token / F1
```

**它直接回答"记忆到底有没有用"**，而不是笼统地说"我实现了记忆系统"。

### 三个设计要点

**① 唯一变量是记忆开关。**
同一批 issue、同一模型、同一工具集、同一个历史库。

**② warm 组的记忆来自"前一阶段"。**
先用前半批 issue 让系统积累记忆，再用后半批测 warm 表现。
这样测的是**真实的经验复用**，而不是"人为注入的记忆"。

**③ 报告必须包含没有提升的情况。**

### 实测输出

```
  指标                  fresh(无记忆)       warm(有记忆)            变化
  ──────────────────────────────────────────────────────────────
  步数                         3.0             2.0        -33.3%
  Token                   4234.5          2878.0        -32.0%
  F1                         1.0             1.0         +0.0%
```

**注意 F1 没有提升 —— 而报告如实写出了这一点并解释原因。**
（原因：合成数据的重复性不够高、Mock 模型的记忆使用是规则分支。）

## 六、实验单位：一个隐蔽但致命的选择

这是踩坑后修正的（见 [`05`](05-开发实录-真实缺陷复盘.md) 的 C2）。

| 做法 | 结果 |
|---|---|
| 每样本跑 N 次，每次新建记忆库 | 记忆永远为空 → **记忆类指标恒为 0** |
| **跑 N 遍完整批次，每遍一个新库** | 每遍内部记忆正常累积，各遍独立可比 ✓ |

```python
# 正确做法
for run_idx in range(runs):
    store = _new_store()                    # 每遍一个新库
    for issue in issues:
        ...                                 # 库内记忆正常累积
```

**教训**：

> **实验的"单位"选错了，指标就失去意义。**
>
> 这不只是实现问题，是"你想测什么"的问题。
> 要测"持续运行的系统"，实验单位就必须是"一段时间"，而不是"单次调用"。

修复后，记忆命中率从 0%（不可测）变成 28.6%（可测）。

## 七、阈值标定：从"经验值"到"扫出来的"

### 做法

`scripts/sweep_threshold.py` 扫 0.10 ~ 0.95，输出完整的 P/R/F1 曲线：

```
  阈值    TP   FP   FN   TN   precision  recall     F1
  0.25     3    7    0    8      0.300    1.000   0.462
  0.30     2    3    1   12      0.400    0.667   0.500  ← F1 最优
  0.35     1    1    2   14      0.500    0.333   0.400
  0.40     0    1    3   14      0.000    0.000   0.000
```

**但注意：不要直接用 F1 最优的那个值。** 还要看两类错误的代价
（误报严重得多，所以实际取值应该更保守）。

### 扫描暴露的更重要的问题

```
  重复样本的 top1 相似度:   0.2865 ~ 0.3612
  非重复样本 top1 相似度:   0.1101 ~ 0.4137     ← 两组重叠
```

**重叠意味着任何阈值都会有错误**，F1 的天花板就在 0.5 附近。

根因不是阈值选得不好，是**哈希伪向量的判别力不足**：

```
「接口在高峰时段频繁超时」vs「高峰时段接口超时（重复）」  → 真重复
「接口在高峰时段频繁超时」vs「定时任务偶发执行超时」      → 不是重复
三条都含"超时"，共享大量 bigram，哈希向量给出的相似度几乎一样
```

**结论**：正确的优化方向不是继续调阈值，而是换语义 embedding。
项目为此加了 `APIEmbedding`（设 `NW_LLM_API_KEY` 自动启用）。

### 这件事的价值

> "我扫了阈值"比"我用的 0.75"强得多。
>
> 但更强的是**发现"扫了也没用"** —— 并且能说清为什么没用、该怎么修。

这个"发现问题 → 定位根因 → 给出修复路径"的链条，
比一个漂亮但没来由的数字有价值得多。

## 八、LLM-as-Judge 的偏差处理

**这是必然会被问的问题。** 四件事，按重要性排序：

### ① 校准（最重要）

先人工标注一批，测裁判与人工的一致率。**一致率不够就不能用。**

```python
cal = JudgeCalibrator(min_agreement=0.7)
result = cal.agreement(judge_scores, human_scores)
if not result["可用"]:
    # 不是"凑合用"，是"不能用"
```

**为什么不能用**：一个不可靠的裁判比没有裁判更糟 ——
它会给你一个错误的信号，让你优化错方向。

### ② 拆细粒度

不评"回答得好不好"（主观、不稳定），而是拆成**可判定的子项**：

```python
"has_label":    是否给出了明确标签
"has_reason":   是否说明了理由
"has_citation": 是否给出了引用依据
```

**三个原则**：可判定（不是"好不好"，是"有没有"）、正交（不重复计量）、
少（3~4 个，多了会互相干扰）。

子项比整体判断稳定得多。

### ③ 位置偏差

做 A/B 对比评测时**交换顺序跑两次**，避免裁判偏心第一个。

### ④ 规则兜底

**能用确定性规则判的绝不用模型。**
比如"输出里是否包含禁用操作名" —— 规则没有随机性。

## 九、指标清单与口径

| 类别 | 指标 | 怎么测才公平 |
|---|---|---|
| **效果** | 自助解决率 | 定义写死："建议被采纳且正常关闭"才算，不能凭模型自评 |
| | 转人工率 | **单独统计** —— 它不是失败（见 `03` 文档） |
| | 误诊率 | 需要 ground truth；判据是"预测与维护者标注无交集" |
| | 平均收敛轮次 | 报中位数，并报 P95 |
| | 首次响应延迟 | 报 P50/P95，注明硬件和模型版本 |
| **记忆** | 记忆命中率 | 召回后被**实际使用**的比例 |
| | 无效召回率 | `1 - 命中率`。**这个指标最能暴露召回质量问题** |
| | 记忆准确率 | 抽取结果与人工标注的一致性，要报样本量和标注人数 |
| **长程** | 长程一致性得分 | 同一任务跑 5 轮 vs 50 轮，测初始约束的遵守率差异 |
| | 污染纠正速度 | 注入错误记忆，测经过多少次人工反馈能纠正 |
| **成本** | 单工单 Token | 拆分：主链路 vs 记忆抽取 |
| | 记忆开销占比 | 记忆相关 token / 总 token —— 成本意识的直接证据 |

### 一个反直觉的指标：无效召回率

只看"召回了几条"会误导你。有些记忆被频繁召回，
仅仅因为它的向量"吸引"了很多不相关查询（噪音吸铁石）。

实测中，没有召回门槛时**无效召回率高达 76.9%** ——
而那些无效召回**正在主动误导模型**（实测导致过分类错误），不只是浪费 token。

所以在 `Trace` 里同时记录两个数字：

```python
memory_recalled: list[str]   # 召回了哪些
memory_used:     list[str]   # 实际用了哪些
```

**而这要求 Agent 显式声明"我引用了哪条记忆"** ——
所以记忆渲染里带了 `记忆ID=ep_xxx`，并要求模型引用。
这不只是指标需求，也是可追溯性要求
（"某次判断当时依据了哪条记忆"必须能回答）。

## 十、防过拟合：三道防线

### ① 分层采样

保证稀有类型也有覆盖，不然评测集全是被简单样本刷出来的高分。

### ② 留出集

```python
DatasetBuilder(holdout_ratio=0.3)   # 30% 完全不参与调试
```

**调试期间不得使用 holdout**，最后只用它报数。

### ③ 数据来自真实来源且脚本化

评测集由脚本生成、进版本控制，别人能复现。
而不是手工挑几十条"看起来合适"的样本。

**并且必须诚实标注来源**：

```python
source="synthetic",
notes=("⚠️ 合成数据，仅用于跑通流程与演示。"
       "症状描述比真实 issue 规整，指标会虚高。"
       "**不要把这个数据集上的数字写进简历。**")
```

代码里还会在跑评测时**主动打印警告**：

```
⚠ 本次评测用的是合成数据 + Mock 模型。
  这些数字只能验证"流程正确"，**不能写进简历**。
```

## 十三、统计检验与校准

前十二章解决的是"**测什么、怎么测**"；这一章解决"**测出来的差异算不算数**"。

四块能力，对应四个常见但容易被跳过的问题：

| 问题 | 原来的缺口 | 现在 |
|---|---|---|
| "提升显著吗" | 只有单比例的区间标注（`_wilson_margin`），从不用于组间对比 | 配对检验 `significance.py` |
| "哪条能自动出、哪条转人工" | 准确率只说整体，不说"哪条靠谱" | 置信度校准 `calibration.py` |
| "在 18 个阈值里挑最优" | 没有任何多重比较意识 | `bonferroni_note` 提示 |
| "错在哪一层" | 失败分析散落在各文档，无统一口径 | 错误分类 `error_taxonomy.py` |

### 13.1 为什么必须是**配对**检验

同一个实验，如果两组观测来自**同一批样本**（改动前 / 改动后），
那就是配对设计，必须用配对检验。

误用独立样本检验的后果不是"算得不准"，而是**系统性损失统计功效** ——
每个样本自己的基线信息被丢掉了，真实存在的差异会被判成"不显著"。
反过来，两组本来就是不同样本却硬套配对检验，则是凭空制造相关性，p 值虚假地小。

判断方法只有一句：**两次测量是不是发生在同一个对象上。**
本项目的所有前后对比都是同一批 issue → 一律配对。

#### 三个函数的分工（选错比不做更糟）

| 指标类型 | 用什么 | 为什么 |
|---|---|---|
| 连续（F1 / 步数 / token / 时延） | `paired_bootstrap` 或 `wilcoxon_signed_rank` | 不假设分布形状；差值分布常常很偏 |
| 二元（命中 / 未命中） | `mcnemar` | 二元值没有"大小"只有"翻没翻"，只需看不一致的那部分 |

`paired_bootstrap` 和 Wilcoxon 之间：**要给置信区间用前者，要抗极端值用后者。**
两个都跑也不冲突，但报告里必须说明**主口径是哪个** ——
两个都报却不说明以谁为准，等于把选择的负担推给读者。

#### 与 `_wilson_margin` 的分工（别混用）

```
_wilson_margin        → 单比例的区间标注。描述性，回答"这个数字有多虚"。
                        不做假设检验，也不能用来比较两组。
significance 模块     → 组间对比。推断性，回答"两个数字的差是不是真的"。
```

不能拿 `_wilson_margin` 比两组，因为它用的是 `1.96 × 0.5 / √n` ——
一个**与数据无关的保守上界**（p=0.5 时正态近似方差最大），
而且完全没利用配对结构。**区间不重叠是显著的必要不充分条件。**

> 一句话记法：`_wilson_margin` 说"这个数字有多虚"，
> `significance` 说"两个数字的差是不是真的"。

#### 实现里两处容易写错的地方

**① CI 和 p 值要用两种不同的重采样**

```
置信区间 → 重采样【原始差值】      （刻画估计量本身有多不稳定）
p 值     → 重采样【中心化后的差值】（必须在 H0 下模拟）
```

直接拿原始差值去数"有多少次跨过 0"，得到的是"CI 是否包含 0"，
**和 p 值不是一回事** —— 偏斜分布上两者会明显分歧。

**② 二元配对的有效样本量是 b+c，不是总样本数**

McNemar 只数"翻没翻"，两次都对的、两次都错的**对差异没有信息**，已被排除。
报告里必须写 b+c，否则读者会以为是全部样本的证据。

#### 实测结果（61 条前瞻数据）

```
F1 口径（bootstrap）    p = 0.0169，CI [+0.0219, +0.1530] → 显著
命中口径（McNemar）     b=0 / c=4，p = 0.1250            → 不显著
```

**两个口径不一致** —— 而这里的不一致本身是最有信息量的部分：

> b+c = 4 时，双侧精确检验的最小可能 p 值就是 2/2⁴ = 0.125。
> 也就是说，**这个口径在本轮数据上数学上不可能达到显著** ——
> 它的"不显著"完全不含"没有效果"的信息，是**检验功效不足**。

由此得到一条比结论更重要的纪律：

> **「不显著」≠「没有差异」。** 不显著只说明这批数据没提供足够证据，
> 可能的原因是样本量不够、效应太小、或检验功效不足 ——
> 三者要用不同方式回应，混在一起就会得出"改动没用"的错误结论。

汇报这类结果时，"检验功效不足"和"效果不存在"必须分开说 ——
前者要的是**更多样本**，后者要的是**换方向**。

### 13.2 错误分类：把"错了多少"变成"错在哪一层"

报告里"错了 4 条"这句话信息量为零 —— 它把四种性质完全不同的失败
混成了一个数字，而**其中两种根本不是模型的问题**：

```
knowledge_gap    领域知识缺失：类别名/缩写不在词表里，模型没机会答对
reasoning_error  推理被误导：信息都在，但被无关内容带偏
evaluation_bug   评测侧缺陷：模型答对了，是映射/归约环节把它丢了
tool_failure     工具调用失败：流程没跑完，谈不上推理对错
no_error         预测正确（或 gold 本身存疑）
```

#### 最容易搞反的一处

```
knowledge_gap ：模型输出里【根本没有】正确信号  → 它不知道
evaluation_bug：模型输出里【已经有】正确信号，但最终预测没有 → 被丢了
```

判据是"**原始预测里有没有指向正确答案的线索**"，**不是"预测对不对"**
（后者两个类别都一样错）。搞反了就会把评测的 bug 记在模型头上，
然后照着完全错误的方向去优化模型。

★ 实现上这一点对应一条硬要求：判据必须看 `predicted_raw`（粗化**之前**），
不能看最终预测 —— 线索正是在粗化那一步被丢掉的，拿结果去判断永远判不出来。
（第一版就写错了，结果是这条规则**永不触发**。
一个永不触发的分支比没有分支更糟，因为它看起来在守。）

#### 实测：真实数据上 3/4 是评测的锅

对 61 条前瞻实验里未命中的 4 条做分类：

```
#67982  title="CI: ..."  raw=['CI','config','dependency']  gold=Build → 预测 []
#66735  title="BLD: ..." raw=['BLD','needs-info']          gold=Build → 预测 []
#67983  title="CI: ..."  raw=['ci','config','documentation','bug']  gold=Build
#67985  title="BUG: ..." 模型照抄了标题前缀                    gold=Build

→ 责任归属聚合：评测 3 条 / 模型 1 条
```

模型**明明输出了 `CI` / `BLD`**，是评测侧的映射表没收录这两个缩写，
归约时把它们丢了。**只报"错了 4 条"会把方向指向模型，而 3/4 的病灶在评测。**

`taxonomy_report` 因此把"**责任归属**"单独聚合一次 ——
这一步直接决定下一步该动哪里。报告里同时给"该怎么做"，
读的人不必回去翻文档。

#### 一个诚实性设计：证据强度

兜底类别（`reasoning_error`）总是会接住"其他原因"的那些。
把它和"已定位到原因"的混在一起报，读者会以为每条都查清了。
所以每条判定都带 `evidence_strength`，报告里单独报出"证据强度不足比例"。

#### 已知局限

- 五类**不是 MECE 的穷尽划分**：模型答对但 gold 标错的会被归到 `no_error`，
  那属于数据问题，需要人工复核才能发现
- 分类靠**规则 + 调用方提供的上下文**，不是模型判断。
  好处是完全确定、可复现、可单测；代价是**上下文给得不全就会误分** ——
  所以信息不足的比例是单独报出来的，不塞进某个类别里
- 别名表（`ci → Build`）**不在本模块**，由调用方通过 `context["coarsen"]` 传入。
  自己再存一份就是"同一件事两份实现"

### 13.3 置信度校准：决定"能不能做转人工分流"

准确率相同的两个系统，能做的事可以完全不同：

```
系统 A：每条都报 confidence = 0.9，其中 90% 是对的
系统 B：一半报 0.99（全对）、一半报 0.55（对一半）
```

两者准确率一样，但 B 可以"0.99 的直接出、0.55 的转人工"，
整体准确率拉到接近 100%。

> **决定"能不能分流"的不是准确率，是校准质量。**
> 如果 confidence 和实际正确率对不上，任何基于阈值的分流都会失效 ——
> 你以为转的是低质量样本，实际不是。

#### 三个指标是递进关系

| 指标 | 回答 | 用途 |
|---|---|---|
| `ece` | 模型的自信**准不准**？ | 判断"能不能用" |
| `risk_coverage_curve` | 只出最自信的 x% 时错误率多少？ | 判断"能用多少" |
| `suggest_escalation_threshold` | 要保证直出准确率 ≥ 某值，切在哪？ | 给出可执行切点 |

**AURC 必须和"整体错误率"对比着读** —— 置信度无信息时，
AURC 的**期望值**就等于整体错误率。单看 AURC 的绝对值没有参照物。
（是期望值不是恒等：单次取值会在它附近浮动。）

#### 阈值的目标函数：覆盖率最大，不是准确率最大

`min_accuracy` 是**质量约束**，在满足它的前提下**覆盖率最大化**。
不用"准确率最大化"是因为那样会把保留条数压到 1 条
（准确率 100%、覆盖率 1%）—— 对业务毫无意义。
**阈值问题永远是"质量 × 覆盖"的权衡，不能只优化一头。**

#### 三条必须写在结论旁边的边界

**① `confidence` 是模型自报的，不是概率。**
校准分析测的是"**自报值和实际正确率的一致性**"，
不是"它是不是真的概率"—— 后者需要模型内部 logits，本项目拿不到。

**② ECE 依赖分桶数。**
桶越少每桶平均越"平"，ECE 会系统性偏小。
所以 `n_bins` 是 ECE 的**隐含参数**，放在 `config.EVAL["calibration_bins"]`，
报告里必须写明用了几个桶。

**③ `expected_accuracy` 有乐观偏差。**
切点是在**同一批数据**上挑出来、又在**同一批**上评估的 ——
这个数字是观测值，不是上线后的真实准确率。
必须在独立数据上复验。这与阈值扫描、超参搜索是同一类问题。

> 另外：找不到切点（`found=False`）本身是一个**有用的结论** ——
> 它说明问题不在阈值，而在上游（模型或置信度质量）。

### 13.4 多重比较：为什么只做提示，不做完整校正

**在 k 个候选里挑最优，这个"挑"的动作本身就会让结果偏高。**
比较次数越多，"碰巧看起来最好"的那一个越可能出现 ——
即使所有候选的真实效果完全相同。

`bonferroni_note(k, alpha=0.05)` 会算出校正后的阈值 α/k，并同时说明三件事。
**但它刻意不做完整的校正计算**，理由是：

1. 完整校正需要**全部**候选的 p 值列表，而阈值扫描 / L9 实验当前只保留"最优值" ——
   没有输入，算不出正确的校正结果
2. **更根本的问题是选择偏差，不只是门槛。** 即使做了 Bonferroni，
   那个最优配置仍是在同一批数据上挑出来的，效果估计依然偏高。
   真正要做的不是把门槛调严，而是**拿独立数据复验**
3. 目标是**把意识写进报告**，而不是给一个没人检查的校正 p 值

接入两处：`doe.recommend()` 的 `multiple_comparison_note`，
以及阈值扫描报告尾部（k 由循环**实际计数**得出，不写死）。

★ 措辞的分寸：**正交实验（L9 等）的定位本来就是筛选性**，不是验证性 ——
自由度有限，主效应之间可能存在混杂。所以报告写的是
"这是一个待验证的候选"，而不是"实测最优是 X"。

### 13.5 这一章解决的是什么

把四块放在一起看，它们守的是同一件事：

> **一个数字从"算出来"到"能用来说话"，中间隔着好几次判断。**

| 判断 | 不做会怎样 |
|---|---|
| 差异是不是真的 | 把噪声当成果（或把成果当噪声） |
| 错在哪一层 | 去修不该修的地方 |
| 置信度能不能用 | 分流策略建立在失效的信号上 |
| 挑最优的代价 | 引用一个系统性偏高的数字 |

而这些判断的共同点是：**跳过它们不会报错**。
数字照出、报告照生成、退出码 0 —— 只是结论悄悄错了。

这与本项目一贯的主题是同一条：
**最危险的失败不是崩溃，是看起来正常地错下去。**
