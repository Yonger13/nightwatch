# 04 · 评测设计

> 为什么说评测是这个项目最重要的模块，而不是收尾工作？

---

## 一、两组值得记住的数字

```
Gartner：到 2027 年底，超过 40% 的 Agentic AI 项目会被取消或降级
MIT Media Lab：95% 的企业 AI 试点未产生任何可衡量的财务回报（300 个部署样本）
IDC：AI 试点失败率 70%
```

结论很直接：**"做出来"的人很多，"能度量"的人极少。**

招聘数据也印证了这一点：在多份 Agent 岗位 JD 里，评测能力出现频次高、
且被明确列为"真正的分水岭"—— 同时它又是"培训班不教、也最难自己练"的东西。

**这就是你的稀缺性所在。**

## 二、三条纪律（写在代码里，也被测试守住）

### 纪律 1 · 不报单次最好成绩

大模型有随机性，跑一次的结果没有意义。做法：

- 每个样本跑 N 次（默认 3）
- 报**中位数**，不报平均值（平均值受极值影响大）
- 同时报 P95（长尾才是用户体验）

### 纪律 2 · 不只报赢的那组对比

如果 warm 组（带记忆）没有明显更好，要**如实说明并解释原因**。

代码里就是这样的：

```python
f1_change = result["F1变化"]["百分比"]
if f1_change != "N/A" and float(...) <= 0:
    print("⚠ 说明：本次对照中 F1 没有提升。")
    print("  可能的原因（必须如实说明，不能藏起来）：")
    print("    ① 合成数据的重复性不够高，记忆没发挥空间")
    print("    ② Mock 模型的'使用记忆'是规则分支，不代表真实模型的行为")
    print("    ③ 召回精度不足（相似度阈值/向量质量问题）")
```

**不报失败结果的评测不是评测。**

### 纪律 3 · 所有指标注明样本量和版本

```python
"样本量": len(results),
"confidence_interval_note": (
    f"样本量 {len(results)}，F1 的 95% 置信区间约为 ±"
    f"{wilson_margin(len(results)):.2f}；"
    f"样本量偏小时该指标不宜下强结论"
),
```

> **面试官真正看的是"这个人知不知道自己数字的边界在哪"**，
> 不是数字好不好看。

一个说"这个指标我只测了 30 条，置信区间很宽，不能下强结论"的候选人，
比一个报出漂亮数字却答不出实验设置的候选人可信度高得多。

## 三、为什么必须分层报告

假设 70% 的 issue 是 timeout 类，模型表现很好（F1 = 0.9）；
30% 是配置类，模型表现很差（F1 = 0.2）。

**总分是 0.69，看起来"还不错"** —— 但实际上有一整类问题它处理不了。

```
分层                样本      中位F1      最低F1      中位步数
────────────────────────────────────────────────────
config             2     0.833     0.667       1.0
crash              2     0.833     0.667       1.0
dependency         2     1.000     1.000       1.0
duplicate          2     0.667     0.667       1.0
feature            2     1.000     1.000       1.0
permission         2     1.000     1.000       2.0
timeout            2     1.000     1.000       1.0
unclear            2     0.000     0.000       1.0    ← 一整类处理不了
```

**最低 F1 这一列是重点** —— 它告诉你"最差的那一类有多差"。

而"要不要分层"这个决定本身，就体现了你有没有真的做过评测。

### 分层怎么分

先枚举问题类型，每类保证最少样本数：

```python
STRATA = {
    "timeout":    "超时、限流、性能问题",
    "permission": "权限、鉴权、访问控制",
    "config":     "配置错误、环境问题",
    "dependency": "依赖冲突、安装失败",
    "crash":      "崩溃、异常退出",
    "duplicate":  "重复问题（用于测判重能力）",
    "feature":    "功能请求（非 bug，需要区分出来）",
    "unclear":    "信息不足，应转人工",
}
```

**分层要来自真实数据，不是拍脑袋。** 第 0 周采集的标签分布就是依据
（见 [`01-第0周-观察真实项目.md`](01-第0周-观察真实项目.md)）。

## 四、duplicate 检测：为什么必须分四象限

```python
tp / fp / fn / tn      # 而不是一个准确率
```

因为**两类错误的代价不对称**：

| 错误 | 后果 | 严重程度 |
|---|---|---|
| 漏报（FN）真重复但没识别 | 维护者重复处理一遍，浪费一点时间 | 轻 |
| **误报（FP）** 不重复却说是重复 | 新问题被标记为"已解决"，**永远不会被处理** | **重** |

**所以阈值应该偏保守（宁可漏报，不要误报）。**

这个取舍是"业务理解"在指标设计上的体现 —— 它说明你不是在机械地调 F1。

## 五、最有区分度的实验：记忆效果对照

### 实验设计

同一批 issue，分两组跑：

```
fresh 组：记忆库为空（或屏蔽召回）
warm  组：记忆库已积累历史经验
对比：步数 / token / F1
```

**它直接回答"记忆到底有没有用"**，而不是笼统地说"我实现了记忆系统"。

### 三个设计要点

**① 唯一变量是记忆开关。**
同一批 issue、同一模型、同一工具集、同一个历史库。

**② warm 组的记忆来自"前一阶段"。**
先用前半批 issue 让系统积累记忆，再用后半批测 warm 表现。
这样测的是**真实的经验复用**，而不是"人为注入的记忆"。

**③ 报告必须包含没有提升的情况。**

### 实测输出

```
  指标                  fresh(无记忆)       warm(有记忆)            变化
  ──────────────────────────────────────────────────────────────
  步数                         3.0             2.0        -33.3%
  Token                   4234.5          2878.0        -32.0%
  F1                         1.0             1.0         +0.0%
```

**注意 F1 没有提升 —— 而报告如实写出了这一点并解释原因。**
（原因：合成数据的重复性不够高、Mock 模型的记忆使用是规则分支。）

## 六、实验单位：一个隐蔽但致命的选择

这是踩坑后修正的（见 [`05`](05-开发实录-真实缺陷复盘.md) 的 C2）。

| 做法 | 结果 |
|---|---|
| 每样本跑 N 次，每次新建记忆库 | 记忆永远为空 → **记忆类指标恒为 0** |
| **跑 N 遍完整批次，每遍一个新库** | 每遍内部记忆正常累积，各遍独立可比 ✓ |

```python
# 正确做法
for run_idx in range(runs):
    store = _new_store()                    # 每遍一个新库
    for issue in issues:
        ...                                 # 库内记忆正常累积
```

**教训**：

> **实验的"单位"选错了，指标就失去意义。**
>
> 这不只是实现问题，是"你想测什么"的问题。
> 要测"持续运行的系统"，实验单位就必须是"一段时间"，而不是"单次调用"。

修复后，记忆命中率从 0%（不可测）变成 28.6%（可测）。

## 七、阈值标定：从"经验值"到"扫出来的"

### 做法

`scripts/sweep_threshold.py` 扫 0.10 ~ 0.95，输出完整的 P/R/F1 曲线：

```
  阈值    TP   FP   FN   TN   precision  recall     F1
  0.25     3    7    0    8      0.300    1.000   0.462
  0.30     2    3    1   12      0.400    0.667   0.500  ← F1 最优
  0.35     1    1    2   14      0.500    0.333   0.400
  0.40     0    1    3   14      0.000    0.000   0.000
```

**但注意：不要直接用 F1 最优的那个值。** 还要看两类错误的代价
（误报严重得多，所以实际取值应该更保守）。

### 扫描暴露的更重要的问题

```
  重复样本的 top1 相似度:   0.2865 ~ 0.3612
  非重复样本 top1 相似度:   0.1101 ~ 0.4137     ← 两组重叠
```

**重叠意味着任何阈值都会有错误**，F1 的天花板就在 0.5 附近。

根因不是阈值选得不好，是**哈希伪向量的判别力不足**：

```
「接口在高峰时段频繁超时」vs「高峰时段接口超时（重复）」  → 真重复
「接口在高峰时段频繁超时」vs「定时任务偶发执行超时」      → 不是重复
三条都含"超时"，共享大量 bigram，哈希向量给出的相似度几乎一样
```

**结论**：正确的优化方向不是继续调阈值，而是换语义 embedding。
项目为此加了 `APIEmbedding`（设 `NW_LLM_API_KEY` 自动启用）。

### 这件事的价值

> "我扫了阈值"比"我用的 0.75"强得多。
>
> 但更强的是**发现"扫了也没用"** —— 并且能说清为什么没用、该怎么修。

这个"发现问题 → 定位根因 → 给出修复路径"的链条，
比一个漂亮但没来由的数字有价值得多。

## 八、LLM-as-Judge 的偏差处理

**这是必然会被问的问题。** 四件事，按重要性排序：

### ① 校准（最重要）

先人工标注一批，测裁判与人工的一致率。**一致率不够就不能用。**

```python
cal = JudgeCalibrator(min_agreement=0.7)
result = cal.agreement(judge_scores, human_scores)
if not result["可用"]:
    # 不是"凑合用"，是"不能用"
```

**为什么不能用**：一个不可靠的裁判比没有裁判更糟 ——
它会给你一个错误的信号，让你优化错方向。

### ② 拆细粒度

不评"回答得好不好"（主观、不稳定），而是拆成**可判定的子项**：

```python
"has_label":    是否给出了明确标签
"has_reason":   是否说明了理由
"has_citation": 是否给出了引用依据
```

**三个原则**：可判定（不是"好不好"，是"有没有"）、正交（不重复计量）、
少（3~4 个，多了会互相干扰）。

子项比整体判断稳定得多。

### ③ 位置偏差

做 A/B 对比评测时**交换顺序跑两次**，避免裁判偏心第一个。

### ④ 规则兜底

**能用确定性规则判的绝不用模型。**
比如"输出里是否包含禁用操作名" —— 规则没有随机性。

## 九、指标清单与口径

| 类别 | 指标 | 怎么测才公平 |
|---|---|---|
| **效果** | 自助解决率 | 定义写死："建议被采纳且正常关闭"才算，不能凭模型自评 |
| | 转人工率 | **单独统计** —— 它不是失败（见 `03` 文档） |
| | 误诊率 | 需要 ground truth；判据是"预测与维护者标注无交集" |
| | 平均收敛轮次 | 报中位数，并报 P95 |
| | 首次响应延迟 | 报 P50/P95，注明硬件和模型版本 |
| **记忆** | 记忆命中率 | 召回后被**实际使用**的比例 |
| | 无效召回率 | `1 - 命中率`。**这个指标最能暴露召回质量问题** |
| | 记忆准确率 | 抽取结果与人工标注的一致性，要报样本量和标注人数 |
| **长程** | 长程一致性得分 | 同一任务跑 5 轮 vs 50 轮，测初始约束的遵守率差异 |
| | 污染纠正速度 | 注入错误记忆，测经过多少次人工反馈能纠正 |
| **成本** | 单工单 Token | 拆分：主链路 vs 记忆抽取 |
| | 记忆开销占比 | 记忆相关 token / 总 token —— 成本意识的直接证据 |

### 一个反直觉的指标：无效召回率

只看"召回了几条"会误导你。有些记忆被频繁召回，
仅仅因为它的向量"吸引"了很多不相关查询（噪音吸铁石）。

实测中，没有召回门槛时**无效召回率高达 76.9%** ——
而那些无效召回**正在主动误导模型**（实测导致过分类错误），不只是浪费 token。

所以在 `Trace` 里同时记录两个数字：

```python
memory_recalled: list[str]   # 召回了哪些
memory_used:     list[str]   # 实际用了哪些
```

**而这要求 Agent 显式声明"我引用了哪条记忆"** ——
所以记忆渲染里带了 `记忆ID=ep_xxx`，并要求模型引用。
这不只是指标需求，也是可追溯性要求
（"某次判断当时依据了哪条记忆"必须能回答）。

## 十、防过拟合：三道防线

### ① 分层采样

保证稀有类型也有覆盖，不然评测集全是被简单样本刷出来的高分。

### ② 留出集

```python
DatasetBuilder(holdout_ratio=0.3)   # 30% 完全不参与调试
```

**调试期间不得使用 holdout**，最后只用它报数。

### ③ 数据来自真实来源且脚本化

评测集由脚本生成、进版本控制，别人能复现。
而不是手工挑几十条"看起来合适"的样本。

**并且必须诚实标注来源**：

```python
source="synthetic",
notes=("⚠️ 合成数据，仅用于跑通流程与演示。"
       "症状描述比真实 issue 规整，指标会虚高。"
       "**不要把这个数据集上的数字写进简历。**")
```

代码里还会在跑评测时**主动打印警告**：

```
⚠ 本次评测用的是合成数据 + Mock 模型。
  这些数字只能验证"流程正确"，**不能写进简历**。
```

## 十一、如何得到可写进简历的数字

```bash
# 1. 采集真实 issue
python scripts/collect_issues.py --repo owner/name --state closed \
    --limit 300 --save data/real_dataset.json

# 2. 配置真实模型与语义 embedding
export NW_LLM_API_KEY=sk-xxxx

# 3. 在留出集上跑最终数字
python scripts/run_eval.py --dataset data/real_dataset.json --real-llm --holdout

# 4. 重新标定阈值（换了 embedding 必须重标）
python scripts/sweep_threshold.py
```

### 报告里要写清的四件事

1. **数据来源**：哪个项目、多少条、ground truth 来自谁
2. **样本量**：以及由此带来的置信区间
3. **对照组设置**：唯一变量是什么
4. **已知限制**：哪些指标不可靠、为什么

## 十二、面试速查

| 问题 | 答题骨架 |
|---|---|
| 评测集怎么造的 | 分层采样 + 留出集 + 脚本化 + **来源诚实标注** |
| 会不会过拟合 | 三道防线；另外**主动说明价值偏差** |
| 记忆有效吗 | fresh vs warm 对照实验（唯一变量、同批样本、中位数） |
| 裁判偏差怎么办 | 校准（一致率不足就不用）→ 拆子项 → 换顺序 → 规则兜底 |
| 阈值怎么定的 | 扫出来的 + **发现阈值调不动所以换 embedding** |
| 你的数字可信吗 | 主动给出样本量和置信区间，说明哪些结论不能下 |

**最有说服力的一句**：

> 「这个指标我只在 16 条合成数据上测过，而且用的是哈希伪向量，
> 所以 F1 只能说明流程跑通了。要得到可用的数字，
> 需要真实 issue 队列 + 语义 embedding，那时阈值也要重新标定。」

—— 这句话证明的不是你的数字好，而是**你知不知道自己数字的边界**。
后者才是评测能力的真正体现。
