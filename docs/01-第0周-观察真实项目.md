# 01 · 第 0 周：先观察，再动手

> **这一周不写任何 Agent 代码。**
>
> 如果跳过这一步直接开写，你会做出一个"技术上正确、业务上无用"的东西。

---

## 为什么必须有这一周

业务场景调研里有一条明确的低 ROI 画像：

> 「**你自己都没搞清楚的流程** —— Agent 不会修复这个缺口，
> 它会立刻、反复地把它暴露出来。」

这句话的含义是：**Agent 是一个放大器。**
流程清楚，它放大效率；流程不清楚，它放大混乱。

具体到本项目，如果在没搞清楚"维护者实际怎么判断"的情况下就开始写分类逻辑，
会发生这些事：

- 你按自己的理解设计标签体系 → 和维护者实际用的对不上 → 准确率永远上不去
- 你不知道什么情况该判 duplicate → 阈值无从标定
- 你不知道哪类问题必须转人工 → 系统会自信地给出错误建议

## 第 0 周的四件事

### 任务 1 · 采集并看统计（半天）

```bash
# 先不保存，只看统计
python scripts/collect_issues.py --repo <你选的项目> --limit 200 --stats
```

**选什么项目**？四个标准：

| 标准 | 为什么 | 怎么判断 |
|---|---|---|
| 活跃 | 有持续的新 issue，说明流程在运转 | 最近一周有提交 |
| 标签规范 | ground truth 的质量决定评测的可信度 | 看 issue 列表里标签是否普遍 |
| 规模适中 | 太大采不全，太小样本不够 | 历史 issue 几百到几千 |
| 你熟悉领域 | 你能判断维护者的判断对不对 | 你用过或了解这个项目 |

**看统计时重点看这四个数字**：

```
【标签分布】有标签 X/Y 条（Z% 无标签）
```
→ **无标签超过 30% 就换项目。** 因为 ground truth 太少，评测没有意义。

```
【重复】显式标记为重复的 N 条（M%）
```
→ 低于 3% 说明 duplicate 检测在这个项目上收益有限，
可以考虑把精力放在分类准确率上（**这是一个真实的项目决策**，不是逃避）。

```
【提交者集中度】
```
→ 如果头部提交者占比高（>20%），"按作者精确召回"这条路有实际价值。
如果很分散，就应该更依赖语义召回。

```
【堆栈信息】含报错堆栈的 N 条
```
→ 占比高说明可以依赖堆栈做相似度检索；占比低就要靠标题和正文。

### 任务 2 · 人工通读 30~50 条（1~2 天）

**这是这一周最重要的任务，不能省。** 用 Excel 或 Markdown 表格记录：

| issue | 标题 | 维护者打的标签 | 关/开 | 如果是重复，依据是什么 | 我能不能自己判断出来 |
|---|---|---|---|---|---|
| #101 | 接口超时 | bug/timeout | closed | — | 能 |
| #112 | 高峰时段超时 | duplicate | closed | 正文提到 #101 | 能 |
| #117 | 用不了 | needs-info | closed | 信息不足，要求补充 | 能（但要判断"够不够"） |

**最后一列是关键**：如果某条你自己都判断不出来，那 Agent 也不该被要求判断出来 ——
这类样本属于"应该在评测集里标为转人工"的。

### 任务 3 · 画流程（半天）

画出「一个 issue 从提交到关闭」的完整路径，包括**维护者在每一步做什么判断**：

```
新 issue 提交
    ↓
维护者看标题 → 能判断类型吗？
    ├─ 不能 → 要求补充信息（needs-info）→ 等待 → 回到判断
    └─ 能 ↓
判断是否重复 → 检索相似 issue
    ├─ 是重复 → 标记 duplicate → 关闭
    └─ 否 ↓
分类打标签 → bug/timeout, bug/config...
    ↓
分派处理 / 或标记 wontfix / 或保持 open
```

**这张图就是你后面所有设计的依据**：
- "判断类型"这一步 → Agent 的分类能力
- "判断是否重复"这一步 → duplicate 检测
- "要求补充信息"这一步 → 低置信度转人工
- 每一步的输入输出 → 决定了要哪些工具

### 任务 4 · 自检三问（1 小时）

在动手写代码前，确认你能回答：

1. **这个项目的标签体系里，最容易混淆的是哪两个？**
   （如果你答不上来，说明读得不够。这个答案会直接决定你的关键词表。）

2. **维护者在什么情况下判 duplicate？依据是什么？**
   （是"症状相同"还是"根因相同"？这两者的判定难度差很多。）

3. **哪一类问题你想让 Agent 处理，哪一类必须转人工？**
   （这个边界就是你系统的能力边界。**能说清楚边界比声称全能更有说服力。**）

**答不上来就继续读。** 这一周多花的每一天，都能在后面省下三天。

## 采集之后：数据准备

```bash
# 正式采集（建议只采集已关闭的 —— 关闭的 issue 才有完整的处理链条）
python scripts/collect_issues.py \
    --repo <你的项目> \
    --state closed \
    --limit 300 \
    --save data/real_dataset.json
```

**为什么优先用 closed**：
- 已关闭的 issue 有完整的「问题 → 判断 → 处置」链条，是更好的样本
- open 的 issue 可能还在处理中，维护者的判断还没做完（ground truth 不完整）

**采完之后要检查一件事**：数据集里的 `gold_labels` 是不是真的来自维护者。
用几行代码确认：

```python
import json
d = json.load(open("data/real_dataset.json", encoding="utf-8"))
for item in d["train"][:5]:
    print(item["issue_id"], item["gold_labels"], "|", item["gold_action"])
```

如果你看到大量 `[]`（空标签），说明这个项目的维护者打标不积极，
需要换项目或扩大采样量。

## 关于 ground truth 的诚实说明

**维护者打的标签 ≠ 绝对正确答案。** 它有三个局限，写文档和面试时都要说清楚：

1. **数据缺失**：有些 issue 维护者根本没打标签
2. **机器人标注**：自动化工具（dependabot、stale bot）会按规则打标签、关 issue，
   那不是人类判断（`collect_issues.py` 里有 `is_bot()` 过滤，但不可能 100% 干净）
3. **标准不一致**：不同维护者对同一个问题的分类可能不同

所以正确的表述是：

> ✓「ground truth 来自维护者的标注」
> ✗「正确答案」

这个区别很小，但它体现的是**你知不知道自己数据的边界**。

## 常见错误

**错误 1：跳过这一步，直接开写**

结果：做出一个能跑但没法评估的东西。因为不知道该测什么、拿什么当标准答案。

**错误 2：选了一个维护者不打标签的项目**

结果：采集了几百条 issue，但 ground truth 覆盖率只有 20%，评测集建不起来。

**错误 3：只采数据，不通读**

结果：你不理解维护者的判断逻辑，于是你的 Agent 逻辑和真实业务对不上。
**表现为"指标还行但维护者不用"** —— 这是最尴尬的失败。

**错误 4：把"我熟悉这个领域"当成"我了解这个项目的流程"**

你对某个开源库很熟 ≠ 你知道它的维护流程。
流程是**人**的行为，必须观察。
