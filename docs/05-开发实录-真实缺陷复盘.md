# 开发实录：从"能跑"到"可靠"的 13 个修复

> **这是本项目最有教学价值的一篇文档。**
>
> 它记录的不是"我怎么设计的"，而是"我的设计错在哪里、怎么发现的、怎么修的"。
>
> 为什么这比设计文档更有价值？因为设计文档展示的是**意图**，而这篇展示的是
> **现实**。一个 Agent 项目从"能跑通"到"可信赖"，中间隔着十几处
> **不会报错、只会静默出错**的地方 —— 而发现它们的能力，比写出它们的
> 能力更稀缺。

---

## 为什么这些 bug 特别危险

普通程序的 bug 分两种：崩溃（你会立刻知道）和逻辑错误（测试会发现）。

但 Agent 项目的 bug 有第三种：**系统正常运行、日志没有异常、指标看起来正常，
只是效果悄悄变差。**

本文里的 13 个缺陷，有 8 个属于这一类。举两个例子：

- 记忆库明明在工作，但因为评分公式的一个细节，**所有记忆都被筛掉了** ——
  系统不报错，只是"记忆功能实际上等于不存在"
- 评测跑出了 F1 = 0.000，看起来像"模型完全不会分类"，
  实际是**评测代码的标签格式没对齐** —— 而你会花几天去调模型

**这类问题的共同解法是：让系统可观测。** 没有 trace 和诊断脚本，
你连"记忆库到底有没有写进去"都不知道。

## A 类 · 解析与格式

### A1. `re.DOTALL` 让字段跨行污染

**现象**：记忆抽取出来的 `symptom` 字段里，装的是整篇提示词的文本。

**根因**：

```python
re.search(r"(?:症状|symptom)[:：]\s*(.{0,120})", text, re.DOTALL)
#                                              ^^^^^^^^^^^^^^^^
#                                              `.` 跨过了换行符
```

`.` 默认不匹配换行 —— 加上 `DOTALL` 之后就会，于是 `(.{0,120})` 从
"症状：" 一路吃到了后面的所有内容，包括下一段 `【处理过程与结论】` 和根因字段。

**修复**：显式把字段边界限定在行内，不要靠贪婪/非贪婪去猜边界。

```python
re.search(r"(?:症状|symptom)[:：][ \t]*([^\n]{2,150})", text)
#                                       ^^^^^ 显式不跨行
```

**教训**：

> 解析结构化文本时，**字段边界要显式限定**。
> `.` 加 `DOTALL` 是一种"我很确定这个字段不会换行"的假设 ——
> 而提示词拼接出来的文本，永远会有你没预料到的换行。

### A2. 标签格式不对齐，导致 F1 恒为 0

**现象**：评测跑出来 Precision / Recall / F1 全部是 `0.000`。

第一反应是"模型完全不会分类"。但这个想法是错的。

**根因**：

```
ground truth（维护者打的）:  "timeout"
我的预测                :  "bug/timeout"
```

集合取交集 → 空集 → F1 = 0。

**修复**：在指标计算前做标签归一化。

```python
@classmethod
def normalize_label(cls, label: str) -> str:
    s = str(label).strip().lower()
    for sep in ("/", ":", "-", "_", " "):
        s = s.replace(sep, "|")
    parts = [p for p in s.split("|") if p]
    # 剥掉通用命名空间前缀（bug / kind / type ...）
    for p in reversed(parts):
        if p not in cls._PREFIXES:
            return p
    return parts[-1]
```

**教训**：

> **当指标恰好等于 0 或 1 时，先怀疑评测代码，再怀疑模型。**
>
> 完美的 0 和完美的 1 都是可疑信号 —— 真实系统的指标很少这么极端。
> 这个判断顺序很重要：前者改代码就能修（几分钟），后者要改模型和提示词（几天）。
> 搞反了就会在错误的方向上优化很久。

这条经验后来被固化成了单元测试 `test_标签归一化`。

### A3. 文件指针包在括号里，导致读不回来

**现象**：上下文演示里显示"已卸载"，但按指针读回文件时返回空字符串。

**根因**：

```
...(见 offload://read_code_abc123.txt)
                    ↑ 提取指针的正则会把右括号一起吃进来
```

`offload://(\S+)` 匹配到 `read_code_abc123.txt)` —— 因为 `)` 不是空白字符。
于是路径错误 → 文件不存在 → **静默返回空字符串**。

**修复**：机器要解析的字段，单独占一行，格式明确。

```
[read_code] 结果过大已卸载
摘要: ...
文件指针: offload://read_code_abc123.txt
尾部: ...
```

**教训**：

> **不要为了排版好看，把机器要解析的字段塞进句子里。**
>
> 而且注意这个 bug 的危险性：读取失败返回的是空字符串，不是异常。
> 如果调用方不做长度检查，表现就是"Agent 突然忘了刚才读到的东西" ——
> 又是一次静默失效。

## B 类 · 逻辑与设计

### B1. Agent 自己判自己重复

**现象**：处理 `#202` 时，输出"与 #202 高度相似，建议按重复处理"。

**根因**：判重逻辑从上下文里用正则找 issue 编号：

```python
m = re.search(r"#(\d+)", ctx)          # 第一个匹配到的就是它自己
```

而"当前正在处理的 issue 编号"本来就在上下文里（任务状态卡中），
所以第一个匹配的就是自身。

**修复（两层）**：

1. 工具层排除：`ToolRegistry.current_issue_id`，检索时跳过
2. 输出层双保险：`_compose_answer` 里再次比对 `current_id`

**教训**：

> **任何"从上下文里提取实体 id"的逻辑，都必须显式排除"我自己"。**
>
> 这个坑在真实项目里同样常见 —— 比如拼接历史记录时把当前记录也拼进去了，
> 或者在用户的历史数据里查"和当前这条最像的是哪条"，结果返回它自己。

### B2. `UNKNOWN = 0.5` 让记忆系统整体失效

**现象**：跑的每个 issue 都不写记忆。记忆库永远是 0 条。

**根因**（诊断脚本输出）：

```
✗ 抽取成功但未写入: score=0.535 阈值=0.55
  scores={'reusability': 0.7, 'causal_depth': 0.3,
          'non_triviality': 0.6, 'human_signal': 0.5}
```

`human_signal = 0.5`，因为它被设计成"没有人工反馈时的中性值"。

代入加权和：

```
0.35×0.7 + 0.25×0.3 + 0.25×0.5 + 0.15×0.6 = 0.535   <  0.55
```

**问题不在于差那 0.015，而在于设计思路错了**：

在没有人给反馈的场景下（离线评测、自动化批处理 —— **恰好是最常见的状态**），
`human_signal` 永远恒定为 0.5，它不携带任何信息，
却凭着 0.25 的权重**稀释**了其他三个真实信号。

**修复**：区分「没有信号」和「中性的信号」。

```python
# 没有反馈 → 返回 None（而不是 0.5）
HumanVerdict.UNKNOWN: None
```

```python
# Scorer 里只对"有信号"的因子做加权平均
available = {k: float(v) for k, v in s.items() if k in w and v is not None}
total_w = sum(w[k] for k in available)
total = sum(w[k] * v for k, v in available.items()) / total_w
```

修完之后：`(0.35×0.7 + 0.25×0.8 + 0.15×0.6) / 0.75 = 0.713` ✓

**教训**：

> **不要把"缺失"编码成"中间值"。**
>
> 缺失就是缺失，用 `None` / `NaN` 表达，让下游显式处理它。
> 用 0.5 或 0 代替缺失，是"看起来方便、实际上会污染计算"的经典做法。
>
> 这条原则不只适用于打分：缺失的年龄不要填平均年龄，
> 缺失的评分不要填 3 星，缺失的指标不要填中位数。

### B3. 上游少输出一个字段，下游整个模块失效

**现象**：B2 修复后，分数是 `0.713` 了 —— 但只在"能抽到根因"的样本上成立。
实际跑评测时，抽到的根因永远是空。

**根因**：这是一条**跨模块的链式依赖**：

```
主循环的输出结构（summary 里没有"根因："这一行）
        ↓
记忆抽取抓不到 root_cause 字段
        ↓
causal_depth = 0.3（而不是 0.8）
        ↓
总分 0.535 < 阈值 0.55
        ↓
所有记忆都被筛掉 → 记忆系统等于不存在
```

**上游少写一个字段，下游一个模块就整体失效。** 而且每个模块单独看都没问题。

**修复**：让主循环的输出里包含根因字段，并且明确它是下游的记忆输入契约。

```python
return {
    "predicted_labels": labels,
    "duplicate_of": dup or "",
    "root_cause": root_cause,          # ★ 下游记忆抽取需要它
    "summary": f"根因：{root_cause}。..." ,
    ...
}
```

**教训**：

> **Agent 的最终输出结构不是"随便写写"，它同时是下游系统的输入契约。**
>
> 这类 bug 只有通过**端到端跑一遍并检查副作用**才能发现 ——
> 单测每个模块都过，因为每个模块本身是对的。

### B4. 混合排序不同量纲的分数，导致判重错乱

**现象**：duplicate 检测完全不触发，或者触发到错误的 issue 上。

**根因**：`_search_similar` 把两个来源的结果混在一起排序：

```python
history_issue:    similarity                              # 纯余弦相似度 [0,1]
episodic_memory:  similarity × (0.5 + 0.5 × decay_weight) # 被衰减权重缩放过
```

**两个分数的量纲不同**，混排之后"一条衰减权重高的记忆"可以轻易压过
"一条真正重复的 issue"。整个判定就变成了噪声。

更深一层的问题是概念错位：

> **"重复"是 issue 与 issue 之间的关系。**
> 记忆里存的是"我们以前怎么处理这类问题"，它是经验，不是待比对的报告。
> 用经验去判定"这条新报告是否重复"，概念上就是错位的。

**修复**：判重只看 `history_issue` 来源。

```python
issue_items = [x for x in items if x.get("source") == "history_issue"]
top_issue = issue_items[0] if issue_items else None
likely_dup = (top_issue["issue_id"]
              if (top_issue and top_issue["similarity"] >= 0.30) else None)
```

**教训**：

> **排序前先确认所有候选的分数是可比的。**
>
> 不同来源、不同归一化方式的分数混在一起排序，
> 是排序类 bug 最常见的来源。如果一定要混排，先做归一化。

**修复效果**：duplicate F1 从 `0.000` → `0.800`。

### B5. 记忆召回没有门槛，错误记忆主动误导模型

**现象**：一个内容只有"有 bug"的 issue，被分类成了 `bug/config`。
而正确答案是"信息不足，转人工"。

**根因**：`_prefetch_memory` 无条件取 top_k —— 只要库里有记忆就注入。

那个内容为"有 bug"的 issue 检索到了完全不相关的记忆，
然后**模型照着那条记忆的标签给它分类**。

**这是记忆系统特有的风险：**

> **错误的召回比不召回更糟 —— 因为模型会相信上下文里的一切。**

没有门槛的召回，等于往提示词里灌噪音。而噪音不只是浪费 token，
它是在**主动误导模型**。

**修复**：加召回相似度门槛。

```python
min_sim = self.settings.memory.get("recall_min_similarity", 0.30)
for mem, score in self.store.recall(...):
    if score < min_sim:
        continue
```

**教训**：

> **召回要有门槛，注入要有判断。**
>
> 这也解释了「无效召回率」这个指标为什么重要：
> 在没有门槛的情况下它会非常高（实测 **76.9%**），
> 而那些无效召回**正在主动误导模型**。

**修复效果**：无效召回率从 100% 降到 71.4%，unclear 类不再被错分。

### B6. 人工确认过的记忆被时间衰减归档

**现象**：单元测试 `test_人工确认过的记忆不被轻易归档` 失败。

一条被工程师明确 `ACCEPTED` 的经验，400 天后权重降到 0.03，被系统当垃圾归档了。

**根因**：衰减公式是纯时间的：

```python
weight = time_decay × effectiveness × authority_bonus
# 400 天 / 半衰期 90 天 → time_decay = 0.5^4.44 = 0.046
```

**这个公式的隐含假设是"旧信息更可能过时"。** 但对"被人工验证过的结构性经验"
这个假设不成立：

- **验证过是对的**，这件事本身价值很高，而验证成本很高
- 这类经验通常描述**稳定事实**（架构缺陷、协同模式），
  不是易变状态（客户配额、版本号）

**修复**：给人工确认过的记忆加权重下限。

```python
if mem.human_verdict in (HumanVerdict.ACCEPTED, HumanVerdict.EDITED):
    weight = max(weight, 0.25)
```

**教训**：

> **纯数学的公式不知道领域知识，得靠设计者补上。**
>
> 衰减公式不知道"这条经验被人验证过"意味着什么。
> 把领域知识显式写进公式，是设计工作的一部分，不是"调参"。

### B7. 只读工具绕过沙箱，导致异常分类丢失

**现象**：读一个越权路径，返回的错误类型是 `unknown` 而不是 `permission`。

**根因**：

```python
if tool.readonly:
    try:
        return ToolResult(ok=True, data=tool.handler(**args))
    except Exception as e:
        return ToolResult(ok=False, error=str(e), error_kind="unknown")  # ← 一律 unknown
```

只读工具没走沙箱，也就没走沙箱的**异常翻译**逻辑。

后果：`permission` 这类**本该快速失败、不该重试**的错误被标成 `unknown`
（可重试），于是重试机制会对它反复重试三次。

**修复**：只读工具也走 `sandbox.run()`。

```python
if tool.readonly:
    return self.sandbox.run(lambda: tool.handler(**args))
```

**教训**：

> **异常分类是横切关注点，不要因为"没有副作用"就绕过它。**
>
> 沙箱的价值不只在隔离，还在于它把异常翻译成了**可重试性分类** ——
> 而这个分类决定了重试机制的行为。

## C 类 · 流程与工程

### C1. Mock 的决策逻辑与循环的观察格式不匹配

**现象**：Agent 跑满 20 轮上限都没收敛，每次都走兜底。

**根因**：Mock 判断"下一步做什么"的依据是上下文里的特定字符串：

```python
if "已检索相似历史" in ctx:      # ← 循环里写入的是 "动作: search_similar_issues(...)"
    return finalize
```

**两边对同一个事实用了不同的表达方式**，于是条件永远不成立，
Agent 永远在"还没检索过"的状态里打转。

**修复**：改用**基于实际痕迹**的判断，而不是基于约定的标记字符串。

```python
called_similar = "search_similar_issues(" in ctx   # 搜工具调用痕迹
called_docs = "search_docs(" in ctx
```

**教训**：

> **跨组件的隐式约定是 bug 温床。**
>
> "我写 A 字符串，你读 A 字符串"这种约定没有类型检查、
> 没有编译期保障，改一边忘另一边就静默失效。
> 尽量改用**可验证的痕迹**（工具真的被调用过）而不是**约定的信号**。

**修复效果**：步数从 20（触顶）降到 3。

### C2. 评测的实验单位选错，指标恒为 0

**现象**：`记忆质量` 一栏永远显示"总召回 0 次"。

**根因**：评测的实现是"每个样本跑 N 次，每次新建记忆库"：

```python
for issue in issues:
    for r in range(runs):
        store = MemoryStore(":memory:")     # ← 每次都是空的
```

**记忆永远不会累积**，所以永远没有东西可召回。

**修正后的理解**：

| 做法 | 结果 |
|---|---|
| 每样本跑 N 次，每次新建 store | 记忆永远为空 → 记忆类指标恒为 0 |
| **跑 N 遍完整批次，每遍一个新 store** | 每遍内部记忆正常累积，各遍之间独立可比 ✓ |

**教训**：

> **实验的"单位"选错了，指标就失去意义。**
>
> 这不只是实现问题 —— 它是"你想测什么"的问题。
> 如果你想测"持续运行的系统"，实验单位就必须是"一段时间"
> 而不是"单次调用"。

**修复效果**：记忆命中率从 0% → 28.6%（可测量了）。

### C3. 阈值没有数据支撑

**现象**：duplicate 判定阈值最初写的是 `0.75` —— 一个看起来合理的"经验值"。

**问题**：没有任何依据。面试被问"这个阈值怎么定的"时只能答"经验值"。

**做法**：写一个扫描脚本，扫 0.10~0.95，输出完整的 P/R/F1 曲线。

结果（`scripts/sweep_threshold.py` → `data/_thr_sweep.txt`）：

```
  阈值    TP   FP   FN   TN   precision  recall     F1
  0.25     3    7    0    8      0.300    1.000   0.462
  0.30     2    3    1   12      0.400    0.667   0.500  ← F1 最优
  0.35     1    1    2   14      0.500    0.333   0.400
```

**而且扫描暴露了一个更重要的问题**：

```
  重复样本的 top1 相似度:   0.2865 ~ 0.3612
  非重复样本 top1 相似度:   0.1101 ~ 0.4137     ← 两组重叠
```

**重叠意味着任何阈值都会有错误**，F1 的天花板就在 0.5 附近。

根因不是阈值选得不好，是**哈希伪向量的判别力不足** ——
它分不清"同一个问题"和"碰巧都含『超时』这个词"：

```
「接口在高峰时段频繁超时」vs「高峰时段接口超时（重复）」  → 真重复
「接口在高峰时段频繁超时」vs「定时任务偶发执行超时」      → 不是重复
三条都含"超时"，共享大量 bigram，哈希向量给出的相似度几乎一样
```

**结论**：正确的优化方向不是继续调阈值，而是**换语义 embedding**。
项目为此加了 `APIEmbedding`（设 `NW_LLM_API_KEY` 自动启用）。

**教训**：

> **"我扫了阈值"比"我用的是 0.75"强得多。**
>
> 但更强的是**发现"扫了也没用"** —— 并且能说清为什么没用、该怎么修。
> 这个"发现问题 → 定位根因 → 给出修复路径"的链条，
> 比一个漂亮但没来由的数字有价值得多。

### C4. 诊断脚本本身写错了（元问题）

## D 类 · 实验设计（做长程一致性压测时踩的）

> 这一类的问题有个共同特点：**它们不是代码 bug，是实验方法的 bug。**
> 而实验方法的 bug 比代码 bug 更危险 —— 因为它会让你**基于错误的数据做出正确的推理**，
> 最后得到一个错误但看起来很有道理的结论。

### D1. 证据采集位置错误，导致误判"实验无效"

**背景**：做长程一致性压测时，脚本要报告"上下文压力是否形成"的证据
（驱逐次数 / 压缩次数），否则无法说明"约束为什么丢了"。

**现象**：第一次跑，所有组的驱逐和压缩都是 0：

```
  [7/8] padding=40  状态卡=开 ... 遵守率 100.00%  驱逐 0  压缩 0
  [8/8] padding=40  状态卡=关 ... 遵守率 100.00%  驱逐 0  压缩 0
```

看起来像是"状态卡没用"（两组都 100%）。

**根因**：证据取的是**最后一次 build** 的数据：

```python
usage = result.trace.context_usage[-1]        # ← 最后一次
"evicted": len(usage.get("evicted", [])),
```

但**信息丢失发生在第一次 build** —— 那时 history 最长（约束 + 40 条 padding），
触发了压缩/驱逐。之后历史被压短了，后续几轮自然不再触发。

所以 `[-1]` 看到的是"灾难之后"的状态，什么都看不到。

**修复**：累加所有轮。

```python
usage_list = result.trace.context_usage or []
"evicted": sum(len(u.get("evicted", [])) for u in usage_list),
"compressed": sum(len(u.get("compressed", [])) for u in usage_list),
```

修完后立刻看到了证据：累计驱逐 444 次、压缩 18 次。

**教训**：

> **采集"是否发生过"的证据时，要看全过程，不能只看终态。**
>
> 这和"只看最终指标不看过程指标"是同一类错误。
> 一个只在终态才检查的系统监控，会漏掉所有的瞬时故障。

---

### D2. 对照组设计缺陷：你以为只改了一个变量，其实改了俩

**现象**：修好 D1 后，差异出现了（无状态卡组掉到 33%）。
但在这之前还有一轮**更隐蔽**的问题：

第一版对照组只往 history 里写了"约束"，**没写当前 issue 信息**：

```python
# 第一版（有问题）
ctx.add_history(
    "[任务约定]\n目标：...\n硬约束：① 判重优先 ② 不得编造根因 ③ 必须给出引用"
)
```

而实验组的状态卡里**同时包含** issue 信息和约束。

于是两组的差异实际上有**两项**：

| | 实验组 | 对照组 | 差异 |
|---|---|---|---|
| 当前 issue 信息 | ✅（在状态卡里） | ❌ | **混淆变量** |
| 约束是否每轮重注入 | ✅ | ❌ | 想测的变量 |

结果：对照组连"当前在干什么"都不知道 ——
症状提取抓不到标题、检索用错 query、判重检查根本不触发。
测出来的差异有一部分来自"任务信息缺失"，不是"约束漂移"。

**修复**：让两组的差异**只有一项**。

```python
# 修复后：也写 issue 信息，格式和状态卡保持一致
ctx.add_history(
    f"[任务说明]\n"
    f"标题：{issue.title}\n"
    f"编号：{issue.issue_id}　提交者：{issue.author}\n"
    f"报错堆栈：...\n"
    f"目标：...\n"
    f"硬约束：① 判重优先 ② 不得编造根因 ③ 必须给出引用"
)
```

**教训**：

> **设计对照组时，要逐项列出两组的所有差异，而不是只想"我要变的是什么"。**
>
> 一个简单的自检方法：把两组的输入**并排打印出来 diff 一遍**。
> 如果有任何非预期的差异，实验结论就不成立。
>
> 这类错误在 A/B 测试里极其常见 ——
> "我们改了按钮颜色"，但实际上连文案也顺手改了。

**而且这里还有一个副产品**：修完之后发现，两组的**驱逐次数完全相同**（17 次、57 次）：

```
    轮数   状态卡   累计驱逐   累计压缩
    60      关       17        1
    60      开       17        1        ← 压力完全一样
```

这比"只给实验组压力"严谨得多 —— 它证明差异**只来自约束放在哪个桶**，
而不是来自"两组承受的压力不同"。

### D3. 附注：两次测试预期写错，暴露了我对自己设计的理解偏差

写长程一致性的单元测试时，有两次断言失败了 —— 而两次**都是我的预期错了**，实现是对的。

**第一次**：我预期"不适用的检查不计入分母"时 `checks_run = 3`，
实际是 2。因为 `_check_tool_loop` 在没有 trace 时也不计数 ——
也就是说"不适用就不计入"这条原则在**两个地方**都贯彻了，而我只想到了一处。

**第二次**：我预期"低置信 + 无引用"的 `adherence = 1.0`，实际是 0.5。
因为我下意识把"没给引用"和"置信度低"当成了一件事（觉得"既然承认不知道了，
没引用也情有可原"），但实现里它们是**两条独立的约束**：
- 诚实地说不知道（低置信）→ 值得肯定，不违规
- 没给依据 → 仍然是缺陷

**教训**：

> **测试失败时，先问"是我预期错了还是实现错了" —— 而答案经常是前者。**
>
> 这不是坏事。测试的价值之一，就是**逼你把"我以为的设计"和"实际的设计"对齐**。
> 两次失败都让我更清楚地理解了自己的约束模型 ——
> 一次发现了"不适用不计入"适用范围比我想的更广，
> 一次发现了"诚实"和"有据"是两个独立的维度。

## E 类 · 真实模型上线后暴露的问题

> 这一类的问题有个共同特征：**在 Mock 上永远不会出现。**
> 因为 Mock 是"按设计输出"，而真实模型"按它自己的理解输出"。
> 所以它们是"Mock 能验链路、不能验健壮性"的具体证据。

### E1. 实验设计漏掉了 system prompt 里的约束

**现象**：长程一致性压测的第一版在 Mock 上效果很好（差 66.67%），
但换到**真实模型**上几乎测不出差异 —— 两组都是 100%。

**根因**：`SYSTEM_PROMPT` 里本来就写着 5 条判断准则：

```
## 判断准则
1. 先查再判
2. 判重优先于分类
3. 允许不确定
4. 不要重复调用同一个工具
5. 给出依据
```

而 **system 桶是不可压缩的** —— 所以约束始终在上下文里。

也就是说：对照组（关掉状态卡）**不是"没有约束"，只是"少了一份每轮重申的强调"**。

**修复**：加第三组对照，把 system prompt 里的约束也拿掉，构成真正的基线。

```
A. system有约束 + 状态卡      ← 完整设计（生产环境用这个）
B. system有约束 + 无状态卡    ← 分离出状态卡的贡献
C. system无约束 + 无状态卡    ← 真的没有保护
```

有了 C 组，才能做**逐层贡献分解**：

```
C → B   system prompt 里那份约束值多少
B → A   任务状态卡的增量值多少
```

**教训**：

> **设计对照实验时，必须把"这个变量在系统里所有的出现位置"都列出来。**
>
> 我改了状态卡，却忘了 system prompt 里还有一份 ——
> 这和 D2 号缺陷（对照组混淆了任务信息）是同一类错误的两个变体：
>
> **D2 是"多改了一个变量"，E1 是"少改了一个变量"。**
> 两者都会让实验结论失效，而且都不会报错。

### E2. 真实模型把 `action` 输出成对象，导致崩溃

**现象**：真实模型压测跑到最后一格崩了：

```
TypeError: unhashable type: 'dict'
  at reliability.py:152  is_open(tool_name)
```

**根因**：模型有时把 `action` 输出成**对象**而不是字符串：

```json
{"thought": "...",
 "action": {"name": "search_similar_issues",     ← 对象，不是 "search_similar_issues"
            "params": {"query": "..."}},
 "action_input": {}}
```

而下游（熔断器、工具路由）都假设 `action` 是字符串 —— 于是 `dict` 作为字典键时报错。

**原代码的问题**：

```python
if isinstance(d, dict) and "action" in d:
    return d          # ← 只检查 key 在不在，没检查类型
```

**修复**：加一层 `_validate_decision`，做两件事：

1. **尽力修复** —— 从对象里按常见键名（`name` / `tool` / `tool_name` / `function`）
   提取工具名，顺便把参数从 `params` / `arguments` 里捞出来
2. **救不回来就返回 None** —— 走"解析失败"分支，把错误反馈给模型重试

**为什么要"修复"而不是直接判失败？**
因为模型输出不规范是**预期内的常态**，不是异常情况。
能自动纠正的就不该浪费一次重试。

**教训**：

> **解析模型输出时，每个字段都要校验类型，不能只检查 key 存在。**
>
> `"action" in d` 只保证有这个键，不保证值是字符串。
> 而这个疏漏的后果是：**在很远的地方崩，报错信息毫无线索**
> （`unhashable type` 完全看不出是"模型把 action 写成了对象"）。

**而且这个 bug 只有真实模型能暴露** —— Mock 永远输出规范的字符串，
因为它是按我的设计写的。这就是"Mock 能验链路、不能验健壮性"。

### E3. 真实数据推翻了 Mock 给出的乐观结论

**现象**：同一套脚本、同一个场景，Mock 和真实模型的结果差距很大：

| 组 | Mock @100 轮 | 真实模型 @100 轮 |
|---|---|---|
| A（完整设计） | 100% | 100% |
| B（无状态卡） | **33.33%** | **83.33%** |
| C（无保护） | 33.33% | 66.67% |

**Mock 高估了状态卡的价值**：它测出 B→A 差 66.67%，而真实只有 16.67%。

**根因**：Mock 的 `has_constraint` 判断是字符串匹配：

```python
has_constraint = ("硬约束" in ctx) or ("必须给出引用依据" in ctx)
```

这两个字符串**只出现在状态卡和对照组任务说明里**，
所以 Mock 一旦看到状态卡被驱逐，就立刻"全盘漂移"。

而**真实模型能读懂 system prompt 里的完整准则** ——
它即使看到状态卡没了，也还记得"要给出依据"。

**所以：Mock 的漂移是"全有全无"（开关式），真实模型的漂移是"渐变的、部分的"。**

**这个发现的价值**：

> **Mock 能验证机制（链路通不通），但不能验证效果（设计值不值）。**
>
> 而且——**真实数据可能推翻 Mock 给出的结论**。
> 如果我只跑 Mock 就下结论"状态卡带来 66.67% 的提升"，
> 那这个数字在面试被追问时会站不住（因为真实场景下它只有 16.67%）。

**附带的一个更强的发现**：C 组（完全无约束）的过程指标很说明问题 ——
**步数恒为 20（触顶）、引用 0 条、置信度 0.00**。
它不是在"违反约束"，而是**根本完不成任务**。

这比我原先设想的结论更强：

> system prompt 里的约束不只是"提高遵从度"，而是**让任务可完成的基础**；
> 状态卡则提供长任务的额外保护（+16.67%）。

**这个结论是数据给的，不是我想出来的。** 这就是做真实实验的意义。

## F 类 · 模型选型：以为换更快的模型是优化，实测打脸

> 这一类只有一个案例，但它直接印证了业务调研里的那条反直觉结论：
> **"能力最强、成本最高的模型配置反而表现最差"——反过来同样成立：
> "更快更便宜的模型"也不一定够用。**

### F1. 换成 `qwen3.8-flash` 后，指标掉了 33%，还慢了 5 倍

**背景**：用户要求在 `.env` 里把默认模型改成 `qwen3.8-flash`。

**第一反应是错的**：

我看到这个名字就想"这不对吧，公有云叫 `qwen-flash`，没有 `qwen3.8-flash`"。
但实测**三档全部通过**（3471ms / 1593ms / 2722ms）——
因为用户的 base_url 是**私有部署端点**（`ws-*.maas.aliyuncs.com`），
私有部署可以用自定义模型名。

> 教训：**不要用公有云的命名规律去判断私有部署。**
> 我差点因为"觉得名字不对"而提出一个错误的质疑。
> **配置类问题一律以实测为准，不以经验判断为准。**

**但实测数据暴露了真问题**。同样前 5 条 holdout 样本：

| issue | gold | qwen-max 预测 | F1 | qwen3.8-flash 预测 | F1 |
|---|---|---|---|---|---|
| #64546 | Bug, Visualization | Bug, Visualization | **1.00** | Bug, Visualization, Error Reporting | 0.80 |
| #66550 | Bug | Bug | **1.00** | Bug, Error Reporting, Internals | 0.50 |
| #67970 | Performance | Performance | **1.00** | Performance, Internals | 0.67 |
| #65914 | Bug | Bug, Visualization | 0.67 | Bug, Warnings, Error Reporting | 0.50 |
| #66475 | （空，应转人工） | Bug | 0.00 | Bug, Error Reporting | 0.00 |
| **平均 F1** | | | **0.734** | | **0.494** |

| 指标 | qwen-max | qwen3.8-flash | 变化 |
|---|---|---|---|
| 平均 F1 | 0.734 | 0.494 | **−33%** |
| 单条延迟 | ~17 秒 | 57~241 秒（中位 92 秒） | **慢 5 倍** |
| 平均步数 | 2~3 | 3~7 | 多 1.5 倍 |

**根因：它倾向于"多打标签"。**

每条都多了 1~2 个标签（`Error Reporting` / `Internals` / `Warnings`），
而我们的评测口径是**严格的多标签匹配** ——
多打一个不存在的标签，Precision 就掉一截。

这是 flash 类模型的典型特征：**为召回率牺牲精确率**
（宁可多给，不愿漏给）。

**这个发现的价值在于它推翻了一个想当然的判断**：

```
想当然：更快的模型 = 更低的延迟 = 更好的性价比
实测：  更快 ≠ 够用，在这个任务上它同时更差和更慢
```

**为什么会"更慢"？** 因为它多打标签的同时**步数也变多了**（2~3 → 3~7 步），
而每一步都是一次完整的模型调用。所以"单次快"被"调用次数多"吃掉了。

> **延迟不能只看单次调用，要看"完成任务的总耗时"。**
> 一个单次快但做不对的模型，会花更多轮次去弥补 —— 总账是亏的。

**结论与建议**：

1. **主循环（`agent_step`）建议保留 qwen-max 或 qwen-plus** ——
   分类质量直接决定业务可用性，这里不能省。
2. **`qwen3.8-flash` 适合用在 `memory_extract` / `memory_score`** ——
   这两个任务对"精确率"不敏感（抽取错了会被评分函数过滤掉），
   而且调用量最大，省成本的价值最大。
3. 如果业务侧更关心"不遗漏"（高召回），flash 的多标签可以接受 ——
   **但这需要跟业务确认口径**，不能自己拍。

**改配置的正确姿势**（分档而不是一刀切）：

```bash
# 主循环要质量
NW_MODEL_STRONG=qwen-max
# 记忆抽取量大、对质量不敏感 → 用便宜的
NW_MODEL_SMALL=qwen3.8-flash
NW_MODEL_MEDIUM=qwen-plus
```

**这个案例也验证了项目一开始就写进 `config.py` 的设计**：
`MODEL_ROUTING` 把任务分成三档，**按任务匹配模型** ——
而不是"全用最强"或"全用最便宜"。

**当初那个设计是对的，但我一度想用 `qwen3.8-flash` 替换全部三档，
那正好是它反对的做法。**

### F2. 慢的真正原因：思考链（thinking）—— 以及"关掉它"为什么不是万能解药

**问题的提出**：`qwen3.8-flash` 是 flash 系列，按设计应该比 `qwen-max` 快得多。
实测却慢 5 倍。为什么？

**诊断方法**（`scripts/diagnose_latency.py`）：

直接比"端到端延迟"没有意义，因为延迟里混着三样东西：

```
总延迟 = 排队时间 + 预填充(prefill) + 解码(decode)
```

必须把它们分开，才能回答"是模型慢，还是别的原因"。

**关键指标不是延迟，而是"输出速率"（tokens/sec）** ——
它才反映模型的生成能力。

**实测结果**：

```bash
# 极短输入（"只回复两个字：正常"）
qwen-max           566ms   出=  1 tok          无思考链
qwen3.8-flash     2103ms   出= 40 tok  19.5 tok/s  ⚠含思考链

# 模拟 Agent 真实调用（730 tok 输入 + JSON 输出要求）
qwen-max          3348ms   出=100 tok  29.9 tok/s  无思考链
qwen3.8-flash    18608ms   出=987 tok  53.0 tok/s  ⚠思考链 1839 字符
```

**答案一清二楚**：

| | qwen-max | qwen3.8-flash |
|---|---|---|
| **生成速率** | 29.9 tok/s | **53.0 tok/s** ← 它确实更快 |
| **输出 token** | 100 | **987** ← 但多 10 倍 |
| 端到端延迟 | 3348ms | **18608ms** ← 净效果更慢 |

> **用户的直觉是对的：flash 的生成速度确实更快（快 77%）。
> 但它默认开启了思考链，输出 token 多 10 倍，把速度优势彻底吃掉了。**

**如果它只输出 100 tok**：`100 / 53.0 = 1.89 秒` ——
**比 qwen-max 的 3.35 秒快 43%。**

**验证"关掉思考是否有效"**：

```bash
qwen3.8-flash 默认                      2162ms   出= 87tok  含思考链
qwen3.8-flash enable_thinking=False     1091ms   出= 14tok  无思考链
qwen3.8-flash +thinking disabled         836ms   出= 14tok  无思考链  ← 比 max 快
qwen-max 默认                           1186ms   出= 23tok  无思考链
```

**`enable_thinking=False` 有效**（写进了 `client.py` 的 `disable_thinking` 参数）。

**⚠️ 但"关掉思考"不是万能解药 —— 这是本次最有价值的发现**：

关掉思考后跑同一批评测：

| issue | 带思考 | | 关思考 | |
|---|---|---|---|---|
| | 耗时 | 步数 | 耗时 | 步数 |
| #64546 | 241346ms | 6 | **25761ms** | 5 | ← 快 9.4 倍 ✓ |
| #66550 | 57065ms | 3 | 58113ms | **20（触顶）** | ← F1 0.5 → **0.00** ✗ |
| #67970 | 92502ms | 3 | 50912ms | 9 | |
| #65914 | 83301ms | 4 | 47707ms | 12 | |

**关掉思考后：简单任务快 9 倍，困难任务反而陷入试错循环（3 步 → 20 步触顶）。**

**根因**：**思考链不是纯粹的浪费 —— 它在"任务复杂度"和"输出长度"之间做权衡。**

- 简单任务：思考链是冗余开销 → 关掉更快
- 困难任务：思考链帮助"一次想清楚" → 关掉后想不清楚，只能靠多轮试错弥补
  → **总耗时不降反升，而且可能因为步数触顶而彻底失败**

> **这解释了为什么"单次调用更快"不等于"任务更快"：**
> 一个想不清楚的模型会用更多轮次来弥补，而每轮都是一次完整调用。
> **只优化单次延迟，可能让总耗时变差。**

**结论与建议**：

| 方案 | 适用场景 | 代价 |
|---|---|---|
| **保留思考链**（推荐先这样） | 任务复杂度不确定时 | 单次慢，但步数稳定、质量更高 |
| 关掉思考 + **加强提示词约束** | 任务简单且明确 | 必须同时防"步数暴增"（如明确禁止重复调用、收紧 max_steps） |
| 按任务分档开关 | 能区分简单/困难任务 | 需要先有任务复杂度判断逻辑 |

### F3. 我试了"关思考 + 强化提示词"，**结果更差**（一个被实测推翻的假设）

上面表格里第二行那个"关思考 + 加强提示词"，我实际去做了 —— **失败了**。

**我的假设是**：

> 思考链的作用是"规划"（决定下一步做什么）。
> 那就把流程直接写进提示词 —— 第 1 步查历史、第 2 步查文档、第 3 步给结论，
> 并写死"工具调用最多 3 次"。
> 这样模型不需要自己想规划，应该能既快又稳。

**提示词我写得很细**（`SYSTEM_PROMPT_STRICT`），核心是四条硬规则：
```
1. 工具调用总数最多 3 次
2. 每个工具只用一次，绝不用相似参数重复调用
3. 检索不到就停 —— 不要换关键词再查
4. 不确定就给低置信度并转人工，这比反复检索正确
```
再加一个动态的「步数预算」提示（跑到第 18 步时告诉它"预算即将耗尽"）。

**实测结果——比不加强化提示词还差**：

| 配置 | #64546 | #66550 | #67970 | #65914 | 平均 F1 |
|---|---|---|---|---|---|
| qwen-max（基线） | 1.00 | 1.00 | 1.00 | 0.67 | **0.734** |
| flash + 思考 | 0.80 | 0.50 | 0.67 | 0.50 | 0.494 |
| flash 无思考 + 常规提示词 | 0.67 | 0.00 | 0.67 | 0.50 | 0.46 |
| **flash 无思考 + 强化提示词** | **0.00** | **0.00** | … | … | **≈0.00** |

最后一行：**步数全部触顶 20，输出的标签为空**（完全没有产出）。

**为什么我的假设错了？**

```
原假设：思考链 = 规划能力  →  提示词可以替代规划
实际情况：思考链 = 规划能力 + **判断能力**  →  提示词只能替代前者
```

**关键区别**：

| | 能做到吗 |
|---|---|
| 提示词告诉模型"按什么流程做" | ✅ 能 |
| 提示词告诉模型"在信息不足时该怎么办" | ⚠️ 只能给规则，**但规则覆盖不了所有情况** |
| 模型自己判断"当前信息够不够下结论" | ❌ **这个判断力来自思考链，提示词给不了** |

把流程写死之后发生了更糟的情况：**模型既失去了判断力，又失去了灵活性** ——
它严格执行那个 3 步流程，但走完流程后如果还无法确定答案，
就被卡住了（因为流程里没有"怎么办"的下一步），只能反复重试直到触顶。

**所以最终结论是**：

> **提示词能替代「流程」，但不能替代「判断」。**
>
> 思考链的价值主要在于**判断力**（在不确定时做出合理决策），
> 而不是流程规划。想通过"关掉它 + 写清流程"来省钱省时间，
> 在这个任务上是行不通的。

**这也回答了一个更普适的问题**：什么时候该关思考链？

- ✅ **可以关**：任务足够简单、且判断路径完全可枚举（如"提取字段"）
- ❌ **不该关**：任务需要"在信息不足时做取舍"（如分诊、路由、升级判断）

本项目的任务（issue 分流）属于后者 —— **所以最终配置是保留思考链**
（`client.py` 的 `DEFAULT_DISABLE_THINKING = False`）。

**这个失败实验的价值**：

它排除掉了一个看起来非常合理的方案。
如果不做，我可能会在某个时刻"顺手优化"一下关掉思考链，
然后困惑于"为什么困难 case 全挂了"。

> **负面结果也是结果 —— 而且往往比正面结果更值钱，
> 因为它省掉的是"未来某天的困惑"。**

### ⚠️ 补充：F3 的结论后来被推翻了 —— 真凶是一个低级实现错误

> **这一段是本文档最该读的部分。**
> 因为上面那段"提示词不能替代判断力"的分析写得很像那么回事，
> **但它的证据根本不成立。**

后续做 F4 的提示词调优时，发生了**同样的失败**（步数全部触顶、预测为空）。
顺着这条线排查，发现了真正的共同原因：

**`SYSTEM_PROMPT_STRICT` 从头到尾没有「输出格式」这一节。**

检查三个 prompt 的完整性：

| prompt | 输出格式章节 | 含 `finalize` | 含 `JSON` | 实际表现 |
|---|---|---|---|---|
| `SYSTEM_PROMPT`（原版） | ✅ | ✅ | ✅ | **正常** |
| `SYSTEM_PROMPT_STRICT` | ❌ | ⚠️ 提到了但没给格式 | ❌ | 失败 |
| `SYSTEM_PROMPT_TUNED`（同病） | ❌ | **❌ 连这个词都没有** | ❌ | 失败 |

**原版能工作，是因为它明确写了**：

```
## 输出格式
每次回复必须是一个 JSON 对象：
{"thought": "...", "action": "工具名，或 finalize 表示结束", ...}
```

我写 STRICT / TUNED 版本时**把这一节漏掉了**。

**于是模型不知道"给结论"该怎么表达** —— 它只认得"调用工具"这一个动作，
所以只能一直调工具，直到步数触顶 → 走兜底 → **预测为空**。

**这完美解释了所有现象**：步数全部触顶 ✓、预测全部为空 ✓、耗时不降反升（步数多 × 思考链）✓。

**所以 F3 的失败原因是"模型不知道该输出什么"，而不是"提示词替代不了判断力"。**

**诚实说明这意味着什么**：

上面那段「提示词能替代流程、不能替代判断」的分析，
**是一个看起来深刻的结论，用来掩盖了一个低级的实现错误。**

而且它不容易被发现，因为：
- 现象（失败）是真的
- 分析（思考链负责判断力）逻辑自洽
- 甚至还有"额外佐证"（强化提示词反而更差）

**但这些全是巧合。** 真凶只是一个漏写的章节。

**由此得到一条关于「归因」的教训**：

> **在得出原理性结论之前，先逐项检查实现层面的完整性。**
>
> 一个深刻的结论会让人满意，从而停止排查 ——
> 而"实现有低级错误"这个假设，恰恰因为太朴素而被跳过了。
>
> **排查顺序应该是：先确认输入是完整的（提示词该有的章节都在吗），
> 再讨论模型能力。** 顺序反了，就会把 bug 写成理论。

**修正后的结论**：
- ❌ 「提示词不能替代思考链的判断力」—— **证据不成立，撤回**
- ✅ 待验证：补上输出格式后，STRICT / TUNED 能否正常工作（结果见 F5）

**保留这段被推翻的分析，而不是删掉它** —— 因为
**"如何识别自己写出了看似深刻但没有证据的结论"** 本身就是个值得学的技能。

### F4. 按任务分档控制思考链 —— 方向对，但收益比预期小

**思路**（用户的判断，我认为是对的）：

不要"全部关"或"全部开"，而是**按任务性质分档**：

```
需要判断力的任务（分诊、路由、矛盾裁决）  → 开思考
判断路径可枚举的任务（结构化抽取、子项检查）→ 关思考
```

这个判断标准来自 F2/F3 的实测结论：
**思考链的价值主要是「判断力」，而流程规划只是副产品。**

**实现**：`config.py` 新增 `THINKING_POLICY`，`client.py` 逐任务查表：

| 任务 | 性质 | 策略 |
|---|---|---|
| `agent_step` | 在"继续查"和"下结论"之间取舍 | **开** |
| `memory_resolve` | 语义矛盾裁决 | **开** |
| `memory_extract` | 结构化字段抽取（抽不到就留空，无需权衡） | **关** |
| `eval_judge` | 检查子项（有没有标签/理由/引用） | **关** |

**实测：策略确实生效，单个任务快 2~3 倍**

| 任务 | 思考 | 延迟 | 输出 tok |
|---|---|---|---|
| `agent_step` | 开 | 3674ms | 149 |
| `memory_extract` | **关** | **1650ms** | **57** ← 快 2.2 倍 |
| `memory_resolve` | 开 | 3369ms | 139 |
| `eval_judge` | **关** | **1163ms** | **30** ← 快 2.9 倍 |

**⚠️ 但端到端收益有限 —— 这是必须诚实说明的部分。**

同一批 5 条样本的完整对比：

| 配置 | #64546 | #66550 | #67970 | #65914 | #66475 | 平均 F1 | 平均耗时 |
|---|---|---|---|---|---|---|---|
| qwen-max（基线） | 1.00 | 1.00 | 1.00 | 0.67 | 0.00 | **0.734** | ~17s |
| flash 全开思考 | 0.80 | 0.50 | 0.67 | 0.50 | 0.00 | 0.494 | ~92s |
| flash 无思考 + 强化提示 | 0.00 | 0.00 | — | — | — | ≈0.00 | — |
| **flash 分档策略** | 0.80 | 0.67 | 0.67 | 0.40 | 0.00 | **0.508** | ~98s |

**分档策略 vs 全开思考：F1 从 0.494 → 0.508（+2.8%，在噪声范围内）。**

**为什么提升这么小？**

因为 **Agent 一次任务的调用量分布极不均衡**：

```
一次 triage 的模型调用：
  agent_step      × 3~7 次   ← 占绝大部分（每轮循环都要调）
  memory_extract  × 1 次     ← 只在最后沉淀记忆时调一次
```

关掉 `memory_extract` 的思考，只省掉 `1/(N+1) ≈ 15~25%` 的开销。
**而占大头、且不能省的 `agent_step`，原封不动。**

**所以这个实验得出了一个更重要的判断**：

| 目标 | 该动哪里 | 不该动哪里 |
|---|---|---|
| **降低 token 成本** | ✅ 关掉 `memory_extract` / `eval_judge` 的思考（有效，省 15~25%） | — |
| **提升分类 F1** | ✅ **必须优化 `agent_step`**（换更强的模型 / 优化提示词 / 改进工具） | ❌ 关其他任务的思考，对 F1 没有任何帮助 |

> **这两件事不能混为一谈。**
>
> 我之前把"关掉思考"当成一个统一的性能优化来看，
> 但实测说明：它**只在成本维度有效**，在质量维度无效（甚至有害，见 F3）。
>
> **一个优化手段的作用域，必须先界定清楚再谈它的价值。**

**样本量限制**：以上对比只有 5 条样本，0.014 的差异**没有统计意义**。
要得到可信结论需要跑完整 holdout（85 条）——
但按实测速度（~98 秒/条）需要约 2.3 小时。
这个数字上的不确定性必须标注出来，不能拿 5 条就下结论。

### F5. ★ 口径决定结论：加了 Top-1 指标后，"flash 不如 max"这个结论直接反转了

**这是本文档最有价值的一个案例**，因为它推翻的不是别人的结论，是**我自己前面几轮反复给出的建议**。

**经过**：

我用**严格多标签 F1** 评测，得出 flash（0.494）比 max（0.734）低 33%，
于是在 README 和 `.env` 里写下建议：**"主循环换回 qwen-max"**。

这个建议看起来很有依据 —— 有实测数据、有明确差距。但它**错**了。

**转折点**：给 `eval/metrics.py` 加上 **Top-1 准确率**和 **Hit@k** 后，
用同一批数据重算（median 口径）：

| | 严格 F1 | **Top-1 准确率** | Hit@2 | 过度标注指数 |
|---|---|---|---|---|
| qwen-max (2.5) | 1.000 | **1.000** | 1.000 | +0.40 |
| qwen3.8-flash | 0.667 | **1.000** | 1.000 | +1.40 |

**两者的 Top-1 准确率都是 100%。**

**也就是说：flash 每一次都抓住了最核心的分类，它只是习惯多打几个标签。**

这不是"能力差"，是"输出风格"问题 —— 而风格问题**调提示词就能解决**，
换模型是完全不成比例的过度反应。

**根本原因：严格 F1 隐含了一个不符合业务的假设。**

```
严格多标签 F1 的假设：漏报和误报的代价相同
issue 分流的真实代价：  漏报（漏了正确标签）→ 问题可能被忽略
                        误报（多打了标签）  → 维护者看到无关标签，影响小
```

**代价不对称，但指标假设对称** → 指标系统性惩罚"多打标签"的行为，
把这个行为算成了"能力缺陷"。

**同一批数据，两个都合理的口径，导向完全相反的行动**：

| 口径 | 结论 | 行动建议 |
|---|---|---|
| 严格 F1 | flash 差 33% | **换模型**（成本高） |
| Top-1 | 两者打平 | **调提示词**（成本低得多） |

**教训（这是我要记住的一条）**：

> **当你用单一指标下结论时，先问"换个合理口径，结论还成立吗"。**
>
> 如果换个口径就反转，那说明你测到的差异**不是模型能力差异，而是口径造成的**。
> 此时**任何基于这个指标的优化方向都是可疑的**。

**顺带一个次级教训**：均值和中位数也会给出不同数字 ——
mean 口径是 0.734 vs 0.494，median 口径是 1.000 vs 0.667。
两者都指向"有差距"，但幅度差很多。
**单一统计量 + 单一口径，是双重脆弱。**

**所以现在的评测会**：
1. **并排输出多个口径**（严格 F1 / Top-1 / Hit@2 / Hit@3）
2. **量化过度标注**（平均预测标签数 - 平均 gold 标签数）
3. **自动诊断差异来源** —— 直接告诉读者"这个差距是来自多打标签还是抓不住核心"

第 3 点是关键：**把诊断逻辑写进指标报告**，让读报告的人不用自己推断。

```python
def _sensitivity_note(strict_f1, top1) -> str:
    gap = top1 - strict_f1
    if gap > 0.25:
        return "差异主要来自「多打标签」→ 优先调提示词，换模型未必必要"
    if gap > 0.10:
        return "既有过度标注、也有核心分类错误 → 两者都要处理"
    return "两个口径接近 → 严格 F1 的差距更能反映真实能力，换模型是有效手段"
```

**验证：调优提示词后，三个口径全部追平 max**

既然诊断出"差异来自多打标签"，那就该用提示词解决（而不是换模型）。
针对性地写了 `SYSTEM_PROMPT_TUNED`（标签数量预期 + 主/细分分级 + 给"信息不足"正名），
再测同一批 5 条：

| 配置 | 严格 F1 | Top-1 | Hit@2 | 过度标注指数 | 平均耗时 |
|---|---|---|---|---|---|
| qwen-max (2.5) | 1.000 | 1.000 | 1.000 | +0.40 | **17.0 秒** |
| flash + 常规提示词 | 0.667 | 1.000 | 1.000 | +1.40 | 97.1 秒 |
| **flash + 调优提示词** | **1.000** | **1.000** | **1.000** | **+0.40** | 39.0 秒 |

**逐条对比（常规 → 调优）**：

```
#64546  Bug,Visualization,Error Reporting  →  Bug,Visualization       0.80 → 1.00
#66550  Bug,Internals                      →  Bug                     0.50 → 1.00
#67970  Performance,Internals              →  Performance             0.67 → 1.00
#65914  Bug,Deprecate,Warnings,Visualization →  Bug,Warnings          0.40 → 0.67
#66475  Bug                                →  Bug                     0.00 → 0.00
                                                                平均   0.474 → 0.734
```

**结论**：

1. **质量差距被 100% 抹平** —— 严格 F1、Top-1、过度标注指数**三项全部追平 qwen-max**
2. **耗时也从 97 秒降到 39 秒**（步数 5~7 → 2~3）
3. **所以不需要换模型** —— 这验证了 F5 的诊断结论
4. 唯一残留差异是速度：**39 秒 vs max 的 17 秒**（2.3 倍），
   而这一项可以通过"分档思考链策略"部分缓解（见 F4）

**完整闭环**（这是本文档最有价值的一条链路）：

```
严格 F1 显示 flash 差 33%        → 建议"换模型"（错）
        ↓ 加多口径
Top-1 显示两者打平               → 修正为"调提示词"
        ↓ 定位原因
过度标注指数 +1.40 vs +0.40      → 差异来自"多打标签"
        ↓ 针对性修复
写 tuned prompt                  → 三个口径全部追平
        ↓ 验证
不换模型也能达到相同质量
```

**每一步都改变了下一步的方向，而且每一步都有数据支撑。**
这就是"评测驱动优化"的完整样子 —— 不是先有方案再找数据，而是数据决定方案。

**这个案例的元价值**：它证明了"加一个指标"这件事本身能改变结论 ——
**而这件事只有真正做评测的人才会遇到。**

### F6. 完整 holdout 结果：中位数说"完美"，均值说"有 20% 损失"

**配置**：真实数据（pandas 85 条 holdout）× 真实模型（qwen3.8-flash）× tuned prompt
**耗时**：约 85 分钟

**结果**：

| 指标 | 中位数 | 均值 |
|---|---|---|
| 严格 F1 | **1.000** | **0.800** |
| Top-1 准确率 | 1.000 | 0.785 |
| Hit@2 | 1.000 | 0.835 |

**中位数和均值差了 0.2** —— 这是本项目第三次遇到"单一统计量脆弱"这个问题
（第一次是 mean vs median 的模型对比，第二次是 K=1 vs K=3 的召回率，
第三次就是这里）。

**F1 分布揭示了真相**：

```
F1=1.00 : 56 条  ████████████████████████████████████████████████████████  71%
F1=0.67 : 10 条  ██████████                                                13%
F1=0.50 :  1 条  █                                                          1%
F1=0.00 : 12 条  ████████████                                              15%
```

**71% 的样本完全正确** —— 所以中位数是满分。
但那 15% 的零分把均值拉到了 0.800。**两个数字都是对的，取决于你问什么**：
- 问"典型情况有多好" → 中位数 1.000
- 问"整体期望损失是多少" → 均值 0.800

**分层报告定位了唯一的真短板**：

| 分层 | 样本 | 中位 F1 | 说明 |
|---|---|---|---|
| Bug | 38 | 1.000 | ✓ |
| Docs | 13 | 1.000 | ✓ |
| Enhancement | 5 | 1.000 | ✓ |
| Performance | 5 | 1.000 | ✓ |
| **unlabeled** | **14** | **0.000** | ✗ **全部 12 个零分都来自这里** |

**unlabeled 层细查**：14 条里只有 **2 条**正确转人工（14.3%），其余 12 条**误猜了标签**。

**所以真实情况是**：
- 在**有明确 ground truth** 的样本上（65 条）：均值约 **0.94**
- 在**信息不足**的样本上（14 条）：只有 **14.3%** 判断正确

**总分 0.800 掩盖了这个结构** —— 而分层报告把它暴露出来了。

**这正是"必须分层"的现实意义**：如果只报一个 0.800，
你会以为"模型整体一般"；分层之后才知道"**模型其实很好，只是不会说"我不知道"**"。

**其他指标**：

| 指标 | 值 | 说明 |
|---|---|---|
| 自助解决率 | 95.3% | |
| 转人工率 | 2.4% | **明显偏低** —— 该转的没转（对应上面的 unlabeled 短板） |
| 中位步数 | 2 | tuned prompt 让它很干脆 |
| 过度标注指数 | +0.29 | 接近 0，tuned prompt 有效 |
| duplicate 检测 | **不可报告** | FP=16 但 TP=0 — 数据集里几乎没有 duplicate 标注 |

**下一步明确**：唯一该优化的是**"信息不足"的判断**。
tuned prompt 的规则 3 已经写了"信息不足时输出空"，但模型执行得不彻底
（14 条只遵守了 2 条）。这比"改模型"或"改其他提示词"都更聚焦。

**顺带修复的一个缺陷**：第一次跑完整 holdout 时，JSON 里**只存了汇总指标、没存逐条数据**。
导致我发现"中位数 vs 均值"差异时**无法从 JSON 重算**，
只能回头用正则从日志文本里解析 —— 既脆弱又难看。

> **评测结果必须存逐条原始数据，不能只存汇总。**
> 因为汇总口径是"当时的判断"，而原始数据支持未来任何角度的重算。
> 后来加 Top-1 指标时就是这样：如果当时存了逐条数据，直接重算即可，
> 不用重跑 55 分钟。（已修复）

### F7. ★★ 最严重的一个：gold 标注口径错了，导致模型答对被判 0 分

**这是本文档里代价最高的一个缺陷** —— 它让一份已经跑完的报告结论完全失真。

**发现过程**：F6 报出"unlabeled 层只有 14.3% 正确"，我准备去优化"信息不足的判断"。
动手前先看了那 14 条的**实际内容** —— 结果发现：

| issue | 标题 | 真实情况 |
|---|---|---|
| #66475 | `BUG: read_sas segfaults on a SAS7BDAT file...` | **明显是 Bug** |
| #64426 | `Double braces used in docs in read_csv` | **明显是 Docs** |
| #66699 | `BUG: assert_series_equal ignores atol/rtol...` | **明显是 Bug** |
| #66750 | `BUG: test_spss_metadata fails with pyreadstat...` | **明显是 Bug** |
| #65987 | `Add logging support...`（正文 `## Feature Request`） | **Enhancement** |
| #64730 | `BLD\|CI: Failing to Build Wheels on macosx_x86_64` | **Build/CI** |
| #64312 / #64315 | `Test Issue from API` | ✅ 真·信息不足 |

**14 条里只有 2 条真的信息不足，其余 12 条信息非常充分。**

**模型的预测全部正确**（#66475 预测 Bug、#64426 预测 Docs），**是我把 gold 判错了**。

**根因是一条错误的等价关系**：

```
我在 prepare_dataset.py 里把 gold_labels 收敛为「只保留类型标签」
        ↓
这 12 条的原始标签是领域标签（IO SAS / Plotting / Missing-data），被过滤掉
        ↓
gold 变成空数组
        ↓
我的口径把「空 gold」定义为「正确答案 = 转人工」
        ↓
模型答对了却被判 0 分 ✗，而且我还打算去"优化"一个不存在的问题
```

**如果我没有先看案例就直接改提示词，会浪费一整轮实验，而且方向完全错。**

**修复分三步（每一层都救回一批）**：

**第一步：区分「无标签」和「只有非类型标签」**

```python
if types:            # 有类型标签 → 正常评测
elif has_any:        # 只有领域/流程标签 → 剔除（不是"信息不足"，是"我们没测那一层"）
else:                # 完全无标签 → 才算"该转人工"
```

→ holdout 的 unlabeled 从 14 条降到 10 条

**第二步：发现 pandas 的标题前缀约定**

剩下的 10 条里，8 条的标题带着项目约定前缀：

```
BUG: read_sas segfaults...        TST: pandas/tests/api/... fails
DIST: Include Vendored Licenses   CI regression: Doc Build failing
[BUG] Use-after-free...           BLD|CI: Failing to Build Wheels...
```

**这些前缀本身就是分类信号，而且比维护者的标签覆盖更全**（提交者写标题时的自觉约定）。

加了 `TITLE_PREFIX_TO_TYPE` 映射（BUG/ENH/DOC/TST/BLD/CI/DEPR/PERF/REG/REF/API/VIZ/QST/SEC）

→ unlabeled 从 10 条降到 5 条

**第三步：发现正文小标题也是信号**

`#65987 Add logging support...` 标题没前缀，但**正文第一行是 `## Feature Request`** ——
**项目自带的 issue 模板在帮忙做分类**。

加了 `BODY_HEADING_TO_TYPE`（在正文前 15 行里找 markdown 小标题）

→ **unlabeled 从 5 条降到 2 条（holdout 内）**

**最终统计**：

```
① 有类型标签        253 条（84.3%）
② 只有领域标签       13 条 → 剔除
③ 无标签但有前缀      25 条 → 从标题前缀 / 正文小标题推断出类型
④ 完全无信息          9 条 → 该转人工
```

（从最初的 34 条"无信息"降到 9 条）

**三条教训**：

**① 「没有 gold」和「gold 被过滤掉了」是两件完全不同的事。**
把它们混为一谈，会让模型背锅，还会让优化方向完全跑偏。

**② 领域约定要靠通读数据发现，不能靠看文档。**
`BUG:` / `TST:` / `DIST:` 这类前缀约定，任何文档里都不会写 ——
它们是社区实践中形成的。
**这正是"第 0 周人工通读 30~50 条"的真正价值**：它找的是这类没被记录下来的隐性规则。
（我在 `docs/01` 里写了这件事，但自己在实现时也漏了 ——
说明"知道要做"和"真的做了"之间差得很远。）

**③ 在动手修之前，先看几个真实案例。**
我原本已经准备好去改提示词（教模型"信息不足时输出空"），
目标是把那 14 条的准确率从 14.3% 提上去。
**如果直接动手，会浪费一整轮实验，而且优化的是一个不存在的问题。**

> **看 5 分钟数据，省 1 小时实验，而且避免方向性错误。**
> 这是本文档里最实用的一条操作建议。

**关键是有工具能让问题暴露**：trace、诊断脚本、单元测试、分层指标、

没有这些，上面每一个问题都会**静默地留在代码里**。

特别是 E 类 —— 它们全部需要真实模型才能暴露。
**Mock 跑一万遍也不会告诉你"模型会把 action 写成对象"。**

## 可迁移的七条原则

把上面 16 个案例抽象一下：

### 1. 完美等于可疑

F1 = 0.000 和 F1 = 1.000 都是信号 —— 信号是"先检查评测代码"。
真实系统的指标很少这么极端。

（同理：压测里"两组都是 100%"也是可疑信号，第一反应应该是
"压力是不是没形成"，而不是"设计没用"。）

### 2. 缺失不是中间值

没有反馈 → `None`，不是 `0.5`。
没有数据 → 留空，不是填平均值。
用中间值代替缺失，会污染整个计算，而且**不报错**。

### 3. 跨模块的契约要显式

上游的输出结构就是下游的输入契约。
少一个字段，下游一个模块整体失效 —— 而每个模块单测都是过的。

### 4. 不同量纲的分数不要混排

排序前先确认所有候选可比。不可比就归一化，或者分开处理。

### 5. 用痕迹而不是信号

"工具真的被调用过" > "上下文里有个约定的字符串"。
痕迹是可验证的，信号是约定的。

### 6. 过程证据要看全过程，不能只看终态

"是否发生过某事"这类问题，必须累加所有轮次。
只看最后一次，等于在灾难发生之后去现场。

### 7. 说"实验没测出差异"之前，先确认干预真的生效了

这是第 6 条的自然延伸，但它值得单列，因为它对应一个更贵的错误：

> **用一个无效实验得出一个"设计没用"的结论。**

所以任何对照实验都应该有**前置的有效性检查**：

```
先确认：处理组确实被处理了（驱逐/压缩真的发生了）
再看：  效果组之间有没有差异
```

如果第一步没过，第二步的结论**无论是什么都不能采信** ——
包括"两组没差异"这个看起来最保守的结论。

在压测脚本里，这就是那段 `实验有效性检查`：

```python
if total_evicted == 0 and total_compressed == 0:
    print("本次实验的结论不予采信 —— 上下文压力没有真正形成")
```

**并且要给出修复路径**（加大 padding / 减小 window），
而不是只说"实验失败"。一个有用的失败信息必须包含"下一步怎么做"。

### 8. Mock 能验链路，**不能验效果** —— 而且真实数据可能推翻 Mock 的结论

这是全书最重要的一条，因为它是从 E 类缺陷里总结出来的。

| 能力 | Mock | 真实模型 |
|---|---|---|
| 验证代码链路能跑通 | ✅ | ✅ |
| 验证错误处理路径 | ✅（可以构造） | ✅ |
| **验证提示词的有效性** | ❌ | ✅ |
| **验证输出格式的健壮性** | ❌ | ✅ |
| **给出可用于报告的指标** | ❌ | ✅ |

具体到本项目的三个例子：

1. **Mock 测不出"action 是对象"** —— 它按设计输出，永远规范
2. **Mock 高估了状态卡的价值** —— 66.67% vs 真实的 16.67%
3. **Mock 看不到"步数触顶"这种失败模式** —— 它不会空转

**所以正确的顺序是**：

```
先用 Mock 把链路跑通（快、免费、确定性）
      ↓
再用真实模型验证效果（慢、花钱、有随机性）
      ↓
两者结果不一致时，**以真实模型为准**，并解释差异来源
```

**最后一句尤其重要**：如果只跑 Mock 就下结论"我的设计带来 66.67% 提升"，
那这个数字在面试被追问时会站不住 —— 因为真实场景下它只有 16.67%。

**宁可报一个小而真的数字，不要报一个大而假的数字。**

## 最后一条，也是最重要的一条

回看这 16 个案例，有一个共同点：

> **它们全都没有让程序崩溃，全都只是让效果变差了。**

没有异常堆栈、没有测试红灯（在写测试之前）、日志一切正常。
如果只看"程序能不能跑"，它们**一个都发现不了**。

所以真正让它们暴露出来的，是这四样东西：

| 工具 | 发现了什么 |
|---|---|
| **trace** | 每轮的上下文占用、驱逐/压缩记录、记忆召回明细 |
| **诊断脚本** | 一次性把"记忆到底写没写进去"查清楚，而不是猜 |
| **分层指标** | 总分 0.69 看起来还行，分层才看出有一整类是 0 |
| **实验有效性检查** | 阻止了"用无效实验得出结论" |

**这四样东西的工程量加起来不到整个项目的 20%，
但它们决定了剩下 80% 的代码到底有没有在起作用。**

如果只记住一件事，记住这个。
