
# Nightwatch

**带长程记忆的开源项目维护 Agent** —— 接管 issue 队列的一级分流与处理建议，
在工具失败、任务循环、记忆冲突的情况下能可靠降级，并用**维护者的真实动作**
作为 ground truth 验证效果。

> AI 处理高频判断，人处理异常决策。

---

## 这个项目想解决什么

开源项目维护者每天面对大量 issue，其中很多是重复的、信息不全的、或者根本
不属于这个仓库的。分流这件事高频、半结构化、输出可判定 ——
**恰好是 Agent 最能发挥价值的场景**。

但真正难的不是"分类"，而是三件事：

| 难点 | 现象 | 本项目的做法 |
|---|---|---|
| **会忘事** | 跑长任务后忘记最初的约束 | 三层记忆 + 任务状态卡每轮重注入 |
| **会卡住** | 调三个工具开始死循环，烧完 token | 四层可靠性：重试 / 熔断 / 循环检测 / 兜底 |
| **会污染** | 一次误判写进记忆，之后反复复用错误 | 写入评分 + 冲突进 pending 队列交人工 |

## 快速开始（零配置，30 秒）

不需要 API key，不需要数据库，不需要网络：

```bash
cd "项目目录"
python scripts/run_demo.py
```

你会看到三段演示：
1. **记忆效果**：同一个提交者的第二个相似问题，处理得更快（步数 -33%、Token -32%）
2. **循环检测**：让 Agent 陷入循环，看它自己停下来
3. **上下文卸载**：工具返回 25000 tokens，自动卸载为「摘要 + 可回读的指针」

跑测试：
```bash
python scripts/run_tests.py        # 35 个用例
```

跑完整评测：
```bash
python scripts/run_eval.py
```

跑长程一致性压测（验证"任务状态卡"这个核心设计）：
```bash
python scripts/run_longhorizon.py
```

> ⚠️ 以上默认用 **合成数据 + Mock 模型**，指标只能验证"流程正确"，
> **不能写进简历**。见下方「如何得到可写进简历的数字」。

## 七个工具（刻意克制）

Gartner 把「用 50+ 工具的通用 Agent」点名为失败模式。所以工具控制在 **7 个**，
每加一个都要能回答"为什么非它不可"：

| 工具 | 作用 | 类型 |
|---|---|---|
| `search_issues` | 关键词检索历史 issue | 只读 |
| `search_similar_issues` | **语义检索 + 判重**（含 `likely_duplicate` 判定） | 只读 |
| `read_code` | 读代码/堆栈（白名单路径） | 只读 |
| `search_docs` | 查维护规范 / SOP | 只读 |
| `apply_labels` | 打标签（**幂等 + 只增不减**） | 写 |
| `post_comment` | 发建议评论（**幂等 + 可回滚**） | 写 |
| **`review_pr_diff`** | **PR diff 结构风险初审**（P2-3 新增） | 只读 |

**分级策略**：只读工具直接执行；写操作进沙箱 + 幂等 + 可回滚。
（面试原题："沙箱是数据隔离还是执行隔离？" —— 答案是**要同时做**，
两者是不同层面：数据隔离管"能看到什么"，执行隔离管"能做什么"。）

**关于 `review_pr_diff`**：它的性质与前六个不同 ——
前六个是"围绕一个 issue 做分诊"，它是**另一类任务**（读代码改动评风险）。
所以它不是"第七个工具"，而是 **CodeAgent 方向的第一个工具**。

> **数量类断言应该表达"约束"而不是"快照"。**
> 测试里断言的是 `<= 10` 而不是 `== 7` ——
> 真加到第 11 个时，该停下来重新想架构，而不是顺手改数字。

### 长程一致性压测结果（核心设计验证）

项目有一个核心设计主张：**把约束放进"任务状态卡"每轮重注入，就不怕长任务里指令漂移。**

用 **三组对照** 验证（`scripts/run_longhorizon.py`）：

| 组 | 说明 |
|---|---|
| **A** | system prompt 有约束 **+** 任务状态卡每轮重注入 ← **完整设计** |
| **B** | system prompt 有约束 **+** 无状态卡（约束只在开头说一次） |
| **C** | system prompt **无**约束 + 无状态卡 ← 真的没有任何保护 |

#### 真实模型结果（每格 2 次取中位数）

| 上下文轮数 | A 完整设计 | B 仅 system 约束 | C 无保护 |
|---|---|---|---|
| 0 | 100.00% | 100.00% | **66.67%** |
| 30 | 100.00% | 100.00% | **66.67%** |
| 60 | 100.00% | **66.67%** | **33.33%** |
| 100 | 100.00% | **83.33%** | **66.67%** |

**逐层贡献分解（100 轮时）**：

```
C → B   +16.67%    ← system prompt 里那份约束的贡献
B → A   +16.67%    ← 任务状态卡的增量贡献
合计    +33.33%
```

#### 两个反直觉的发现

**① C 组不是在"违反约束"，而是根本完不成任务。**

看它的过程指标：**步数恒为 20（等于轮数上限）、引用 0 条、置信度 0.00**。
它跑满 20 轮在空转 —— 这比"给出错误的自信答案"更彻底地失败。

→ 说明 system prompt 里的约束不只是"提高遵从度"，而是**让任务可完成的基础**。

**② 压力下才显出差异。**

- 0/30 轮（无驱逐）：A 和 B 都是 100%，**状态卡没有增量价值**
- 60/100 轮（触发驱逐 17/57 次）：B 开始波动，A 保持 100%

→ 这恰好符合设计假设：**状态卡对抗的是"长上下文导致的信息丢失"**，
   没有信息丢失时它确实是多余的。

#### Mock 版对照（同一套脚本，规则版模型）

| 上下文轮数 | A | B | C |
|---|---|---|---|
| 0 | 100.00% | 100.00% | 33.33% |
| 100 | 100.00% | 33.33% | 33.33% |

**Mock 高估了状态卡的价值**（B 组差异 66.67% vs 真实的 16.67%）。
原因：Mock 的 `has_constraint` 只认状态卡里那两个精确字符串，
而真实模型能读懂 system prompt 里的完整准则。

> **这是"Mock 能验链路、不能验效果"的最好例证 ——
> 而且真实数据推翻了 Mock 给出的乐观结论。**
> 详细复盘见 [`docs/05`](docs/05-开发实录-真实缺陷复盘.md) 的 E 类。

#### 这次实验暴露的三个真实缺陷

1. **实验设计缺陷 ①**：第一版只有 A/B 两组，漏掉了"system prompt 里也有约束"这件事
2. **实验设计缺陷 ②**：对照组只关状态卡，却连任务信息一起关了（混淆变量）
3. **代码缺陷**：真实模型会把 `action` 输出成**对象**而不是字符串，
   导致 `TypeError: unhashable type: 'dict'` —— **Mock 永远测不出来**

| 记忆命中率 | 28.6% | 召回后被实际使用的比例 |
| 约束遵守率（40 轮压力） | 100% vs 33% | 有状态卡 vs 无状态卡 |

**这些数字只说明流程跑通了。** 原因是：合成数据的症状描述比真实 issue 规整得多，

## 如何得到可写进简历的数字

**这是本项目最重要的一节。** 面试官一定会追问实验设置，编的数字撑不过三个问题。

```bash
# 第 1 步：选一个活跃的开源项目，采集真实 issue
#         （先看统计，确认这个项目的 ground truth 够用）
python scripts/collect_issues.py --repo owner/name --limit 300 --stats

# 第 2 步：采集并保存
python scripts/collect_issues.py --repo owner/name --state closed \
    --limit 300 --save data/real_dataset.json

# 第 3 步：配置真实模型与语义 embedding
export NW_LLM_API_KEY=sk-xxxx

# 第 4 步：在留出集上跑最终数字
python scripts/run_eval.py --dataset data/real_dataset.json --real-llm --holdout

# 第 5 步：重新标定阈值（换了 embedding 必须重标）
python scripts/sweep_threshold.py
```

**三条纪律**（写在 `eval/metrics.py` 里，也被测试守住）：
1. 不报单次最好成绩 —— 报多次的中位数和分布
2. 不只报赢的那组 —— 没有提升的情况要如实说明
3. 所有指标注明样本量 —— 并主动说明置信区间

## 配置真实模型（可选，但出简历数据必须做）

项目默认零配置可跑（Mock 模型 + 哈希伪向量）。要用真实模型，三步：

```bash
# 1. 安装可选依赖（调用真实 API 需要）
pip install httpx

# 2. 配置 key
cp .env.example .env        # 然后把 key 填进去
#    .env 已被 .gitignore 忽略，不会提交到 git

# 3. 验证配置（会逐项检查 + 估算成本）
python scripts/check_api.py
```

`check_api.py` 做五件事，**顺序是有讲究的**（从最基础的条件开始查）：

```
0. 依赖检查        httpx 装了吗
1. 环境变量检查    key / base_url / 模型映射
2. 三档模型连通性  ★ 很多账号并非所有型号都有权限，
                      不分档测会在跑到一半时突然 403
3. 向量编码器      ★ 能识别"静默降级到哈希版"——
                      降级了却不知道，会误以为"真实模型效果就这水平"
4. 真实 triage 冒烟  ★ 用实测 token 量反推压测成本（不是估算，是实测）
```

配好之后可以跑真实模型版压测：

```bash
# 先小规模验证（1 次，只跑两个端点）
python scripts/run_longhorizon.py --real-llm --paddings 0,100 --runs 1

# 确认无误再跑完整版
python scripts/run_longhorizon.py --real-llm --runs 3 \
    --json data/longhorizon_real.json
```

### 思考链策略（按任务分档，不是一刀切）

新一代码模型默认开启**思考链**（reasoning），它会在回答前生成一段推理内容，
**这部分算作输出 token 并计入延迟**。实测 `qwen3.8-flash` 因此输出 token 多约 10 倍
（987 vs 100），把"更快"的优势彻底吃掉。

但**"关掉思考"不是无脑优化** —— 实测发现关掉后困难 case 会陷入试错循环
（步数 3 → 20 触顶），加"强化提示词"也救不回来。原因是：

> **提示词能替代「流程」，但不能替代「判断」。** 思考链的价值主要在判断力。

所以本项目**按任务性质分档**（`config.THINKING_POLICY`）：

| 任务 | 性质 | 策略 | 实测延迟 |
|---|---|---|---|
| `agent_step` | 在"继续查"和"下结论"之间取舍 | **开** | 3674ms |
| `memory_resolve` | 语义矛盾裁决 | **开** | 3369ms |
| `memory_extract` | 结构化字段抽取（路径可枚举） | **关** | **1650ms** |
| `eval_judge` | 检查子项（有没有标签/理由/引用） | **关** | **1163ms** |

**判断标准**：
- ✅ 可以关：任务确定、判断路径**完全可枚举**（抽不到就是抽不到）
- ❌ 不该关：需要**在信息不足时做取舍**（分诊、路由、升级判断）

**⚠️ 但要说清收益边界**：这个策略**只在成本维度有效**（省 15~25% token），
在质量维度无效。因为一次 triage 里 `agent_step` 要调 3~7 次（占大头），
`memory_extract` 只调 1 次。

### 多口径评测（口径决定结论）

评测**并排输出多个口径**，而不是只给一个 F1：

| 口径 | 含义 | 适合的判断 |
|---|---|---|
| **严格 F1** | 多标签严格匹配（假设漏报=误报） | 要求"不多不少刚刚好" |
| **Top-1 准确率** | 只看预测的第一个标签 | 只关心核心分类对不对 |
| **Hit@2 / Hit@3** | 正确标签是否在前 k 个里（召回导向） | 宁可多给候选，不能漏 |
| **过度标注指数** | 平均预测标签数 − 平均 gold 标签数 | 量化"爱多打标签"的倾向 |

**为什么必须多口径** —— 一个真实的反转（同一批 5 条样本）：

| 配置 | 严格 F1 | Top-1 | 过度标注 | 平均耗时 |
|---|---|---|---|---|
| qwen-max (2.5) | 1.000 | 1.000 | +0.40 | 17.0 秒 |
| flash + 常规提示词 | 0.667 | **1.000** | +1.40 | 97.1 秒 |
| **flash + 调优提示词** | **1.000** | **1.000** | **+0.40** | 39.0 秒 |

**读法**：
- 只看严格 F1 → "flash 差 33%，**换模型**"（贵，且错）
- 看 Top-1 → "两者打平，只是多打标签 → **调提示词**"（对，且已验证有效）

**结果：调优提示词后三个口径全部追平 max，质量差距 100% 被抹平，不用换模型。**
唯一残留的是速度差异（39 秒 vs 17 秒）。

所以报告里还会**自动诊断差异来源**：如果宽松口径明显高于严格口径，
说明差距来自"多打标签"（调提示词即可），而不是"抓不住核心分类"（才需要换模型）。

> **单一指标下的结论，先问"换个合理口径还成立吗"。**
> 换个口径就反转的差异，不是能力差异，是口径造成的。

（完整实测数据与失败实验见 [`docs/05`](docs/05-开发实录-真实缺陷复盘.md) 的 F1~F5）

也可以不用 `.env`，直接设环境变量（临时值优先级更高，方便一次性覆盖）：

```bash
export NW_LLM_API_KEY=sk-xxxx     # Linux/macOS
set NW_LLM_API_KEY=sk-xxxx        # Windows CMD
$env:NW_LLM_API_KEY="sk-xxxx"     # PowerShell
```

## 一句话总结设计原则

> **不要为了显得完整而堆模块，要为每个模块能讲清"为什么非它不可"。**

工具定稿 6 个、不套 Agent 框架、不引入向量数据库、
评测集不填假数字 —— 每一条都是克制的选择，而不是能力的欠缺。
