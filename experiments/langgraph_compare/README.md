# LangGraph 对照实验

用 LangGraph 重写 Nightwatch 的一条核心链路，与手写版做逐项对照。

**完整文档见 [`docs/08-LangGraph对照实现.md`](../../docs/08-LangGraph对照实现.md)** ——
包含设计思路、实现步骤、关键代码说明、与原方案的对照关系。

---

## 为什么做这个

Nightwatch 的主项目**零第三方依赖**（核心链路全手写）。这个选择有理由，
但有个风险：

> **"我没用框架"和"我不会用框架"从外面看是一样的。**

这个实验的作用是**把"手写 vs 框架"从观点变成实测** ——
两个都做过，并且能讲出差异。

## 怎么跑

```bash
cd "D:/agent program"

# 1. 装依赖（只装到实验环境，主项目不受影响）
pip install langgraph

# 2. 跑对照
python experiments/langgraph_compare/compare.py

# 3. 看导出的流程图（可粘贴到 https://mermaid.live 渲染）
cat experiments/langgraph_compare/graph.mmd
```

## 文件

| 文件 | 作用 |
|---|---|
| `shared.py` | **两版共用的部分** —— 提示词 / 动作解析 / 组件 / 样本 |
| `custom_agent.py` | 手写版（基线） |
| `graph_agent.py` | LangGraph 版 |
| `compare.py` | 对比运行器 |
| `dim_sweep.py` | **嵌入维度单变量对照**（64/256/1024，只改 dim 一个变量） |
| `compare_result.json` | 对照结果（运行时生成） |
| `graph.mmd` | 导出的流程图（运行时生成） |

## ★★ 嵌入维度：为什么是 256

`EMBED_DIM = 256` —— **这个值等于主项目 `HashEmbedding` 的默认值**
（`src/nightwatch/memory/store.py:199`）。

早期版本这里写的是 `dim=64`（**实验脚本自己拍的，不是默认值**），
结果哈希碰撞严重到"完全无关"的样本也拿到 0.587 ——
比"该命中"的 #901（0.473）还高，**两组分布重叠、任何阈值都切不开**。

`dim_sweep.py` 的结果（只改 dim，其余全部共用）：

| dim | 相关组区间 | 无关组最高 | 空档 | 结论 |
|---|---|---|---|---|
| 64 | [0.473, 0.668] | 0.587 | **−0.115** | 重叠，切不开 |
| **256** | [0.355, 0.568] | 0.293 | **+0.061** | 分得开（余量小） |
| 1024 | [0.366, 0.550] | 0.222 | +0.144 | 分得开（余量充足） |

**选 256 而不是更宽松的 1024**，理由是"对齐主项目"：
减少一个变量、发现的问题更可能是真的、**实验不该比被测系统更稳健**
（否则测不出真实系统的脆弱点）。

⚠️ 代价：256 的空档只有 +0.061，而且**阈值到下限只有 +0.027**（阈值 0.32）。

⚠️⚠️ **阈值和 dim 是绑定的，改一个必须重标另一个。**
`MIN_RECALL_SIMILARITY = 0.32` 是按 **256 的**空档 [0.293, 0.355] 取的中点
（0.324）往"危险的一侧"让了 0.004。**改了 `EMBED_DIM` 就必须重取中点** ——
正确顺序：改 dim → 跑 `dim_sweep.py` 看新空档 → 取新中点 → 重跑 compare + 测试。
（旧值 0.30 是按 dim=1024 的空档取的中点，换成 256 后它**不再是任何中点**。）

⚠️ 另外注意：dim 提高会让**所有**余弦分数普遍下降
（#901 从 0.473 → 0.366）。所以"区分度出现"里含有**尺度变化**的成分，
不是纯碰撞消除 —— 跨维度比较绝对分数是没有意义的。
**这也是"阈值必须随 dim 重标"的根本原因。**

**改样本措辞后要重跑 `dim_sweep.py` 和全量测试** —— 余量很薄。

## ★ 这个命令才是关键

```bash
python experiments/langgraph_compare/compare.py
```

它会产出**五类可验证的数据**：

1. **功能等价性** —— 两版的预测是否一致（不一致说明对照不成立）
2. **编排代码量** —— 只算代码行，不算注释
3. **运行时开销** —— 多次重复的中位耗时
4. **框架多给了什么** —— 逐条**实测**，不引用文档
5. **框架藏起了什么** —— 从实写遇到的摩擦点提取

## ★★ 看结果时先看这三个数字（顺序不能反）

```
① 循环覆盖   几成的运行走了 ≥2 步？       ← 前提
② 一致率     两版**行为一样**吗？         ← 结论（的一半）
③ 准确率     两版**都对**吗？             ← 结论（另一半）
```

**前提不成立时，结论再好也没意义；而少了 ③，② 会骗你。**

这个实验真的吃过两次亏：

**第一次**：第一版报告里一致率是 **100%**，脚本正常退出、报告正常生成 ——
但**循环一次都没跑**（`0/15` 次走到第 2 步），而且 6 个样本里 2 个两版都返回空。
那个 100% 建立在"两版都在第 1 步就结束"上，
而"框架版更多的那几十行"里有相当一部分是**从未被执行的代码**。

**第二次（2026-10-11）**：一致率 100%、循环覆盖也正常 ——
但补上准确率后才发现**只有 50%**：

```
一致率 100%  +  准确率 50%  =  **两版一起错**
```

两版可以在同一个地方一起错，然后拿到 100% 的一致率
（docs/08"坑 2"：对称的错误最危险）。**"一致"只证明行为相同，
不证明行为正确。** 所以报告现在会显式告警，
并且**在准确率不满时不再打印"✓ 两版功能等价"**。

**这三个指标都被单独统计，且异常时会直接告警** ——
已写进 `compare_result.json`，也被 `TestCompareExperiment`
这组测试守着（**8 个用例**，守的是"实验的前提"，不是"实验的结论"）。

当前状态（2026-10-11 依赖注入改造后）：

```
循环覆盖     6/18 次运行走了 ≥2 步（步数分布 {1: 12, 3: 6}）
预测一致率   100%（6/6）
有效一致率   6/6（排除两版都为空的 0 个）
准确率 Top-1 手写 50% / LangGraph 50%   ← ⚠ 未满，两版一起错
✗ 等价性结论无效 —— 一致率 100%，但准确率只有 50%
```

⚠️ **准确率这一项现在是 50%，不是满分**，根因是标签体系三层不匹配
（`parse_final` 字段名 + 子串兜底 + `MockLLM` 的"记忆优先"没生效）。
**已经定位到具体行，但修复要动主项目，所以另开一轮** ——
详见 `compare.py` 的输出告警和 `docs/08`。

**依赖隔离**

```
src/nightwatch/          ← 零第三方依赖，主项目不受影响
experiments/             ← 这里才用 langgraph
```

`pip install -r requirements.txt` **不会**拉 langgraph。
两个环境互不干扰 —— 因为"想用某个工具做实验"和"想让项目依赖它"是两件事。

## ★ 两个数字的含义在本轮变了（2026-10-11）

改了一处实现，**两个结论的"含义"就变了**（数字本身变化不大，但可解释性完全不同）：

**① 耗时：从"不能归因"变成"可归因"**

```
改造前：手写 2ms / 框架 8ms   ← 差值里混着"每轮回边重建组件"
改造后：手写 1ms / 框架 5ms   ← 两版组件生命周期已对齐
        扣掉两版都要付的那一次组件构造（≈1.06ms）→ 纯编排差价 +4ms
```

原因：`graph_agent` 的节点原来**各自调 `setup_tools()`**（每轮回边重建一次
MemoryStore + 工具集，单次 ≈1.06ms；1 步的样本重建 2 次、3 步的 4 次）。
改成 `config["configurable"]` 依赖注入后，两版都是**一次运行建一次**。

**同一个 8ms，改造前有一半以上在骂我自己写的补丁 —— 现在才是在测框架。**

**② LOC：`+89%` 不是收口补丁撑出来的（一个被实测推翻的假设）**

```
                    全部代码行      其中生命周期     纯编排
手写版                  89            11           78
LangGraph 版           163            15          148
差                    +74           —           +70
百分比                 +83%          —          +90%   ← 反而更高
```

我一度怀疑"框架版多出来的行主要是**我自己加的收口补丁**"——
那个猜测听起来很谦虚，所以很容易直接写进结论。
**但实测推翻了它**：补丁删掉后，扣掉生命周期反而差得更多，
因为手写版的生命周期占比（12.4%）比框架版（9.2%）还高。

> **"对自己不利的猜测"和"对自己有利的猜测"一样需要验证。**

（`compare.py` 会把这两类开销**分开算** —— 源码里用
`# [lifecycle]` / `# >>> lifecycle: begin` 标记，代码改了计数自动跟着变。）
